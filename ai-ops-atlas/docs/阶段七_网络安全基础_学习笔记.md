## 1. 为什么必须懂安全

### 1.1 一个残酷的现实

```
   你以为的网络：                     真实的网络：
   ┌─────────────┐                  ┌─────────────┐
   │  用户 ──▶ 服务器 │                │  用户 ──▶ 服务器 │
   └─────────────┘                  │    ▲   ▲   ▲    │
                                    │    │   │   │    │
                                    │  黑客 内鬼 扫描器 │
                                    └─────────────────┘
```

**只要设备联网，就暴露在攻击面之下。** 安全不是"加个防火墙"就完事，而是一整套**体系化思维**。

### 1.2 为什么"防御者"总是被动的

> 💡 **术语解释｜攻防不对称（Asymmetry of Attack and Defense）**
> **攻击者只需要找到一个漏洞，防御者要堵住所有漏洞。**
>
> - 攻击者：成本低、手段多、可反复尝试
> - 防御者：必须**全面覆盖**，任何一个疏漏都可能被突破

**这就决定了安全的三个基本认知：**

| 认知 | 含义 |
|---|---|
| **没有绝对安全** | 安全是"降低风险"，不是"消灭风险" |
| **纵深防御** | 不能只靠一道防线，要层层设防 |
| **安全是过程** | 不是一次性的，要持续监控、迭代 |

> 💡 **术语解释｜纵深防御（Defense in Depth）**
> 在网络的不同层次、不同环节**部署多重防护**，让攻击者突破一层后还要面对下一层。
>
> **类比**：城堡有护城河、城墙、城门、内城、卫兵——**任何一道被突破，都还有下一道**。
>
> ```
>   边界防火墙 → DMZ → 内部防火墙 → 主机防火墙 → 杀毒软件 → 数据加密
>   （一层被突破，还有下一层）
> ```

> 📌 **本阶段的核心目标**：**建立"威胁—脆弱性—风险—防御"的完整认知链条**，并能识别常见攻击、说出对应防御。

## 2. 安全模型：CIA 三要素与安全思维

### 2.1 CIA 三要素：安全的"三根支柱"

> 💡 **术语解释｜CIA 三要素（CIA Triad）**
> 信息安全的三个核心目标，是所有安全工作的出发点和衡量标准：
>
> | 要素 | 英文 | 含义 | 被破坏的后果 |
> |---|---|---|---|
> | **机密性** | Confidentiality | 信息**不被未授权者获取** | 数据泄露（密码、隐私） |
> | **完整性** | Integrity | 信息**不被未授权篡改** | 数据被改（转账金额、订单） |
> | **可用性** | Availability | 授权用户**需要时能正常访问** | 服务瘫痪（DDoS） |

**用一张图理解三者关系：**

```
              ┌─────────────────┐
              │   CIA 三要素     │
              └────────┬────────┘
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   机密性(C)       完整性(I)       可用性(A)
   防泄露          防篡改          防中断
        │              │              │
   加密、权限      哈希、签名      冗余、备份
   访问控制        校验和          抗DDoS
```

**每种攻击破坏的是哪个要素？**

| 攻击 | 破坏的要素 |
|---|---|
| 数据泄露、窃听 | **机密性** |
| 中间人篡改、SQL 注入改数据 | **完整性** |
| DDoS、勒索软件 | **可用性** |
| 钓鱼窃取账号 | 机密性（+身份） |

> 📌 **行业侧重不同**（理解 CIA 的"权衡"）：
> - **金融**：优先**完整性**（防篡改）+ **可用性**（高并发交易）
> - **军事**：优先**机密性**（严防泄露），可用性可适度牺牲
> - **医疗**：三者并重（病历加密 + 处方防篡改 + 急诊 24/7）
>
> **安全没有"全都要"的完美解，只有"按业务权衡"的合理解。**

### 2.2 威胁、脆弱性、风险：安全分析的三个关键词

> 💡 **术语解释｜威胁（Threat）**
> 可能对系统造成损害的**潜在因素**。包括**人为**（黑客、内鬼）和**自然**（火灾、断电）两类。

> 💡 **术语解释｜脆弱性（Vulnerability，也叫漏洞）**
> 系统**本身存在的弱点**，是威胁能够得逞的"入口"。如未打补丁的软件、弱密码、配置错误。

> 💡 **术语解释｜风险（Risk）**
> **风险 = 威胁 × 脆弱性 × 影响**。即"某个威胁利用某个漏洞，造成多大损失"的可能性。

```
   威胁（谁想搞你）  ×  脆弱性（哪里有洞）  =  风险（可能出多大事）
        │                      │                      │
      黑客                   未打补丁              数据泄露
      内鬼                   弱口令                服务中断
      恶意软件               配置错误              资金损失
        │                      │                      │
        └──────────────────────┴──────────────────────┘
                               │
                    安全措施 = 降低风险
                    · 减少威胁（威慑、溯源）
                    · 修补脆弱性（打补丁、加固）
                    · 降低影响（备份、隔离）
```

> 📌 **安全的正确姿势**：**不是"消除所有威胁"（做不到），而是"持续降低风险"**。识别资产 → 评估威胁与脆弱性 → 计算风险 → 采取对应措施。

### 2.3 核心安全原则

| 原则 | 含义 | 例子 |
|---|---|---|
| **最小权限原则（Least Privilege）** | 只给完成任务**必需的最小权限** | 数据库账号不给 DROP 权限；员工不默认给管理员 |
| **职责分离（Separation of Duties）** | 关键操作**多人分管**，防止单人作恶 | 财务付款需双人审批 |
| **默认拒绝（Default Deny）** | **白名单**思维，未明确允许的一律拒绝 | 防火墙默认全禁，只放行必需端口 |
| **纵深防御** | 多层设防，不依赖单一防线 | 防火墙 + WAF + 主机防护 + 加密 |
| **最小暴露面** | 只暴露**必需的服务** | 关掉不用的端口、服务 |
| **零信任** | 永不信任，持续验证 | 见第 10 章 |
| **安全审计** | 所有关键操作**留痕可追溯** | 日志记录、操作审计 |

> ⚠️ **"默认拒绝"和"默认允许"的区别至关重要**：
> - **默认允许**（黑名单）：先放行，发现坏人才拦 → **容易漏**
> - **默认拒绝**（白名单）：先全禁，只放行认识的 → **更安全**
>
> **安全领域几乎都采用"默认拒绝"思维。**

## 3. 密码学基础（一）：对称加密

密码学是网络安全的**技术基石**。HTTPS、VPN、SSH、数字签名……底层全是密码学。

> 💡 **术语解释｜密码学（Cryptography）**
> 研究**如何隐秘地传递信息**的学科。核心是：**把明文变成密文（加密），只有持有密钥的人才能还原（解密）**。

**基本术语：**

| 术语 | 英文 | 含义 |
|---|---|---|
| **明文** | Plaintext | 原始可读的消息 |
| **密文** | Ciphertext | 加密后不可读的消息 |
| **加密** | Encryption | 明文 → 密文 |
| **解密** | Decryption | 密文 → 明文 |
| **密钥** | Key | 加解密使用的关键信息 |
| **算法** | Algorithm | 加解密的规则方法 |

### 3.1 什么是对称加密

> 💡 **术语解释｜对称加密（Symmetric Encryption）**
> **加密和解密用同一把密钥**。就像一把钥匙锁门，同一把钥匙开门。
>
> ```
> 发送方：明文 + 密钥 → 加密 → 密文
> 接收方：密文 + 密钥 → 解密 → 明文
> ```

**优缺点：**

| 优点 | 缺点 |
|---|---|
| **速度快**（适合大数据量） | **密钥分发困难**（怎么安全把密钥给对方？） |
| 算法简单、密文紧凑 | 密钥管理复杂（N 人两两通信需 N(N-1)/2 个密钥） |
| 适合加密文件、数据流 | **无法解决身份认证**（无法证明"你就是你"） |

> ⚠️ **对称加密的"死结"**：**密钥怎么安全地送达？** 直接在网络上传，会被中间人截获。这个"密钥分发问题"正是非对称加密要解决的（第 4 章）。

### 3.2 常见对称加密算法

| 算法 | 密钥长度 | 分组大小 | 安全性 | 速度 | 状态 |
|---|---|---|---|---|---|
| **DES** | 56 位 | 64 位 | **低**（已破解） | 快 | ❌ 淘汰 |
| **3DES** | 112/168 位 | 64 位 | 中 | 慢 | ⚠️ 逐步淘汰 |
| **AES-128** | 128 位 | 128 位 | **高** | 很快 | ✅ 主流 |
| **AES-192** | 192 位 | 128 位 | 很高 | 快 | ✅ |
| **AES-256** | 256 位 | 128 位 | **极高** | 较快 | ✅ 推荐 |
| **RC4** | 40~2048 位 | 流加密 | **低**（已淘汰） | 很快 | ❌ |
| **SM4** | 128 位 | 128 位 | 高（**国密**） | 快 | ✅ 国内合规场景 |
| **ChaCha20** | 256 位 | 流加密 | 高 | 很快 | ✅ 移动端首选 |

> 💡 **术语解释｜AES（Advanced Encryption Standard，高级加密标准）**
> **目前最主流的对称加密算法**。分组长度 128 位，密钥长度 128/192/256 位，对应 10/12/14 轮加密。采用 **SPN 结构（替换-置换网络）**。目前**无有效破解方法**，CPU 有硬件加速指令（AES-NI）。
>
> **为什么 DES 被淘汰？** DES 密钥只有 **56 位**，暴力穷举 2⁵⁶ 次在现代算力下几分钟就能破。

### 3.3 分组模式：怎么"切块"加密

对称加密是**按块（分组）加密**的。明文很长时，怎么切块、块与块之间怎么关联，就是**分组模式（Mode of Operation）**。

| 模式 | 全称 | 特点 | 安全性 |
|---|---|---|---|
| **ECB** | Electronic Codebook | 每块**独立**加密 | **低**（相同明文块→相同密文块，能看出模式） |
| **CBC** | Cipher Block Chaining | 每块与前一块**异或**后加密 | 中高（**最常用**） |
| **CFB / OFB** | — | 流密码模式 | 中高 |
| **CTR** | Counter | 计数器流密码，可并行 | 高 |
| **GCM** | Galois/Counter Mode | **认证加密**（加密 + 完整性） | **高（推荐）** |

> ⚠️ **ECB 模式不能用！** 经典例子：用 ECB 加密一张图片，加密后仍能**看出图片轮廓**（因为相同颜色的块加密结果相同）。**生产环境用 CBC 或 GCM。**

```
ECB 的致命问题（"企鹅图"效应）：
   原图            加密后（ECB）
  🐧 轮廓清晰  →   🐧 轮廓依然清晰！（只是颜色变了）
                   ↑ 因为相同明文块产生相同密文块，模式暴露
```

> 💡 **术语解释｜认证加密（AEAD，Authenticated Encryption with Associated Data）**
> **同时提供"加密"和"完整性校验"**的模式，如 **GCM**、**CCM**、**ChaCha20-Poly1305**。**现代首选**——它既保证机密性，又能检测密文是否被篡改。

> 💡 **术语解释｜填充（Padding）**
> 明文长度不是块大小的整数倍时，最后一块要**补齐**。常用 **PKCS#7**（每个填充字节的值 = 填充字节数）。

## 4. 密码学基础（二）：非对称加密与密钥交换

### 4.1 什么是非对称加密

> 💡 **术语解释｜非对称加密（Asymmetric Encryption / 公钥加密）**
> 使用**一对密钥**：**公钥（Public Key）** 可以公开，**私钥（Private Key）** 必须保密。
>
> **两种用法**（极其重要）：
> - **加密**：**公钥加密 → 私钥解密**（保证机密性，谁都能加密，只有你能解）
> - **签名**：**私钥签名 → 公钥验签**（保证身份和完整性，只有你能签，谁都能验）
>
> ```
> 【加密场景】明文 + 接收方公钥 → 加密 → 密文 → 接收方私钥 → 明文
> 【签名场景】消息 + 发送方私钥 → 签名 → 消息+签名 → 发送方公钥 → 验签
> ```

**优缺点：**

| 优点 | 缺点 |
|---|---|
| **解决密钥分发问题**（公钥可公开） | **速度慢**（比对称加密慢几个数量级） |
| 密钥管理简单（每人一对） | 密文膨胀（体积大） |
| **支持数字签名和身份认证** | **不适合大数据量加密** |

> 📌 **一句话**：**对称加密快但送不出密钥，非对称加密能送密钥但慢。所以 HTTPS 用"非对称协商密钥 + 对称加密数据"的混合方案**（阶段五讲过）。

### 4.2 常见非对称加密算法

| 算法 | 密钥长度 | 安全性 | 速度 | 数学基础 |
|---|---|---|---|---|
| **RSA** | 1024/2048/4096 | 2048 位以上安全 | 慢 | **大数分解难题** |
| **ECC** | 160/256/384 | 256 位 ≈ RSA 3072 位 | **较快** | **椭圆曲线离散对数** |
| **DSA** | 1024/2048 | 仅用于签名 | 中 | 离散对数 |
| **ECDSA** | 256/384 | ECC 的签名版本 | 快 | 椭圆曲线 |
| **SM2** | 256 | 国密标准 | 快 | 椭圆曲线（国密） |
| **Ed25519** | 256 | 高（推荐） | 很快 | 扭曲爱德华兹曲线 |

> 💡 **术语解释｜RSA**
> 最经典的非对称算法，基于**大数分解难题**：两个大质数相乘很容易，但把乘积分解回两个质数极难。
>
> ```
> RSA 原理（简化）：
> 1. 选两个大质数 p、q
> 2. n = p × q
> 3. 选公钥 e，算出私钥 d（满足 e×d ≡ 1 mod φ(n)）
> 4. 公钥 = (n, e)，私钥 = (n, d)
> 5. 加密：c = m^e mod n    解密：m = c^d mod n
>
> 安全性：知道 n 和 e，想算出 d 必须先分解 n。当 n 是 2048 位以上，分解极其困难。
> ```

> 💡 **术语解释｜ECC（Elliptic Curve Cryptography，椭圆曲线密码学）**
> 基于**椭圆曲线离散对数难题**。**相同安全强度下，ECC 密钥比 RSA 短得多、运算更快。**
>
> | 安全级别 | RSA 密钥 | ECC 密钥 |
> |---|---|---|
> | 112 位 | 2048 位 | **224 位** |
> | 128 位 | 3072 位 | **256 位** |
> | 256 位 | 15360 位 | **512 位** |
>
> **256 位 ECC ≈ 3072 位 RSA**，所以**移动设备、物联网、区块链广泛用 ECC**。

> ⚠️ **量子计算的威胁**：RSA 和 ECC 都**能被量子计算机的 Shor 算法破解**。所以业界正在研究**后量子密码（PQC）**。目前 RSA-2048/ECC-256 在经典计算机下仍然安全。

### 4.3 密钥交换：Diffie-Hellman

**问题**：双方要协商一个**共享密钥**用于对称加密，但**不能直接在网络上传输**（会被截获）。

> 💡 **术语解释｜Diffie-Hellman（DH）密钥交换**
> 让双方在**不安全的信道上**协商出**共享密钥**，而**不需要直接传输密钥**。基于**离散对数难题**。
>
> ```
> 1. 双方约定大质数 p 和底数 g（公开）
> 2. 甲方生成私钥 a，算出公钥 A = g^a mod p
> 3. 乙方生成私钥 b，算出公钥 B = g^b mod p
> 4. 双方交换公钥 A、B
> 5. 甲方算：s = B^a mod p = g^(ab) mod p
> 6. 乙方算：s = A^b mod p = g^(ab) mod p
> 7. 双方得到相同的 s = 共享密钥
> ```
>
> **安全性**：攻击者知道 g、p、A、B，但要算出 s 需要解**离散对数难题**（计算上不可行）。

> 💡 **术语解释｜ECDHE（Elliptic Curve Diffie-Hellman Ephemeral）**
> **椭圆曲线版本的 DH，且密钥是"临时的（Ephemeral）"**——每次会话生成新的临时密钥对。
>
> **关键价值**：**提供前向保密（PFS）**——即使服务器长期私钥泄露，**历史会话也无法解密**（阶段五讲过）。**现代 TLS 必须用 ECDHE。**

> ⚠️ **DH 的中间人风险**：**裸 DH 无法验证对方身份**——中间人可以分别和双方协商密钥。**所以 DH 必须配合"证书认证"**（确认公钥归属）才能防中间人。

## 5. 密码学基础（三）：哈希与数字签名

### 5.1 哈希算法

> 💡 **术语解释｜哈希算法（Hash / 摘要算法）**
> 把**任意长度的输入**变成**固定长度的输出**（哈希值/摘要）。它是**单向的**——能从明文算出哈希，但**几乎不可能从哈希反推明文**。
>
> ```
> 任意长度输入 → 哈希算法 → 固定长度输出（如 256 位）
> ```

**哈希的五大特性（必背）：**

| 特性 | 含义 |
|---|---|
| **单向性** | 从哈希值**无法反推**原文 |
| **确定性** | 相同输入**永远**产生相同输出 |
| **雪崩效应** | 输入**微小变化**，输出**完全不同** |
| **抗碰撞性** | 很难找到**两个不同输入**产生**相同输出** |
| **固定长度** | 输出长度固定，与输入长度无关 |

**常见哈希算法：**

| 算法 | 输出长度 | 安全性 | 状态 |
|---|---|---|---|
| **MD5** | 128 位 | **低（已碰撞）** | ❌ 不推荐 |
| **SHA-1** | 160 位 | **低（已碰撞）** | ❌ 不推荐 |
| **SHA-256** | 256 位 | **高** | ✅ 推荐 |
| **SHA-512** | 512 位 | 极高 | ✅ |
| **SHA3-256** | 256 位 | 高 | ✅ 新标准 |
| **SM3** | 256 位 | 高（**国密**） | ✅ 国内合规 |
| **RIPEMD-160** | 160 位 | 中 | 比特币用 |

> 💡 **术语解释｜MD5 为什么不安全**
> MD5 已被证明存在**碰撞攻击**：能构造出**两个不同的文件，MD5 值完全相同**。
> - **2004 年**：王小云教授宣布找到 MD5 碰撞方法
> - **2008 年**：可用于伪造 SSL 证书
> - **现在**：用 GPU 几秒就能找到碰撞
>
> **结论**：MD5/SHA-1 **绝不能用于密码存储和数字签名**，最多用于"非安全场景的完整性校验"（也不推荐）。

> 💡 **术语解释｜雪崩效应（Avalanche Effect）**
> 输入的**一个比特变化**，会导致输出的**约一半比特变化**。这保证了"改一个字符，哈希就面目全非"，是完整性校验的基础。
>
> ```
> "hello"  → SHA-256 → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
> "hellp"  → SHA-256 → 完全不同的另一串（仅改1个字母，结果天翻地覆）
> ```

### 5.2 密码存储：为什么不能用 MD5

> ⚠️ **绝对不要用 MD5/SHA 直接存密码！**
>
> 因为这些哈希**太快了**——攻击者用 GPU 每秒能算**几十亿次**，配合**彩虹表**（预计算的哈希字典）能快速破解。

**正确做法：加盐 + 慢哈希**

> 💡 **术语解释｜加盐（Salt）**
> 在密码后面**拼接一段随机字符串**再哈希：`hash = SHA256(password + salt)`。**盐值随机且每个用户不同**，与哈希值一起存储。
>
> **作用**：让**彩虹表失效**（因为同样的密码，盐不同，哈希就不同）。

> 💡 **术语解释｜慢哈希（Password Hashing）**
> 专门为密码存储设计的**故意很慢**的哈希算法：
>
> | 算法 | 说明 | 推荐度 |
> |---|---|---|
> | **bcrypt** | 自适应密码哈希 | ★★★★★ |
> | **scrypt** | 内存难解（抗 GPU/ASIC） | ★★★★ |
> | **Argon2** | 密码哈希竞赛冠军 | ★★★★★ |
> | **PBKDF2** | 基于 MAC 的密钥派生 | ★★★ |
>
> **核心思想**：**让攻击者算一次要花很多时间** → 暴力破解的成本剧增。

```python
# bcrypt 密码哈希示例
import bcrypt

password = "mypassword".encode('utf-8')
hashed = bcrypt.hashpw(password, bcrypt.gensalt(rounds=12))  # rounds 越大越慢越安全

if bcrypt.checkpw(password, hashed):
    print("密码正确")
```

### 5.3 数字签名

> 💡 **术语解释｜数字签名（Digital Signature）**
> **用私钥签名，用公钥验证**。证明消息**确实来自私钥持有者**，且**未被篡改**。

**签名与验签流程：**

```
【发送方】                              【接收方】
1. 计算消息的哈希值                     1. 用发送方公钥解密签名 → 得到哈希值 H1
2. 用自己的私钥加密哈希值 → 数字签名     2. 对收到的消息计算哈希值 → H2
3. 发送：消息 + 签名                    3. 比较 H1 和 H2：
                                          相同 → 验证通过（真实 + 完整）
                                          不同 → 拒绝（被篡改或伪造）
```

**数字签名的三大作用：**

| 作用 | 说明 |
|---|---|
| **身份认证** | 确认消息确实来自声称的发送者 |
| **完整性** | 确认消息**未被篡改** |
| **不可否认性** | 发送者**不能抵赖**发过这条消息（因为只有他有私钥） |

> 📌 **签名 vs 加密（易混，务必分清）**：
>
> | | 加密 | 签名 |
> |---|---|---|
> | 目的 | **保密**（不让别人看） | **认证 + 完整性**（证明是谁、没被改） |
> | 用谁的密钥 | **接收方**公钥加密，接收方私钥解密 | **发送方**私钥签名，发送方公钥验签 |
> | 一句话 | "只有你能看" | "只有你能签" |
>
> **数字证书就是"CA 用私钥对网站公钥做的签名"**（第 6 章）。

> 💡 **术语解释｜HMAC（Hash-based Message Authentication Code）**
> **带密钥的哈希**：`HMAC = Hash(消息 + 密钥)`。用于**验证消息完整性和来源**，需要双方**共享同一个密钥**。
>
> **HMAC vs 数字签名**：HMAC 用**对称密钥**（快，但双方都有密钥，无法"不可否认"）；数字签名用**非对称密钥**（慢，但支持"不可否认"）。

## 6. PKI 与数字证书体系

### 6.1 为什么需要 PKI

**问题**：非对称加密解决了"密钥分发"，但**新问题来了**——**你怎么确认拿到的公钥真的属于对方？** 中间人可以冒充对方，把自己的公钥发给你。

> 💡 **术语解释｜PKI（Public Key Infrastructure，公钥基础设施）**
> 一整套**管理公钥和数字证书**的体系，包括：**CA（证书颁发机构）、证书、注册机构 RA、证书库、CRL/OCSP 等**。目的是**把"公钥"和"真实身份"绑定起来**。

### 6.2 数字证书

> 💡 **术语解释｜数字证书（Digital Certificate）**
> CA 签发的"**公钥身份证**"，把**公钥**和**身份信息**绑定，并由 **CA 用自己的私钥签名**。
>
> ```
> 证书 = 用户/网站信息 + 公钥 + CA 的数字签名
> ```

**证书的核心字段（X.509 标准）：**

| 字段 | 内容 |
|---|---|
| 版本 | X.509 v3 |
| 序列号 | 证书唯一编号 |
| **签名算法** | CA 用哪种算法签名 |
| **签发者（Issuer）** | 哪个 CA 签的 |
| **有效期** | 起止时间 |
| **主体（Subject）** | 证书归属的域名/组织 |
| **公钥** | 网站的公钥 |
| **SAN** | 该证书适用的所有域名列表 |
| **数字签名** | CA 用私钥对以上内容的签名 |

### 6.3 证书链

> 💡 **术语解释｜证书链（Certificate Chain）**
> **根证书 → 中间证书 → 站点证书** 的信任传递链。

```
    根 CA 证书（Root CA）
    · 自签名，内置在操作系统/浏览器中（预装信任名单）
    · 离线保管，极少直接签发
           │ 签发
           ▼
    中间 CA 证书（Intermediate CA）
    · 日常使用，可随时吊销
           │ 签发
           ▼
    站点证书（Leaf / End-Entity）
    · 发给具体网站
```

> 💡 **术语解释｜自签名证书（Self-Signed Certificate）**
> **自己给自己签的证书**（签发者 = 主体）。浏览器**不信任**它，会弹告警。常用于内部测试。

**证书文件格式：**

| 格式 | 扩展名 | 说明 |
|---|---|---|
| DER | .der/.cer | 二进制格式 |
| **PEM** | .pem/.crt/.cer | **Base64 编码，最常用** |
| PKCS#7 | .p7b/.p7c | 证书链格式 |
| **PKCS#12** | .pfx/.p12 | **包含私钥 + 证书**，有密码保护 |

### 6.4 证书验证过程

```
浏览器收到证书后，依次检查：
① 用内置 CA 公钥验签 → 证书是不是伪造的？
② 检查证书域名与访问域名是否匹配（看 SAN）
③ 检查有效期是否在范围内
④ 查询吊销状态（CRL / OCSP）→ 证书有没有被提前作废
⑤ 向上追溯证书链，直到落在系统内置的信任根上

全部通过 → 地址栏亮小锁 🔒
任一失败 → 证书告警
```

> 💡 **术语解释｜CRL 与 OCSP**
> - **CRL（Certificate Revocation List，证书吊销列表）**：CA 发布的"已作废证书名单"（定期更新，有延迟）
> - **OCSP（Online Certificate Status Protocol，在线证书状态协议）**：**实时查询**某证书是否有效（更及时，但每次查询有开销）

> ⚠️ **常见证书告警的处理顺序**：
> 1. **先看域名匹配**（可能"连错了机器"）
> 2. **再看签发者**（可能"信任链断了"或自签名）
> 3. **最后看有效期**（可能证书过期或客户端时间错乱）

## 7. 传输层安全：TLS 深入回顾

阶段五已详讲 TLS，这里从"安全视角"再提炼关键点。

### 7.1 TLS 解决的三大问题

| 问题 | TLS 的解法 |
|---|---|
| **机密性**（防窃听） | 对称加密（AES/GCM）加密数据 |
| **完整性**（防篡改） | MAC / AEAD 校验 |
| **身份认证**（防冒充） | 数字证书 + CA |

> 💡 **术语解释｜TLS（Transport Layer Security，传输层安全）**
> HTTPS 背后的加密协议。前身是 **SSL**（已全部废弃，务必用 **TLS 1.2+**）。**HTTPS = HTTP + TLS**。

### 7.2 混合加密的"三步走"

```
① 非对称加密（握手阶段）：安全协商出一把临时的"会话密钥"
        ↓
② 对称加密（传输阶段）：用会话密钥高效加密所有实际数据
        ↓
③ 证书认证（贯穿全程）：确认服务器身份，防中间人
```

> 📌 **一句话**：**"用慢的握手，换来快的全程加密，再用证书锁住身份。"**

### 7.3 TLS 1.3 的安全改进

| 特性 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| 握手往返 | 2-RTT | **1-RTT**（会话恢复可 0-RTT） |
| 前向保密 | 可选 | **强制默认** |
| 不安全算法 | 还保留（RC4/CBC/纯 RSA 交换） | **全部删除** |
| 密钥交换 | RSA / DH / ECDHE | **仅 ECDHE / DHE** |
| 加密范围 | 部分握手明文 | **大部分握手消息加密** |

> ⚠️ **TLS 1.3 的取舍**：删掉了旧算法，**更安全**，但**老旧客户端可能握手失败**。建议**优先 TLS 1.3 + 保留 TLS 1.2 兜底**。

### 7.4 用 openssl 检查网站 TLS 配置

```bash
# 查看网站的 TLS 握手、证书链、使用的加密套件
openssl s_client -connect www.example.com:443 -showcerts

# 只看证书信息
echo | openssl s_client -connect www.example.com:443 2>/dev/null | openssl x509 -noout -text

# 检查证书有效期
echo | openssl s_client -connect www.example.com:443 2>/dev/null | openssl x509 -noout -dates

# 测试是否支持 TLS 1.3
openssl s_client -connect www.example.com:443 -tls1_3
```

> 📌 **在线 TLS 检测神器**：https://www.ssllabs.com/ssltest/ —— 输入域名，给出 A~F 评级，并列出支持的协议版本、套件、证书链。

## 8. 网络层安全：IPSec 与 VPN

> 💡 **术语解释｜VPN（Virtual Private Network，虚拟专用网络）**
> 在**公共网络**上建立**加密隧道**，让数据像在**专用网络**里传输一样安全。用途：**远程接入、分支机构互联、跨地域组网**。

**VPN 的两大类型：**

| 类型 | 说明 | 场景 |
|---|---|---|
| **站点到站点（Site-to-Site）** | 两个**网络**之间建隧道 | 总部 ↔ 分公司 |
| **远程接入（Remote Access）** | **单个用户**接入企业内网 | 员工在家连公司 |

### 8.1 IPSec：网络层的安全协议族

> 💡 **术语解释｜IPSec（Internet Protocol Security，IP 安全协议）**
> **网络层（L3）**的安全协议族，为 **IP 数据包**提供**加密、认证、完整性**保护。是**站点到站点 VPN 的主流技术**。

**IPSec 的两大核心协议：**

| 协议 | 全称 | 提供什么 | 是否加密 |
|---|---|---|---|
| **AH** | Authentication Header | 认证 + 完整性 | ❌ **不加密** |
| **ESP** | Encapsulating Security Payload | 加密 + 认证 + 完整性 | ✅ **加密** |

> 📌 **实际部署几乎都用 ESP**（因为要加密）。AH 只做认证不加密，用得少。

**IPSec 的两种模式：**

| 模式 | 保护范围 | 场景 |
|---|---|---|
| **传输模式（Transport）** | 只保护**数据载荷**（保留原 IP 头） | 主机到主机 |
| **隧道模式（Tunnel）** | 保护**整个原始 IP 包**（含原 IP 头），再封装新 IP 头 | **站点到站点 VPN** |

```
【传输模式】
  原包：[IP头][TCP/UDP][数据]  →  [IP头][ESP头][加密数据][ESP尾]
                                    ↑ 原 IP 头保留（暴露源/目的 IP）

【隧道模式】
  原包：[IP头][TCP/UDP][数据]  →  [新IP头][ESP头][整个原包加密][ESP尾]
                                    ↑ 新 IP 头（隧道端点），原 IP 头被加密隐藏
```

> 💡 **术语解释｜IKE（Internet Key Exchange，互联网密钥交换）**
> IPSec 用来**协商密钥和安全参数**的协议。**IKE 分两个阶段**：
> - **阶段一**：建立 IKE SA（管理通道），双方认证身份、协商保护参数
> - **阶段二**：在管理通道内协商 IPSec SA（数据通道），确定加密/认证算法

> 💡 **术语解释｜SA（Security Association，安全联盟）**
> IPSec 双方协商出的**一组安全参数**（加密算法、密钥、有效期等）。**"感兴趣流（Interesting Traffic）"** 指需要被 IPSec 保护的流量（由 ACL 定义）。

> ⚠️ **IPSec 隧道两端必须配置一致**（加密算法、认证方式、预共享密钥等），否则协商失败。

### 8.2 其他 VPN 技术

| 技术 | 层次 | 说明 |
|---|---|---|
| **IPSec VPN** | L3 | 站点到站点主流，网络层加密 |
| **SSL VPN** | L4-L7 | 基于 TLS，**浏览器即可接入**，远程接入常用 |
| **L2TP/IPSec** | L2 | 二层隧道 + IPSec 加密，老式远程接入 |
| **PPTP** | L2 | **已不安全**（有已知漏洞），**禁用** |
| **WireGuard** | L3 | 现代轻量 VPN，性能高、配置简单 |
| **MPLS VPN** | L2.5 | 运营商提供的专网（阶段六讲过） |

> 📌 **SSL VPN vs IPSec VPN**：
> - **IPSec VPN**：适合**站点到站点**（网关之间），配置复杂，需要专用客户端
> - **SSL VPN**：适合**远程接入**（用户用浏览器就行），**无需安装客户端**，更灵活

## 9. 边界防护：防火墙、IDS/IPS、WAF、DMZ

阶段六讲了设备本身，这里从"安全防护"角度深入。

### 9.1 防火墙（Firewall）

**四代演进（复习 + 深化）：**

| 代际 | 类型 | 检查什么 | 优点 | 缺点 |
|---|---|---|---|---|
| 第一代 | **包过滤** | IP、端口、协议 | 快、简单 | 只看"信封"，无法识别应用，易被绕过 |
| 第二代 | **状态检测** | 连接状态表（会话） | 记住"谁先发起"，更安全 | 无法识别应用层内容 |
| 第三代 | **应用层代理** | 应用层数据 | 深入内容 | **慢**（要代理重建连接） |
| 第四代 | **NGFW（下一代）** | 应用 + 用户 + 内容 + 威胁 | 深度识别、集成 IPS | 复杂、成本高 |

> 💡 **术语解释｜状态检测（Stateful Inspection）**
> 防火墙维护**连接状态表**，记录每条连接的**协议、源/目的 IP、端口、状态**。
>
> **核心能力**：**只放行"内部主动发起的连接的回包"**。
> - 你在内网访问网页 → 返回包能过（属于已建立连接）
> - 外网主动连接你 → 被拦（不在状态表里）
>
> **比"只看包内容"的包过滤安全得多。**

> 💡 **术语解释｜NGFW（Next-Generation Firewall，下一代防火墙）**
> 在传统防火墙基础上**深度集成**：**应用识别与控制、IPS、用户身份管理、加密流量检查、威胁情报**。
>
> **本质**：从"看门牌"升级到"**看人 + 看行李 + 看行为**"。能识别"这是微信还是迅雷"，而不只是看端口。

**防火墙的部署模式：**

| 模式 | 说明 |
|---|---|
| **路由模式（网关模式）** | 作为网关串在网络出口，**最常见** |
| **透明模式（网桥模式）** | 像"透明网线"，不改 IP，旁路部署方便 |
| **旁路模式** | 只监听不阻断（IDS 常见） |

### 9.2 DMZ：缓冲区设计

> 💡 **术语解释｜DMZ（Demilitarized Zone，隔离区/非军事区）**
> 位于**内网与外网之间**的一个**缓冲区**，用来放置**对外提供服务但安全性较低的服务器**（Web、邮件、FTP 等）。
>
> **核心思想**：**把"对外暴露的服务器"和"核心内网"隔开**。即使 DMZ 的服务器被攻破，**攻击者也进不了核心内网**。

```
              ┌──────────────┐
   互联网 ──▶ │  外网防火墙   │
              └──────┬───────┘
                     │
              ┌──────▼───────┐
              │     DMZ       │  ← 放 Web/邮件/FTP 等对外服务器
              └──────┬───────┘
                     │
              ┌──────▼───────┐
              │  内网防火墙   │  ← 严格限制 DMZ → 内网的访问
              └──────┬───────┘
                     │
              ┌──────▼───────┐
              │   核心内网     │  ← 数据库、核心业务系统
              └──────────────┘
```

**DMZ 的三道防线（三明治结构）：**

| 防线 | 作用 |
|---|---|
| **外网防火墙** | 过滤外部入站流量（只放行 80/443 等必要端口） |
| **内网防火墙** | **严格控制 DMZ → 内网的访问**（即使 DMZ 被攻破，也进不了内网） |
| **DMZ 内部** | 服务器本身加固、最小化服务 |

> 📌 **DMZ 的价值**：**限制攻击面 + 多层防御**。对外只暴露**必要的端口和服务**，把风险"圈"在 DMZ 里。

### 9.3 IDS / IPS：入侵检测与防御

| 对比 | IDS（入侵检测系统） | IPS（入侵防御系统） |
|---|---|---|
| 部署方式 | **旁路**（只镜像流量） | **串联**（流量经过它） |
| 行为 | **只检测、告警** | **检测并阻断** |
| 对性能影响 | 无（不阻断） | 有（要实时处理） |
| 风险 | 无法阻止攻击 | 误报会误杀正常流量 |
| 定位 | 监控、取证 | 实时防护 |

> 💡 **术语解释｜IDS / IPS 的检测方式**
> - **特征检测（Signature-based）**：匹配已知攻击特征 → 准，但**无法发现新攻击（0-day）**
> - **异常检测（Anomaly-based）**：对比"正常行为基线"，发现异常 → 能发现新攻击，但**误报多**
>
> **现代多用"特征 + 异常"结合。**

### 9.4 WAF：Web 应用防火墙

> 💡 **术语解释｜WAF（Web Application Firewall，Web 应用防火墙）**
> 专门防护 **Web 应用层攻击**的防火墙，防 **SQL 注入、XSS、CSRF、文件上传漏洞、CC 攻击**等。
>
> **和传统防火墙的区别**：传统防火墙管"**能不能连**"（端口/IP），WAF 管"**连上之后的请求正不正常**"（应用层内容）。

**WAF 的部署方式：**

| 方式 | 说明 |
|---|---|
| **反向代理模式** | WAF 作为代理，流量经过它（最常见） |
| **透明模式** | 串接但不改 IP |
| **旁路模式** | 只检测不阻断（配合其他设备联动阻断） |

> 📌 **一句话区分**：
> - **防火墙**：管"**能不能进**"（网络层/传输层）
> - **WAF**：管"**进来的 Web 请求正不正常**"（应用层）
> - **IPS**：管"**流量里有没有攻击特征**"（全流量）

### 9.5 其他安全设备

| 设备 | 作用 |
|---|---|
| **堡垒机（跳板机）** | 运维操作的**统一入口 + 审计录屏**，所有运维经它跳转 |
| **网闸（GAP）** | **物理隔离**不同安全域（如内网与外网物理断开，只允许特定数据摆渡） |
| **上网行为管理** | 流量审计、应用管控、行为记录 |
| **终端 EDR** | 终端检测与响应，监控终端异常行为 |
| **蜜罐（Honeypot）** | **诱饵系统**，吸引攻击者，记录其手法，不涉及真实数据 |

## 10. 身份与访问控制：AAA、802.1X、零信任

### 10.1 AAA：认证、授权、计费

> 💡 **术语解释｜AAA（Authentication, Authorization, Accounting）**
> 访问控制的三大功能：
> - **认证（Authentication）**：**你是谁？**（验证身份）
> - **授权（Authorization）**：**你能干什么？**（分配权限）
> - **计费/审计（Accounting）**：**你干了什么？**（记录行为）

```
   用户 ──▶ [认证：你是谁] ──▶ [授权：能做什么] ──▶ [审计：做了什么]
              │                    │                     │
          账号密码/证书        权限策略              日志记录
          指纹/短信            角色分配              流量统计
```

### 10.2 RADIUS 与 802.1X

> 💡 **术语解释｜RADIUS（Remote Authentication Dial-In User Service）**
> **AAA 服务的事实标准协议**（UDP 1812 认证 / 1813 计费）。企业无线、VPN、交换机登录认证常用它。

> 💡 **术语解释｜802.1X（基于端口的网络访问控制）**
> **接入认证标准**。设备**接入网络前必须先认证**，认证通过才放行流量。
>
> **三个角色**：
> - **客户端（Supplicant）**：要接入的设备
> - **认证者（Authenticator）**：交换机/AP（转发认证报文）
> - **认证服务器（Authentication Server）**：通常是 **RADIUS 服务器**（做实际认证）

```
   客户端          交换机/AP          RADIUS 服务器
  (Supplicant)  (Authenticator)   (Auth Server)
      │               │                  │
      │  ① 请求接入    │                  │
      │ ─────────────▶ │                  │
      │               │  ② 转发认证请求   │
      │               │ ────────────────▶ │
      │               │  ③ 认证结果       │
      │               │ ◀──────────────── │
      │  ④ 放行/拒绝   │                  │
      │ ◀──────────── │                  │
```

> 📌 **企业 WiFi 的"WPA2-Enterprise"就是 802.1X**——用**账号密码认证**（而非共享一个 WiFi 密码），每个人有独立凭证，可单独吊销。

### 10.3 零信任（Zero Trust）

> 💡 **术语解释｜零信任（Zero Trust）**
> **"永不信任，始终验证"（Never Trust, Always Verify）** 的安全架构思想。**默认不信任网络内外的任何主体**，每次访问都要**验证身份、设备、权限、行为**。
>
> **核心认知**：**"内网 = 安全区"是最大的错觉。** 传统边界安全假设"进了内网就安全"，但**一旦边界被突破，攻击者就能在内网横向移动、畅通无阻**。

**为什么传统"边界信任"过时了？**

| 问题 | 说明 |
|---|---|
| **内网不等于安全** | 一次沦陷（钓鱼/漏洞），攻击者在内网任意横向移动 |
| **边界一破全暴露** | 防火墙后面的设备全"裸奔" |
| **身份冒充成本低** | 拿到一个账号密码，就能在"信任区"畅通 |

**零信任的 NIST 三大原则：**

```
① 所有数据源和计算服务都视为"资源"，必须保护
② 无论网络位置（内网/外网），所有通信都要安全
③ 每次访问都要授权——按"会话"授权，不是按"IP"授权
```

> **一句话**：**"不信任位置，只信任验证。"**

**零信任的三大组件：**

| 组件 | 作用 |
|---|---|
| **IAM（身份与访问管理）** | 强认证（MFA）、最小权限——**管身份** |
| **微隔离（Micro-segmentation）** | 把网络切成小块逐块隔离——**管横向移动** |
| **SDP（软件定义边界）** | **隐藏服务**（不暴露 IP，验证后才可见）——**管隐身** |

> 💡 **术语解释｜微隔离（Micro-segmentation）**
> 把数据中心/内网**细分成许多小的安全区域**，区域之间**默认不互通**，只放行必要的流量。这样即使攻击者攻破一台机器，也**很难横向移动到其他区域**。

> 💡 **术语解释｜SDP（Software Defined Perimeter，软件定义边界）**
> **"先认证，后连接"**——服务**默认对所有人隐藏**（不响应未认证的连接），只有通过认证的设备才能"看到"并访问服务。**"看不见 = 打不到"。**

**零信任 vs 传统边界安全：**

| 对比 | 传统边界安全 | 零信任 |
|---|---|---|
| 信任假设 | 内网可信，外网不可信 | **内外都不信** |
| 认证时机 | 一次认证（进网就信） | **持续验证**（每次访问都验） |
| 权限 | 粗粒度（进内网权限大） | **最小权限**（按需授权） |
| 网络位置 | 决定信任等级 | **不影响**（位置无关） |
| 代表技术 | VPN、防火墙 | IAM、微隔离、SDP、MFA |

> ⚠️ **零信任常见误区**：
> - ❌ "零信任 = 某个产品" → ✅ 它是**理念 + 体系**，靠多种技术组合落地
> - ❌ "上了 VPN 就是零信任" → ✅ VPN 仍是**边界思路**（进隧道就信任）
> - ❌ "零信任能防住所有攻击" → ✅ 它是**降低风险**，不是绝对安全

> 📌 **零信任落地三步走**：**评估（摸清资产和权限）→ 试点（核心应用先上 MFA + 访问控制）→ 扩展（逐步铺开微隔离、行为分析）**。

## 11. 常见攻击与防御（上）：网络层攻击

> ⚠️ **再次声明**：以下内容**仅用于理解防御**，禁止用于任何未授权的攻击行为。

### 11.1 DoS / DDoS 攻击

> 💡 **术语解释｜DoS（Denial of Service，拒绝服务攻击）**
> 通过**大量恶意流量或请求**，耗尽目标系统的**带宽、CPU、内存**等资源，使其**无法响应正常用户**。
>
> - **DoS**：单点发起，规模有限，易被拦截
> - **DDoS（Distributed DoS）**：利用大量**"僵尸机（肉鸡）"分布式发起**，规模可达数百 Gbps

**DDoS 的三大类型：**

| 类型 | 层次 | 手段 | 特点 |
|---|---|---|---|
| **体积型** | L3/L4 | UDP Flood、ICMP Flood | 以 **Gbps/Tbps** 计，拼带宽 |
| **协议型** | L4 | **SYN Flood**（耗尽半连接队列） | 利用协议缺陷 |
| **应用层** | L7 | **CC 攻击**（模拟正常 HTTP 请求） | **更难识别**（看起来像真实用户） |

> 💡 **术语解释｜SYN Flood（SYN 洪泛）**
> 攻击者发送**大量伪造源 IP 的 SYN 包**，服务器回复 SYN+ACK 后**等不到最终 ACK**，**半连接队列被占满**，正常用户无法建立连接。（阶段四讲过，配合 **SYN Cookie** 防御）

> 💡 **术语解释｜僵尸网络（Botnet）**
> 大量被恶意软件控制的设备（电脑、摄像头、路由器、IoT）组成的网络，攻击者**远程操控它们同时发起攻击**。

**防御手段：**

| 手段 | 说明 |
|---|---|
| **流量清洗** | 部署抗 DDoS 设备（流量清洗中心），识别并过滤恶意流量 |
| **CDN 分散** | 用 CDN 分散流量，隐藏源站 IP |
| **负载均衡 + 集群** | 把流量分散到多台服务器 |
| **弹性扩容** | 云环境自动扩容应对突发流量 |
| **限速与阈值** | WAF/防火墙限制单 IP 请求频率 |
| **SYN Cookie / SYN Proxy** | 应对 SYN Flood |

### 11.2 中间人攻击（MITM）

> 💡 **术语解释｜中间人攻击（MITM，Man-In-The-Middle）**
> 攻击者在通信双方**之间插入"中间节点"**，**拦截、篡改、窃取**通信数据，而双方**误以为在直接通信**。

**攻击流程：**

```
   客户端                    攻击者                    真实服务器
     │                        │                          │
     │ 我要连 example.com      │                          │
     │ ─────────────────────▶ │                          │
     │                        │  伪装成客户端连服务器      │
     │                        │ ────────────────────────▶ │
     │                        │ ◀──────────────────────── │
     │ ◀────────────────────── │  伪装成服务器返回
     │                        │
   双方的数据（账号密码）全被攻击者看到/篡改
```

**常见场景**：**公共 WiFi、未加密的 HTTP 连接、ARP 欺骗、DNS 劫持**。

**防御手段：**

| 手段 | 说明 |
|---|---|
| **强制 HTTPS** | TLS 加密 + 证书验证服务器身份 |
| **HSTS** | 强制浏览器只用 HTTPS，防"降级攻击" |
| **证书验证** | 严格校验证书（过期、CA、域名） |
| **VPN / 端到端加密** | 敏感通信走加密隧道 |

> ⚠️ **HSTS（HTTP Strict Transport Security）**：服务器通过响应头告诉浏览器"**以后只用 HTTPS 访问我**"，浏览器会记住并在下次直接强制 HTTPS，**防止攻击者把你降级到 HTTP**。

### 11.3 ARP 欺骗

> 💡 **术语解释｜ARP 欺骗（ARP Spoofing）**
> 在局域网中，攻击者发送**伪造的 ARP 报文**，篡改目标设备的 **ARP 缓存**（IP ↔ MAC 映射），使流量**被转发到攻击者设备**，实现**监听或断网**。
>
> **典型手法**：攻击者告诉主机"**网关的 IP 对应的 MAC 是我的 MAC**"，主机的流量就发给了攻击者，攻击者再转发给真网关（**中间人**）。

```
正常情况：              ARP 欺骗后：
 主机 ──▶ 网关           主机 ──▶ 攻击者 ──▶ 网关
（直接通信）            （攻击者偷看/篡改全部流量）
```

**防御手段：**

| 手段 | 说明 |
|---|---|
| **静态 ARP 绑定** | 手动绑定 IP-MAC（`arp -s`），但维护麻烦 |
| **DHCP Snooping** | 建立"IP-MAC-端口"绑定表（阶段五讲过） |
| **DAI（动态 ARP 检测）** | 交换机检查 ARP 报文是否与绑定表一致，不一致就丢弃 |
| **ARP 防火墙** | 终端软件监控异常 ARP 报文 |
| **VLAN 隔离** | 缩小 ARP 传播范围 |

> 💡 **术语解释｜DAI（Dynamic ARP Inspection，动态 ARP 检测）**
> 交换机上的安全功能，**基于 DHCP Snooping 的绑定表**，检查每个 ARP 报文的"IP-MAC"是否匹配。**不匹配就丢弃**，从而防 ARP 欺骗。

### 11.4 DNS 劫持 / 缓存投毒

| 攻击 | 原理 | 防御 |
|---|---|---|
| **DNS 劫持** | 篡改解析结果，把你导向钓鱼站 | DNSSEC、可信 DNS |
| **DNS 缓存投毒** | 污染 DNS 缓存，误导大量用户 | DNSSEC、随机化查询 ID/端口 |
| **DNS 欺骗** | 伪造 DNS 响应 | DNSSEC |

> 💡 **术语解释｜DNSSEC**
> 给 DNS 记录**加数字签名**，让客户端能验证解析结果**未被篡改**。**注意：DNSSEC 只保证"不被篡改"，不加密（不防监听）**。要防监听用 **DoH/DoT**（阶段五讲过）。

### 11.5 端口扫描

> 💡 **术语解释｜端口扫描（Port Scanning）**
> 攻击者**探测目标主机开放了哪些端口**，从而推断运行了哪些服务、有哪些潜在漏洞。是**渗透的第一步（信息收集）**。
>
> **常用工具**：**Nmap**（最著名）。

**常见的端口状态：**

| 状态 | 含义 |
|---|---|
| **open** | 端口开放，有服务在监听 |
| **closed** | 端口关闭，但主机可达（会回 RST） |
| **filtered** | 被防火墙过滤，无响应 |

**防御手段：**

| 手段 | 说明 |
|---|---|
| **最小暴露** | 关闭不必要的端口和服务 |
| **防火墙** | 只放行必需端口 |
| **端口敲门（Port Knocking）** | 按特定顺序"敲"端口才开放服务 |
| **入侵检测** | 检测异常扫描行为并告警 |
| **蜜罐** | 诱骗扫描者 |

> 📌 **端口扫描的"另一面"**：**在授权范围内扫描自己的资产**是**安全自查**的重要手段。**关键是"授权"**——未经授权扫描他人系统**违法**。

## 12. 常见攻击与防御（中）：应用层攻击

### 12.1 SQL 注入（SQL Injection）

> 💡 **术语解释｜SQL 注入（SQL Injection）**
> 攻击者在**用户输入**中插入**恶意 SQL 语句**，欺骗服务器**执行非预期的数据库操作**，从而**窃取、篡改、删除数据**，甚至**绕过登录**。

**经典例子：**

```sql
-- 正常登录查询
SELECT * FROM users WHERE username='tom' AND password='123456';

-- 攻击者在用户名输入：' OR '1'='1'--
SELECT * FROM users WHERE username='' OR '1'='1'--' AND password='...';
--                              ↑ 条件恒为真 → 绕过密码验证直接登录！
```

**危害**：拖库（窃取全部数据）、篡改数据、删除表、提权。

**防御手段（重点）：**

| 手段 | 说明 |
|---|---|
| **参数化查询（PreparedStatement）** | **核心防御**！把用户输入当**数据**而非**代码**解析 |
| **输入验证（白名单）** | 严格校验输入格式，只允许合规字符 |
| **最小权限** | 数据库账号只给必要权限（不给 DROP/DELETE） |
| **WAF** | 拦截 SQL 注入特征 |
| **错误信息隐藏** | 不把数据库报错返回给用户 |

```python
# ❌ 危险：字符串拼接（可被注入）
sql = "SELECT * FROM users WHERE name='" + name + "'"

# ✅ 安全：参数化查询（输入被当作数据）
cursor.execute("SELECT * FROM users WHERE name = ?", (name,))
```

> 📌 **记住**：**参数化查询是防 SQL 注入的"银弹"**。只要用了参数化，用户输入就**永远不会被当作 SQL 代码执行**。

### 12.2 XSS（跨站脚本攻击）

> 💡 **术语解释｜XSS（Cross-Site Scripting，跨站脚本攻击）**
> 攻击者向网页中**注入恶意 JavaScript 代码**，当其他用户访问该页面时，代码在**用户浏览器中执行**，从而**窃取 Cookie/会话、篡改页面、诱导操作**。

**三种类型：**

| 类型 | 原理 | 例子 |
|---|---|---|
| **存储型** | 恶意代码**存在服务器**（如评论、数据库），所有访问者都中招 | 论坛评论注入 `<script>...</script>` |
| **反射型** | 恶意代码通过 **URL 参数**传递，服务器"反射"到页面 | `?query=<script>...</script>`，诱导点击 |
| **DOM 型** | 不经过服务器，**客户端 JS 直接操作 DOM** 执行 | `document.write(location.hash)` |

> ⚠️ **XSS 的核心危害是"以用户身份执行代码"**——最常用来**窃取 Cookie（会话劫持）**，进而**冒充用户登录**。

**防御手段：**

| 手段 | 说明 |
|---|---|
| **输出编码（转义）** | 把 `<` `>` `&` 等转义为 HTML 实体，让脚本无法执行 |
| **输入过滤** | 过滤危险标签（`<script>`、`onclick` 等） |
| **CSP（内容安全策略）** | 通过响应头限制脚本来源（只允许同源脚本） |
| **HttpOnly Cookie** | 禁止 JS 读取 Cookie，防 XSS 窃取会话 |

> 💡 **术语解释｜CSP（Content Security Policy，内容安全策略）**
> HTTP 响应头，**限制页面能加载/执行哪些来源的脚本**。
> ```
> Content-Security-Policy: default-src 'self'; script-src 'self'
> ```
> 只允许加载**本站**的脚本，**注入的外部脚本会被浏览器拒绝执行**。

### 12.3 CSRF（跨站请求伪造）

> 💡 **术语解释｜CSRF（Cross-Site Request Forgery，跨站请求伪造）**
> 攻击者**诱导已登录的用户**，在**不知情的情况下**向目标网站发送**恶意请求**（如转账、改密码），**利用用户的身份权限**执行操作。
>
> **关键**：依赖浏览器**自动携带 Cookie** 的特性。

**攻击示例：**

```html
<!-- 攻击者页面 evil.com 上的隐藏表单 -->
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
</form>
<script>document.forms[0].submit();</script>
<!-- 用户一访问 evil.com，浏览器自动携带 bank.com 的 Cookie 提交 → 钱转走了 -->
```

> 📌 **XSS vs CSRF 的区别（高频考点）**：
> - **XSS**：**在目标网站注入代码**，窃取用户信息（**信任了用户输入**）
> - **CSRF**：**借用用户的身份**发请求（**信任了用户浏览器**）
> - **一句话**：XSS 是"**偷你的身份**"，CSRF 是"**用你的身份干坏事**"

**防御手段：**

| 手段 | 说明 |
|---|---|
| **CSRF Token** | 服务器下发随机 Token，提交时必须携带并验证（**核心防御**） |
| **SameSite Cookie** | `SameSite=Strict/Lax`，限制第三方网站携带 Cookie |
| **验证 Referer / Origin** | 检查请求来源是否为可信域名 |
| **关键操作二次验证** | 转账/改密码要求输入密码或验证码 |

### 12.4 文件上传 / 命令注入 / 越权

| 攻击 | 原理 | 防御 |
|---|---|---|
| **文件上传漏洞** | 上传恶意文件（如 WebShell）获取服务器控制权 | 白名单校验文件类型、重命名、隔离存储、禁止执行 |
| **命令注入** | 在调用系统命令的输入点插入命令（如 `8.8.8.8; rm -rf /`） | 避免拼接命令、严格过滤特殊字符、最小权限 |
| **越权访问** | 访问本无权限的资源（如改 URL 里的 ID 看别人订单） | 服务端严格校验权限（**不能只靠前端隐藏**） |
| **SSRF** | 让服务器发请求到内网（利用服务器当跳板） | 校验目标地址、限制可访问范围 |
| **XXE** | 利用 XML 外部实体读取文件/发起请求 | 禁用外部实体 |

> ⚠️ **越权是最常见也最容易被忽视的漏洞**：**权限校验必须放在服务端**。前端隐藏按钮**不是安全措施**——攻击者直接构造请求就能绕过。

### 12.5 密码攻击

| 攻击 | 原理 |
|---|---|
| **暴力破解** | 尝试所有字符组合（效率低，适合短密码） |
| **字典攻击** | 用预先准备的密码字典批量尝试（`123456`、`password`） |
| **彩虹表攻击** | 用预计算的哈希值比对（针对**未加盐**的哈希） |
| **撞库** | 用泄露的账号密码去撞其他网站（**用户复用密码**） |

**防御手段：**

| 手段 | 说明 |
|---|---|
| **强密码策略** | 长度 ≥8 位，含大小写、数字、特殊字符 |
| **哈希加盐** | 存储 `SHA256(password + salt)` 或更好用 **bcrypt** |
| **账户锁定 + 验证码** | 多次输错锁定账户，阻止自动化 |
| **双因素认证（2FA/MFA）** | 除密码外加第二重验证（短信/验证器/硬件 Key） |
| **检测撞库** | 异常登录行为告警 |

> 💡 **术语解释｜双因素认证（2FA / MFA）**
> **多因素认证（MFA）**要求提供**两类以上**的凭证：
> - **你知道的**（密码）
> - **你拥有的**（手机、硬件 Key）
> - **你是什么**（指纹、人脸）
>
> **即使密码泄露，攻击者仍无法登录**（因为缺第二因素）。**这是防账号被盗最有效的手段之一。**

## 13. 常见攻击与防御（下）：身份与社工攻击

### 13.1 钓鱼攻击（Phishing）

> 💡 **术语解释｜钓鱼攻击（Phishing）**
> 通过**仿冒合法网站、邮件、短信**，**诱骗用户输入账号密码或下载恶意文件**。是**最有效、最防不胜防**的攻击方式之一——因为它攻击的是"**人**"，而不是"技术"。

**常见形式：**

| 形式 | 说明 |
|---|---|
| **邮件钓鱼** | 伪装成银行/公司发邮件，诱导点击链接或下载附件 |
| **仿冒网站** | 域名与正规网站高度相似（差 1 个字母） |
| **短信钓鱼（Smishing）** | 伪装成快递、银行发短信诱导点击 |
| **鱼叉式钓鱼（Spear Phishing）** | **针对性**钓鱼，针对特定人定制（如冒充老板） |
| **鲸钓（Whaling）** | 针对高管的大鱼 |
| **电话诈骗（Vishing）** | 冒充公检法/上级诱骗转账 |

**防御手段：**

| 手段 | 说明 |
|---|---|
| **安全意识培训** | **最重要**！教会员工识别钓鱼 |
| **邮件安全网关** | 过滤垃圾/钓鱼邮件 |
| **SPF/DKIM/DMARC** | 验证邮件来源（阶段五讲过） |
| **MFA** | 即使密码被钓走，也难登录 |
| **URL 检查** | 悬停看真实链接，核对域名 |

> ⚠️ **钓鱼是"社工攻击"的典型**——**技术防护再强，也挡不住一个点错链接的人**。所以**安全意识培训是安全体系里性价比最高的一环**。

### 13.2 社会工程学（Social Engineering）

> 💡 **术语解释｜社会工程学（Social Engineering）**
> 利用**人的心理弱点**（信任、好奇、恐惧、贪婪、权威服从）来**获取信息或权限**的攻击。**"攻心为上"。**

**常见手法：**

| 手法 | 说明 |
|---|---|
| **假冒身份** | 冒充 IT 支持、领导、同事 |
| **尾随（Tailgating）** | 跟着有权限的人进机房/办公区 |
| **电话套话** | 打电话套取密码、内网信息 |
| **免费诱饵** | U 盘、二维码、免费 WiFi 做诱饵 |
| **恐吓/紧迫感** | "你的账户即将被冻结，立即点击" |

**防御**：**安全意识培训 + 流程规范（如电话核实身份）+ 最小权限**。

### 13.3 恶意软件（Malware）

| 类型 | 说明 |
|---|---|
| **病毒（Virus）** | 依附其他文件，复制传播 |
| **蠕虫（Worm）** | **无需宿主**，自主网络传播（如 WannaCry 利用永恒之蓝漏洞） |
| **木马（Trojan）** | 伪装成正常软件，窃取信息/远程控制 |
| **勒索软件（Ransomware）** | **加密用户文件，索要赎金** |
| **间谍软件（Spyware）** | 窃取信息、监控行为 |
| **挖矿木马** | 偷偷用你的算力挖矿 |
| **僵尸网络客户端** | 让你的机器成为"肉鸡" |

**防御手段：**

| 手段 | 说明 |
|---|---|
| **杀毒软件 / EDR** | 实时监控清除 |
| **及时打补丁** | 修复漏洞（WannaCry 依赖未修复的 SMB 漏洞） |
| **不点不明附件/链接** | 安全意识 |
| **定期备份** | **被勒索后能恢复，不用付赎金**（离线备份 + 云备份） |
| **最小权限** | 降低被感染后的影响 |

> 📌 **应对勒索软件的铁律**：**备份！备份！备份！** 而且是**离线备份**（避免备份也被加密）。**有备份就不用交赎金。**

## 14. 安全运维：日志、漏洞管理与应急响应

安全不只是"部署设备"，更是**持续运营**。

### 14.1 日志与审计

> 💡 **术语解释｜日志审计（Log Auditing）**
> 收集、分析系统和设备的**日志**，用于**发现异常、追溯事件、合规审计**。

**关键日志来源：**

| 来源 | 记录什么 |
|---|---|
| **系统日志** | 登录、进程、错误 |
| **应用日志** | 请求、异常、业务操作 |
| **网络设备日志** | 流量、连接、ACL 命中 |
| **安全设备日志** | 防火墙、IDS/IPS、WAF 告警 |
| **审计日志** | 关键操作（谁、何时、做了什么） |

> 💡 **术语解释｜SIEM（Security Information and Event Management）**
> **安全信息与事件管理系统**：**集中收集**各类日志，做**关联分析**，发现攻击线索并告警。是现代安全运营中心（SOC）的核心平台。

> 📌 **日志的核心价值**：**"可追溯"**。出事之后能查清"**谁在什么时候做了什么**"，是**取证和定责**的基础。同时，**日志本身也要保护**（防止被攻击者删除）。

### 14.2 漏洞管理

> 💡 **术语解释｜漏洞管理（Vulnerability Management）**
> **系统化地发现、评估、修复**安全漏洞的全生命周期管理。

**核心流程：**

```
   发现（扫描）→ 评估（定级）→ 修复（打补丁/缓解）→ 验证（复测）→ 持续监控
```

**相关术语：**

| 术语 | 说明 |
|---|---|
| **CVE** | 公共漏洞编号（如 CVE-2021-44228 是 Log4j 漏洞） |
| **CVSS** | 漏洞**严重性评分**（0~10 分，越高越严重） |
| **补丁管理** | 及时更新系统和软件（**最直接的防御**） |
| **漏洞扫描器** | Nessus、OpenVAS、AWVS 等 |

> 💡 **术语解释｜CVSS（Common Vulnerability Scoring System，通用漏洞评分系统）**
> 给漏洞打分的标准（0~10 分）：
> - **0.0**：无
> - **0.1~3.9**：低危
> - **4.0~6.9**：中危
> - **7.0~8.9**：高危
> - **9.0~10.0**：**严重（Critical）**
>
> **用途**：帮助**优先级排序**——先修高危漏洞。

> 📌 **漏洞管理的核心原则**：**"修补已知漏洞、及时更新补丁"是最直接有效的措施**。90% 的攻击利用的是**已知但未修补**的漏洞。

### 14.3 应急响应

> 💡 **术语解释｜应急响应（Incident Response）**
> 安全事件发生后，**按预案快速处置**，**控制损失、恢复业务、追溯根因**。

**标准流程（PDCERF 模型）：**

| 阶段 | 英文 | 做什么 |
|---|---|---|
| **准备** | Preparation | 建预案、备工具、演练 |
| **检测** | Detection | 发现异常、确认事件 |
| **遏制** | Containment | **隔离受影响系统**，防止扩散 |
| **根除** | Eradication | 清除恶意代码、修复漏洞 |
| **恢复** | Recovery | 恢复业务、验证正常 |
| **跟踪** | Follow-up | 复盘、改进、完善预案 |

```
   准备 → 检测 → 遏制 → 根除 → 恢复 → 跟踪
    ↑                                        │
    └──────────── 复盘改进，持续优化 ──────────┘
```

> ⚠️ **应急响应的第一要务是"遏制"**——**先隔离，别让火继续烧**。很多事故因为"舍不得断网"而扩大损失。

### 14.4 合规与等级保护

> 💡 **术语解释｜网络安全等级保护（等保）**
> 中国的**网络安全合规制度**。根据系统的重要程度分**五个等级**，等级越高要求越严。**"等保 2.0"** 是现行标准。
>
> **核心**：**"一个中心，三重防护"**——安全管理中心 + 安全通信网络、安全区域边界、安全计算环境。

> 💡 **术语解释｜《网络安全法》**
> 中国网络安全的基础法律，明确了**网络运营者的安全义务**、**数据保护责任**、**应急响应要求**等。

> 📌 **合规不是负担，而是"安全底线"**：等保、ISO 27001、GDPR 等标准，本质上都是把"**最佳实践固化为要求**"。

## 16. 常见误区

**误区 1：内网就是安全的，外网才危险**
✅ 正确理解：**"内网 = 安全区"是最大的错觉**。内网横向移动是攻击的"标配"，一次沦陷可能导致全网沦陷。**这正是零信任要解决的问题。**

**误区 2：装了防火墙就安全了**
✅ 正确理解：防火墙只是**纵深防御的一层**。还需要 IDS/IPS、WAF、主机防护、加密、权限管理、安全意识等多层配合。**没有单一防线能防住所有攻击。**

**误区 3：HTTPS 就一定安全**
✅ 正确理解：HTTPS 保证**传输安全**，但**不保证网站可信**——**钓鱼网站也能申请证书**。看到小锁 ≠ 网站可信，还要**看域名是否正确**。

**误区 4：对称加密和非对称加密是对立的，选一个就行**
✅ 正确理解：**两者是配合使用的**。HTTPS 用"**非对称协商密钥 + 对称加密数据**"的混合方案。**非对称解决密钥分发，对称解决性能。**

**误区 5：MD5 可以用来存密码（只要够长）**
✅ 正确理解：**MD5 有碰撞漏洞且速度太快**，**绝不能用于密码存储**。应该用 **bcrypt/scrypt/Argon2** 等慢哈希 + **加盐**。

**误区 6：加密就能保证完整性**
✅ 正确理解：**加密只保证机密性**，不保证完整性。要保证完整性需要**哈希/MAC/数字签名**。所以 HTTPS 用 **AEAD（如 GCM）**同时提供两者。

**误区 7：签名和加密是一回事**
✅ 正确理解：**目的不同**——加密是"**不让别人看**"（用接收方公钥），签名是"**证明是谁发的、没被改**"（用发送方私钥）。**数字证书就是 CA 的签名。**

**误区 8：用了参数化查询就绝对安全了**
✅ 正确理解：参数化查询能防 SQL 注入，但**不能防所有漏洞**。还需要输入验证、最小权限、WAF、错误处理等多层防护。

**误区 9：XSS 和 CSRF 是一回事**
✅ 正确理解：**XSS 是"注入代码偷身份"**（信任了用户输入），**CSRF 是"借用身份发请求"**（信任了用户浏览器）。防御手段也不同。

**误区 10：隐藏 SSID / 改默认端口就能防攻击**
✅ 正确理解：这是"**隐晦式安全**"，**不是真正的防护**。抓包就能发现隐藏的 SSID，端口扫描能发现改过的端口。**真正的安全靠加密、认证、权限。**

**误区 11：零信任就是买个产品/上了 VPN**
✅ 正确理解：零信任是**理念 + 体系**，靠 IAM + 微隔离 + SDP + MFA 等多种技术组合落地。**VPN 仍是边界思路，不等于零信任。**

**误区 12：安全是"一次性"的，部署完就没事了**
✅ 正确理解：**安全是持续的过程**——要持续监控、打补丁、更新策略、应急演练。**"没有绝对安全，只有持续降低风险"。**

**误区 13：技术防护够强，就不需要安全意识培训了**
✅ 正确理解：**钓鱼和社会工程学攻击的是"人"**，技术防护挡不住一个点错链接的人。**安全意识培训是性价比最高的安全投入。**

**误区 14：被勒索软件加密了就交赎金**
✅ 正确理解：**交赎金不保证能解密，还助长犯罪**。正确做法是**平时做好离线备份**，被攻击后直接恢复。**备份是应对勒索软件的根本。**

### 任务 3：用 openssl 查看证书链并解读各字段

### 任务 5：密码哈希实验（理解加盐与慢哈希）

**目标**：亲手体验"为什么不能明文存密码"和"加盐的作用"。

```python
import hashlib, bcrypt, os

password = "mypassword123"

# 1. 不安全的做法：直接 MD5（易被彩虹表破解）
md5_hash = hashlib.md5(password.encode()).hexdigest()
print(f"MD5（不安全）: {md5_hash}")

# 2. 加盐的 SHA-256
salt = os.urandom(16)
salted = hashlib.sha256(salt + password.encode()).hexdigest()
print(f"加盐 SHA-256: {salted}")

# 3. 推荐的 bcrypt（慢哈希）
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
print(f"bcrypt（推荐）: {hashed.decode()}")

# 验证
print(f"密码正确? {bcrypt.checkpw(password.encode(), hashed)}")

# 观察：同样的密码，两次 bcrypt 结果不同（因为盐不同）
hashed2 = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
print(f"bcrypt 第二次: {hashed2.decode()}")
print(f"两次结果相同? {hashed == hashed2}")  # False！
```

**观察要点**：
- 相同密码的 MD5 每次都一样 → 可被彩虹表攻击
- bcrypt **每次结果都不同**（盐随机）→ 但都能验证通过
- **理解"加盐"和"慢哈希"的作用**

> 📝 **学习建议**：
> 1. **守住法律底线**：所有攻防实验**只在授权环境**进行。**"白帽"和"黑客"的区别就是"授权"。**
> 2. **理解攻击才能防御**：本阶段的重点是**"知其攻，方能防"**——每学一个攻击，立刻想"怎么防"。
> 3. **建立"威胁模型"思维**：看到任何系统，先问"**谁能攻击它？有什么弱点？会造成什么损失？**"
> 4. **动手验证**：用 Nmap、Wireshark、openssl、DVWA 亲手体验，**远比看书深刻**。
> 5. **安全意识最重要**：技术防护再强，也挡不住一个点错链接的人。**把安全变成习惯。**
> 6. **没有绝对安全**：安全是**持续降低风险**的过程，不是一次性的"上线即完成"。
