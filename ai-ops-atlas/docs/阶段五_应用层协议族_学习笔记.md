## 1. 应用层：协议的"最后一公里"

### 1.1 为什么还需要应用层

走到传输层，我们已经能**把一串字节从 A 进程可靠地送到 B 进程**了。但这还不够：

> **问题一**：这一串字节到底代表什么？是网页、是图片、是邮件、还是游戏指令？
> **问题二**：双方怎么"对话"？客户端先说什么、服务器怎么答、格式是什么？
> **问题三**：怎么用人类能记住的名字（`www.baidu.com`）代替一串 IP？

**这些"业务规则"就是应用层要定义的东西。**

> 💡 **术语解释｜应用层（Application Layer）**
> OSI 七层模型的最顶层，直接面向用户和应用程序。它**不负责数据传输**，只负责定义"应用程序之间如何交换信息"——包括**报文格式、交互顺序、字段含义**。
>
> **关键点**：应用层协议运行在**用户进程**里，不是操作系统内核。内核负责到传输层为止，再往上就交给具体的应用程序（浏览器、邮件客户端）自己处理。

> 💡 **术语解释｜应用层协议族**
> 应用层不是"一个协议"，而是**一大群协议**的集合，每个解决一类具体需求：
>
> | 需求 | 协议 |
> |---|---|
> | 浏览网页 | HTTP / HTTPS |
> | 域名解析 | DNS |
> | 自动获取 IP | DHCP |
> | 收发邮件 | SMTP / POP3 / IMAP |
> | 传输文件 | FTP / SFTP / TFTP |
> | 远程登录 | Telnet / SSH / RDP |
> | 实时双向通信 | WebSocket |
> | 时钟同步 | NTP |
> | 网络管理 | SNMP |
> | 动态路由信息交换 | RIP / OSPF / BGP（严格说跨层，但跑在应用层之上） |

### 1.2 应用层协议的两大架构

在写具体协议之前，先理解两种"谁主动、谁被动"的组织方式。

> 💡 **术语解释｜客户/服务器模式（Client/Server, C/S）**
> - **客户端**：主动发起请求，通常是"用户用的那一端"
> - **服务器**：被动等待请求，一直开机、有固定 IP、处理并发
>
> **例子**：浏览器访问网站、SSH 连服务器、数据库连接。
>
> **优点**：结构清晰、易管理、易扩展（加服务器）。
> **缺点**：服务器是单点，压力大、成本高。

> 💡 **术语解释｜对等模式（Peer-to-Peer, P2P）**
> 没有固定的服务器/客户端角色，**每个节点既是客户端又是服务器**，互相直接交换数据。
>
> **例子**：BitTorrent 下载、区块链、部分即时通讯。
>
> **优点**：去中心化、可扩展性强（人越多越快）。
> **缺点**：难管理、难计费、安全与版权问题突出。

**现代互联网的主流是 C/S 模式，但在 C/S 内部又演化出了"多层架构"：**

```
        客户端（浏览器/App）
              │  HTTP
              ▼
    ┌──────────────────┐
    │   反向代理/CDN    │  ← Nginx、CDN 节点
    └──────────────────┘
              │
              ▼
    ┌──────────────────┐
    │   应用服务器      │  ← 处理业务逻辑
    └──────────────────┘
         │        │
         ▼        ▼
      数据库    缓存/消息队列
```

> 📌 **面试高频**：为什么要有反向代理？因为它能**负载均衡、缓存静态资源、做 SSL 卸载（HTTPS 解密在这里完成）、隐藏后端结构**。

### 1.3 应用层协议的"三要素"

任何应用层协议，你都可以用这三个问题去拆解它：

| 要素 | 要回答的问题 | 例子（HTTP） |
|---|---|---|
| **报文格式** | 数据长什么样？字段怎么排？ | 请求行 + 头部 + 空行 + 正文 |
| **交互时序** | 谁先发、发几条、怎么应答？ | 请求 → 响应（一问一答） |
| **传输层选择** | 跑在 TCP 还是 UDP 上？ | TCP（HTTP/1.1、2）或 UDP（HTTP/3、DNS） |

**记住这个框架，后面每个协议都能套进去分析。**

## 2. HTTP 基础：万维网的通用语

### 2.1 HTTP 是什么

> 💡 **术语解释｜HTTP（HyperText Transfer Protocol，超文本传输协议）**
> 浏览器和服务器之间**交换网页资源**的应用层协议。它定义了**请求**和**响应**两种报文格式。
>
> **"超文本"**的意思是：文本里可以包含**指向其他资源的链接**（就是超链接），点一下就能跳到另一个文档——这是万维网（WWW）的核心思想。

**HTTP 的几个本质特征：**

| 特征 | 含义 | 通俗理解 |
|---|---|---|
| **无状态（Stateless）** | 服务器不记录"你是谁、上次干了啥" | 每次请求都是"陌生人上门" |
| **请求-响应模型** | 一定是客户端先请求，服务器才响应 | 服务器不会主动找你 |
| **基于 TCP** | HTTP/1.x、2 都跑在 TCP 之上 | 需要先三次握手建立连接 |
| **明文传输** | HTTP 本身不加密 | 中间人能看到全部内容 → 所以有了 HTTPS |
| **可扩展** | 通过头部字段自由扩展 | 想加什么功能，加个 Header 就行 |

> ⚠️ **"无状态"是理解 Cookie/Session 的钥匙**：正因为 HTTP 记不住你，所以要用 Cookie/Session/Token 这些"外挂机制"来给服务器补上记忆能力（见第 5 章）。

> 💡 **术语解释｜URL（Uniform Resource Locator，统一资源定位符）**
> 网络资源的"地址"。一个完整 URL 的解剖：
>
> ```
>   https://  www.example.com : 443 /path/to/page ? key=value # section
>   ────┬───  ───────┬───────   ─┬─  ─────┬──────   ────┬────   ───┬───
>     协议       主机名/域名      端口    路径           查询参数   片段
>   ```
>
> - **协议（Scheme）**：`http` / `https` / `ftp` / `file`
> - **主机（Host）**：域名或 IP，需要 DNS 解析成 IP
> - **端口（Port）**：省略时 http 默认 **80**，https 默认 **443**
> - **路径（Path）**：服务器上的资源位置
> - **查询串（Query String）**：`?` 开头的键值对，多个用 `&` 连接
> - **片段（Fragment）**：`#` 开头，**只在浏览器本地用**（锚点定位），不会发给服务器

### 2.2 HTTP 与 TCP 的关系

```
   应用层    ┌───────────────────────┐
             │   HTTP（请求/响应报文）  │
             └───────────┬───────────┘
   传输层    ┌───────────▼───────────┐
             │   TCP（可靠字节流）     │
             └───────────┬───────────┘
   网络层    ┌───────────▼───────────┐
             │   IP（寻址与路由）      │
             └───────────────────────┘
```

**一次完整网页访问，背后发生了什么（经典面试题）：**

```
1. 浏览器解析 URL，得到域名 www.example.com
2. DNS 解析：域名 → IP（第 9 章详解）
3. 建立 TCP 连接：三次握手（阶段四）
4. 【HTTPS 才有】TLS 握手，协商出会话密钥（第 8 章）
5. 发送 HTTP 请求报文
6. 服务器处理，返回 HTTP 响应报文
7. 浏览器渲染页面，可能再发起更多请求（图片/CSS/JS）
8. 连接关闭：四次挥手（HTTP/1.1 可复用连接，见第 7 章）
```

> 📌 **排查网页打不开的思路**：按上面 8 步顺序排查——域名能不能解析？端口通不通？握手成不成功？是不是证书报错？服务器返回什么状态码？**把这条链路背下来，80% 的网络问题都能定位。**

## 3. HTTP 报文格式详解

HTTP 的一切，都可以归结为**两种报文**：请求报文、响应报文。它们格式高度对称。

### 3.1 请求报文（Request）

```
POST /api/login HTTP/1.1          ← ① 请求行（方法 + 路径 + 版本）
Host: www.example.com              ┐
User-Agent: Mozilla/5.0            │
Content-Type: application/json     ├ ② 请求头（Headers）
Content-Length: 42                 │
Cookie: sessionid=abc123           ┘
                                   ← ③ 空行（CRLF，标志头部结束）
{"username":"tom","password":"***"} ← ④ 请求体（Body，可选）
```

**四部分缺一不可（请求体可为空）：**

| 部分 | 说明 | 关键点 |
|---|---|---|
| **① 请求行** | `方法 URL 版本` | 三者用**空格**分隔 |
| **② 请求头** | `字段名: 值` 的键值对 | 每个字段一行，**大小写不敏感** |
| **③ 空行** | 一个 `\r\n` | **必须存在**，否则服务器不知道头部何时结束 |
| **④ 请求体** | 实际数据 | GET 通常没有，POST/PUT 才有 |

> ⚠️ **空行不是"可有可无的格式"**，它是**协议语法的一部分**。没有空行，服务器无法区分"头部"和"正文"的边界，报文就会解析失败。

> 💡 **术语解释｜CRLF（回车换行）**
> HTTP 报文用 `\r\n`（回车 Carriage Return + 换行 Line Feed）作为**每一行的结束符**。这也是为什么用抓包工具看 HTTP 时，能看到一行行的清晰结构。**空行 = 一个单独的 `\r\n`。**

### 3.2 响应报文（Response）

```
HTTP/1.1 200 OK                    ← ① 状态行（版本 + 状态码 + 短语）
Server: nginx/1.24.0                ┐
Content-Type: text/html            ├ ② 响应头
Content-Length: 128                │
Set-Cookie: sessionid=xyz789        ┘
                                    ← ③ 空行
<html><body>Hello</body></html>     ← ④ 响应体
```

| 部分 | 说明 |
|---|---|
| **① 状态行** | `版本 状态码 原因短语` |
| **② 响应头** | 描述响应内容、缓存策略、Cookie 等 |
| **③ 空行** | 同样必须存在 |
| **④ 响应体** | 真正的资源内容（HTML/图片/JSON…） |

> 📌 **请求行 vs 状态行的记忆法**：请求行"我（客户端）想干什么"，状态行"你（服务器）干得怎么样"。

## 4. HTTP 方法、状态码与头部字段

### 4.1 HTTP 方法

> 💡 **术语解释｜HTTP 方法（Method）**
> 请求行里的第一个词，表示**客户端想对资源做什么操作**。它是"动词"。

| 方法 | 语义 | 幂等？ | 安全？ | 有请求体？ |
|---|---|---|---|---|
| **GET** | 获取资源 | ✅ | ✅ | 通常无 |
| **HEAD** | 只取响应头，不取正文 | ✅ | ✅ | 无 |
| **POST** | 提交数据 / 创建资源 | ❌ | ❌ | 有 |
| **PUT** | 全量更新/创建资源 | ✅ | ❌ | 有 |
| **PATCH** | 部分更新资源 | ❌ | ❌ | 有 |
| **DELETE** | 删除资源 | ✅ | ❌ | 可有 |
| **OPTIONS** | 查询支持的方法（CORS 预检） | ✅ | ✅ | 无 |
| **TRACE** | 回显请求（调试，很少用） | ✅ | ✅ | 无 |
| **CONNECT** | 建立隧道（HTTPS 代理） | ❌ | ❌ | 无 |

> 💡 **术语解释｜幂等（Idempotent）**
> **执行一次和执行多次，对服务器的最终效果相同。**
>
> - `GET`：查 100 次，服务器数据不变 → 幂等
> - `DELETE /user/1`：删 1 次和删 3 次，结果都是"用户 1 不存在" → 幂等
> - `POST /orders`：提交 3 次，就生成 3 个订单 → **不幂等**
>
> **为什么重要**：网络超时后客户端要**重试**。幂等的方法可以放心重试；不幂等的（POST）重试可能造成"重复下单"，所以要用**幂等键（Idempotency-Key）**等机制保护。

> 💡 **术语解释｜安全（Safe）方法**
> **不改变服务器状态**的方法。GET/HEAD/OPTIONS/TRACE 是安全的。
>
> ⚠️ **注意**：GET 是"安全方法"，但**不代表它没有副作用**——如果后端用 GET 做删除操作（`GET /delete?id=1`），那就是设计错误，会被爬虫、预取、浏览器缓存误触发。

> ⚠️ **常见误区**：GET 和 POST 的区别不只是"参数位置"。
>
> | 对比项 | GET | POST |
> |---|---|---|
> | 参数位置 | URL 查询串 | 请求体 |
> | 幂等 | ✅ | ❌ |
> | 可缓存 | ✅ | 默认不缓存 |
> | 长度限制 | 受 URL 长度限制（浏览器/服务器约 2KB～8KB） | 理论无限制（受服务器配置限制） |
> | 安全性 | 参数暴露在 URL、日志、历史记录中 | 相对隐蔽（但**明文传输时一样能被抓包**） |
> | 书签/回退 | 可收藏、可回退 | 回退会提示"重新提交" |

### 4.2 HTTP 状态码

> 💡 **术语解释｜状态码（Status Code）**
> 响应行里的三位数字，表示**请求的处理结果**。**第一位数字决定类别。**

| 类别 | 含义 | 记忆法 |
|---|---|---|
| **1xx** | 信息性，请求已收到，继续处理 | 罕见，如 `101 Switching Protocols`（WebSocket 升级） |
| **2xx** | 成功 | 一切正常 |
| **3xx** | 重定向 | 资源搬走了，去别处找 |
| **4xx** | 客户端错误 | **你（客户端）的锅** |
| **5xx** | 服务器错误 | **我（服务器）的锅** |

**必背的十几个状态码：**

| 状态码 | 短语 | 含义与场景 |
|---|---|---|
| **200** | OK | 请求成功 |
| **201** | Created | 资源创建成功（POST 后返回） |
| **204** | No Content | 成功但无返回内容（DELETE 常用） |
| **206** | Partial Content | 断点续传、视频分片（配合 Range 头） |
| **301** | Moved Permanently | **永久**重定向，浏览器会缓存新地址 |
| **302** | Found | **临时**重定向，下次还访问老地址 |
| **304** | Not Modified | 资源没变，**用你本地的缓存**（第 6 章详解） |
| **307 / 308** | Temporary/Permanent Redirect | 重定向且**保持原方法**（不会把 POST 变 GET） |
| **400** | Bad Request | 请求语法错误，服务器看不懂 |
| **401** | Unauthorized | **未认证**——你没登录 |
| **403** | Forbidden | **已认证但无权限**——登录了但不让你看 |
| **404** | Not Found | 资源不存在 |
| **405** | Method Not Allowed | 方法不被支持（如对只读接口用 POST） |
| **408** | Request Timeout | 请求超时 |
| **429** | Too Many Requests | 请求太频繁（限流） |
| **500** | Internal Server Error | 服务器内部错误（代码报错） |
| **502** | Bad Gateway | 网关/代理从上游拿到无效响应（后端挂了） |
| **503** | Service Unavailable | 服务不可用（过载/维护） |
| **504** | Gateway Timeout | 网关等上游超时 |

> ⚠️ **重点区分（面试高频）**：
> - **301 vs 302**：永久 vs 临时。SEO 上 301 会把权重转移到新地址，302 不会。
> - **401 vs 403**：401 是"**你是谁**"（未认证），403 是"**你不配**"（已认证但无权限）。
> - **502 vs 504**：502 是上游返回了**坏响应**（如后端进程崩了），504 是上游**没在时限内响应**（如后端卡死）。排查方向不同：502 查后端是否存活，504 查后端是否慢。
> - **302 改方法陷阱**：用 302 重定向一个 POST 请求，浏览器会把它变成 GET，参数丢失。要保方法就用 **307/308**。

### 4.3 常用请求头与响应头

**请求头（客户端 → 服务器）：**

| 头部 | 作用 | 示例 |
|---|---|---|
| `Host` | **必填**，指明目标主机（虚拟主机靠它区分） | `Host: www.example.com` |
| `User-Agent` | 客户端身份（浏览器/系统/爬虫） | `Mozilla/5.0 (Windows NT 10.0...)` |
| `Accept` | 能接受的内容类型 | `Accept: text/html,application/json` |
| `Accept-Encoding` | 能接受的压缩方式 | `Accept-Encoding: gzip, br` |
| `Accept-Language` | 语言偏好 | `Accept-Language: zh-CN,zh;q=0.9` |
| `Cookie` | 携带的 Cookie | `Cookie: sessionid=abc` |
| `Referer` | 从哪个页面跳转来的 | `Referer: https://google.com` |
| `Authorization` | 认证凭证 | `Authorization: Bearer <token>` |
| `Content-Type` | **请求体**的格式 | `Content-Type: application/json` |
| `Content-Length` | 请求体的字节长度 | `Content-Length: 42` |
| `If-None-Match` | 缓存校验（配合 ETag） | `If-None-Match: "abc123"` |
| `Range` | 请求部分内容（断点续传） | `Range: bytes=0-1023` |

**响应头（服务器 → 客户端）：**

| 头部 | 作用 | 示例 |
|---|---|---|
| `Content-Type` | **响应体**的类型 | `Content-Type: text/html; charset=utf-8` |
| `Content-Length` | 响应体字节长度 | `Content-Length: 128` |
| `Content-Encoding` | 压缩方式 | `Content-Encoding: gzip` |
| `Set-Cookie` | 下发 Cookie | `Set-Cookie: sessionid=xyz; HttpOnly` |
| `Cache-Control` | 缓存策略 | `Cache-Control: max-age=3600` |
| `ETag` | 资源版本标识 | `ETag: "abc123"` |
| `Last-Modified` | 资源最后修改时间 | `Last-Modified: Wed, 15 Oct 2026 08:00:00 GMT` |
| `Location` | 重定向目标 | `Location: https://new.example.com` |
| `Server` | 服务器软件 | `Server: nginx/1.24.0` |
| `Access-Control-Allow-Origin` | CORS 跨域许可 | `Access-Control-Allow-Origin: *` |
| `Strict-Transport-Security` | HSTS，强制 HTTPS | `max-age=31536000` |

> 💡 **术语解释｜Content-Type vs Accept**
> - `Accept`（请求头）：**我能收什么**（客户端告诉服务器）
> - `Content-Type`（请求/响应头）：**我发的是什么**（发送方告诉接收方）
>
> 记忆：**Accept 是"胃口"，Content-Type 是"这道菜是什么"。**

> 💡 **术语解释｜常见 MIME 类型**
> `Content-Type` 的值来自 **MIME（Multipurpose Internet Mail Extensions）**标准：
>
> | 类型 | 含义 |
> |---|---|
> | `text/html` | HTML 页面 |
> | `text/plain` | 纯文本 |
> | `application/json` | JSON 数据 |
> | `application/xml` | XML 数据 |
> | `application/x-www-form-urlencoded` | 表单默认提交格式 |
> | `multipart/form-data` | 表单含文件上传 |
> | `image/png`、`image/jpeg` | 图片 |
> | `application/octet-stream` | 二进制流（未知类型/下载） |

> 💡 **术语解释｜Host 头为什么必填**
> 一台服务器（一个 IP）上可能托管着几百个网站（**虚拟主机**）。服务器**只靠 `Host` 头**判断你要访问哪个站点。HTTP/1.1 强制要求携带 Host；如果没有，服务器只能返回默认站点或 400 错误。

## 5. Cookie、Session 与 Token

### 5.1 问题的起点：HTTP 无状态

HTTP 是无状态的，但"登录后保持登录状态""购物车不丢"这些需求，**都要求服务器记住你是谁**。于是有了三套方案。

### 5.2 Cookie：客户端的小纸条

> 💡 **术语解释｜Cookie**
> 服务器通过 `Set-Cookie` 响应头**下发给浏览器**的一小段文本（通常 ≤4KB），浏览器把它**存起来**，之后**每次请求同一域名时自动通过 `Cookie` 请求头带回**。
>
> **本质**：存在客户端的一小块"服务器给的凭证"。

**交互过程：**

```
① 客户端                             服务器
   │  POST /login  ──────────────────▶ │
   │                                   │ 验证账号密码
   │  ◀── 200 OK                       │
   │      Set-Cookie: sessionid=abc    │
   │                                   │
② 浏览器把 sessionid=abc 存起来
   │                                   │
   │  GET /profile                     │
   │  Cookie: sessionid=abc ─────────▶ │
   │                                   │ 靠 abc 认出你是谁
   │  ◀── 200 OK (你的个人资料)         │
```

**Cookie 的重要属性：**

| 属性 | 作用 |
|---|---|
| `Expires` / `Max-Age` | 过期时间。不设则为**会话 Cookie**，关浏览器就没了 |
| `Domain` | 哪些域名可以携带此 Cookie |
| `Path` | 哪些路径可以携带此 Cookie |
| **`HttpOnly`** | **禁止 JavaScript 读取**，防 XSS 窃取 |
| **`Secure`** | **只在 HTTPS 下发送**，防明文泄露 |
| **`SameSite`** | 跨站请求是否携带，防 CSRF。`Strict`/`Lax`/`None` |

> ⚠️ **安全三件套**：`HttpOnly` + `Secure` + `SameSite=Lax`（或 Strict）是生产环境的标配，缺一个都可能被攻击。

### 5.3 Session：服务器的小账本

> 💡 **术语解释｜Session（会话）**
> 服务器端保存的**用户状态数据**。服务器为每个用户生成一个唯一 **Session ID**，把数据存在服务器（内存/Redis/数据库），只把 **Session ID** 通过 Cookie 发给客户端。
>
> **本质**：数据在**服务器**，客户端只拿一把"钥匙"（Session ID）。

```
客户端               服务器（Session 存储）
  │  Cookie: sessionid=abc   │
  │ ───────────────────────▶ │
  │                          │  查 abc → {user: "tom", role: "admin"}
  │  ◀─── 个性化响应 ──────── │
```

| 对比 | Cookie | Session |
|---|---|---|
| 数据存放位置 | 客户端（浏览器） | 服务器 |
| 存储容量 | 小（约 4KB/个） | 受服务器内存限制 |
| 安全性 | 低（可被篡改/窃取） | 较高（数据不在客户端） |
| 服务器压力 | 无 | 有（需存储，分布式要共享） |
| 跨域支持 | 受同源策略限制 | 同样依赖 Cookie 传 ID |

> 📌 **Session 的分布式难题**：多台服务器时，用户在 A 机器登录，请求被负载均衡到 B 机器就"掉线"了。解决方案：
> 1. **Session 集中存储**：存到 Redis（最常用）
> 2. **Session 粘滞（Sticky Session）**：同一用户固定打到同一台机器
> 3. **改用 Token（JWT）**：状态放客户端，服务器无状态 ← 现代趋势

### 5.4 Token 与 JWT：无状态的通行证

> 💡 **术语解释｜Token（令牌）**
> 服务器签发的一串**自包含凭证**，客户端保存（通常在 `Authorization: Bearer <token>` 头里携带）。服务器**不存储**它，只靠**验签**判断真伪。
>
> **本质**：把状态**编码进令牌本身**，服务器无需存储 → **无状态**。

> 💡 **术语解释｜JWT（JSON Web Token）**
> 最流行的 Token 格式，由**三段 Base64URL** 用 `.` 连接：
>
> ```
> eyJhbGciOiJIUzI1NiJ9 . eyJ1c2VyIjoiemhhbmdzYW4ifQ . dBjftJeZ4CVP...
>      Header                  Payload                 Signature
>     （算法类型）            （数据+过期时间）          （签名，防篡改）
> ```
>
> - **Header**：声明签名算法（如 HS256、RS256）
> - **Payload**：存放数据（用户 ID、角色、`exp` 过期时间等）——**注意是 Base64 编码，不是加密，任何人都能解开看**
> - **Signature**：用服务器密钥对前两段签名，**防止篡改**

> ⚠️ **JWT 最常见的误用**：**把敏感信息（密码、身份证号）放进 Payload。** Payload 只是 Base64 编码，**任何人 Base64 解码就能看到明文**！JWT 保证的是"不可篡改"，不是"不可读"。要保密就得上 JWE（加密的 JWT）。

**Cookie/Session vs JWT 选型：**

| 维度 | Session | JWT |
|---|---|---|
| 服务器状态 | 有状态（要存） | 无状态（不存） |
| 横向扩展 | 需共享存储 | 天然支持 |
| 主动失效 | 容易（删 Session） | 困难（签发后到期前一直有效，需黑名单） |
| 跨域/多端 | 依赖 Cookie，受限 | 放 Header 里，天然跨域 |
| 适用场景 | 传统 Web、管理后台 | 前后端分离、移动端、微服务 |

## 6. HTTP 缓存机制

缓存的目的是：**别每次都去服务器拿，能省就省。** 它分为"强缓存"和"协商缓存"两级。

### 6.1 强缓存：直接用本地，不问服务器

> 💡 **术语解释｜强缓存（Freshness Cache）**
> 浏览器判断本地缓存**还在有效期内**，就**直接使用，根本不发请求**。
>
> **判断依据**：`Cache-Control` 或 `Expires`。

| 响应头 | 说明 | 优先级 |
|---|---|---|
| **`Cache-Control: max-age=3600`** | 缓存 3600 秒（相对时间） | **高**（HTTP/1.1） |
| `Expires: Wed, 15 Oct 2026 ...` | 绝对过期时间（依赖客户端时钟） | 低（HTTP/1.0） |

**`Cache-Control` 常用指令：**

| 指令 | 含义 |
|---|---|
| `max-age=N` | 缓存 N 秒 |
| `no-cache` | **不**直接用强缓存，**每次都要去服务器验证**（走协商缓存） |
| `no-store` | **完全不缓存**（敏感数据） |
| `public` | 可被任何缓存（含 CDN、代理）缓存 |
| `private` | 只允许浏览器缓存（不允许 CDN 缓存） |
| `must-revalidate` | 过期后必须去验证，不能再用旧的 |

> ⚠️ **`no-cache` ≠ `no-store`**（超高频考点）：
> - **`no-cache`**：**可以缓存**，但**每次使用前必须向服务器确认**是否还有效 → 走协商缓存
> - **`no-store`**：**彻底不缓存**，任何地方都不存
>
> 记法：**no-cache 是"缓存但先问"，no-store 是"根本不存"。**

### 6.2 协商缓存：问一下服务器"变了吗"

强缓存过期后，浏览器**带上标识去问服务器**：

```
客户端                                      服务器
  │  GET /style.css                          │
  │  If-None-Match: "abc123" ──────────────▶ │
  │                                          │ 比对 ETag
  │  ◀── 304 Not Modified ────────────────── │  （没变，用你的缓存）
  │                                          │
  │  （如果变了：）                           │
  │  ◀── 200 OK + 新内容 + 新 ETag ───────── │
```

**两组配对字段：**

| 响应头（服务器给） | 请求头（浏览器带回） | 说明 |
|---|---|---|
| **`ETag: "abc123"`** | **`If-None-Match: "abc123"`** | 资源内容指纹（优先级高） |
| `Last-Modified: <时间>` | `If-Modified-Since: <时间>` | 资源最后修改时间（精度到秒） |

> 💡 **术语解释｜ETag（Entity Tag）**
> 服务器给资源算的一个**内容指纹**（如哈希值）。内容只要变一个字节，ETag 就变。
>
> **为什么 ETag 比 Last-Modified 更准？**
> - Last-Modified 精度只到**秒**，1 秒内改多次识别不出
> - 文件"内容没变但修改时间变了"（如重新部署）会误判
> - 分布式服务器时间不一致会导致判断出错

### 6.3 完整缓存决策流程

```
        发起请求
           │
           ▼
   ┌───────────────┐
   │ 有强缓存吗？   │──否──▶ 直接请求服务器
   └───────┬───────┘
           │是（未过期）
           ▼
   ┌───────────────┐
   │ 直接用本地缓存 │  （200 from cache，不发请求）
   └───────────────┘
           │强缓存过期
           ▼
   ┌───────────────┐
   │ 带 ETag/时间   │
   │ 去服务器验证   │
   └───────┬───────┘
           │
      ┌────┴────┐
      ▼         ▼
   没变       变了
   304        200 + 新内容
  （用本地）  （更新缓存）
```

> 📌 **生产实践**：
> - **HTML**：`no-cache`（每次验证，保证拿到最新页面）
> - **CSS/JS/图片**：`max-age=31536000`（缓存 1 年）+ **文件名带哈希**（如 `app.a3f9c2.js`）——内容变则文件名变，等于"永久缓存 + 自动更新"

## 7. HTTP 版本演进：1.1 → 2 → 3

这是应用层最有意思的一段演进史，**每一版都在解决上一版的性能瓶颈**。

### 7.1 HTTP/1.0 → HTTP/1.1：连接复用

| 特性 | HTTP/1.0 | HTTP/1.1 |
|---|---|---|
| 连接 | **每个请求一个 TCP 连接**，用完就关 | **默认长连接（Keep-Alive）**，可复用 |
| Host 头 | 可选 | **必填** |
| 管道化 | 无 | 有（但基本没人用，因队头阻塞） |
| 缓存 | Expires | 增加 Cache-Control、ETag |

> 💡 **术语解释｜持久连接（Persistent Connection / Keep-Alive）**
> 一次 TCP 连接上可以发送**多个** HTTP 请求/响应，不用每次重新握手。HTTP/1.1 默认开启。
>
> **好处**：省去反复三次握手的开销（一个 RTT 起步）。

**HTTP/1.1 的两大瓶颈：**

**① 队头阻塞（Head-of-Line Blocking, HOL）**

HTTP/1.1 的请求在一条连接上是**串行**的：前一个响应没回来，后一个就得等。

```
连接上的请求队列：  [请求1] [请求2] [请求3]
                      │
                      ▼
              请求1 慢 → 请求2、3 全被堵住 ← 队头阻塞
```

**② 并发连接数限制**

浏览器为绕过队头阻塞，对同一域名**最多开 6 个 TCP 连接**（Chrome 是 6）。超出就排队。

> ⚠️ **HTTP/1.1 的"优化黑科技"**（都是被队头阻塞逼出来的）：
> - **域名分片（Domain Sharding）**：把资源分到 `img1.a.com`、`img2.a.com`… 绕过 6 连接限制
> - **雪碧图（CSS Sprite）**：多张小图拼成一张，减少请求数
> - **资源合并**：多个 JS/CSS 合成一个文件
> - **内联**：小图片转 Base64 直接嵌进 CSS/HTML
>
> **这些手段在 HTTP/2 时代都成了"反模式"**——因为 HTTP/2 多路复用后，分片和合并反而有害。

### 7.2 HTTP/2：多路复用 + 二进制

HTTP/2（2015 年标准化，RFC 7540）是**近十年最大的一次革新**。

**核心改进：**

| 特性 | 说明 |
|---|---|
| **二进制分帧** | 报文从文本改为**二进制帧**，解析更高效、更不易出错 |
| **多路复用（Multiplexing）** | **一条 TCP 连接上并行跑多个请求**，互不阻塞 |
| **头部压缩（HPACK）** | 用静态表 + 动态表压缩头部，典型省 50%+ |
| **服务器推送（Server Push）** | 服务器可主动把资源推给客户端（现已基本弃用） |
| **流优先级** | 可标记资源优先级 |

> 💡 **术语解释｜帧（Frame）、消息（Message）、流（Stream）**
> HTTP/2 的三个层次概念，层层包含：
> - **帧（Frame）**：最小单位，二进制，带 `Stream ID` 标记属于哪个流
> - **消息（Message）**：一个请求或响应，由多个帧组成
> - **流（Stream）**：一条逻辑通道，承载一次请求/响应，有唯一 `Stream ID`
>
> **一条 TCP 连接上可以有成百上千个并发的流。**

```
HTTP/1.1（多条连接，串行）：
连接1: [请求1──────][请求2──────]
连接2: [请求3──────][请求4──────]
连接3: [请求5──────]
       ↑ 每个连接内部仍会队头阻塞

HTTP/2（一条连接，多路复用）：
连接1: [流1─][流2─][流3─][流1─][流2─][流3─]...
       ↑ 各流交织并行，互不阻塞
```

> ⚠️ **HTTP/2 的遗留问题：TCP 层队头阻塞**
> HTTP/2 解决了**应用层**队头阻塞，但因为所有流共享**一条 TCP 连接**，一旦**底层 TCP 丢包**，整个连接的所有流都会被卡住等重传。
>
> **这就是 HTTP/3 要解决的问题。**

### 7.3 HTTP/3：抛弃 TCP，拥抱 QUIC

HTTP/3（2022 年 RFC 9114）**把传输层从 TCP 换成了 QUIC**（基于 UDP）。

> 💡 **术语解释｜QUIC（Quick UDP Internet Connections）**
> Google 主导、基于 **UDP** 的新传输协议。它在**用户态**实现了可靠传输、拥塞控制、加密，并解决了 TCP 的队头阻塞。

| 对比 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | **QUIC（UDP）** |
| 数据格式 | 文本 | 二进制 | 二进制 |
| 多路复用 | ❌ | ✅ | ✅ |
| 应用层队头阻塞 | 有 | 无 | 无 |
| **传输层队头阻塞** | 有 | **有** | **无** |
| 头部压缩 | 无 | HPACK | QPACK |
| 握手延迟 | TCP+TLS 多次 RTT | 同左 | **1-RTT / 0-RTT** |
| 连接迁移 | ❌ | ❌ | ✅ |

> 💡 **术语解释｜连接迁移（Connection Migration）**
> QUIC 用 **Connection ID** 而非"IP+端口四元组"来标识连接。**手机从 WiFi 切到 4G，IP 变了，但连接不中断**——因为 Connection ID 没变。
>
> **对比**：TCP 连接靠四元组标识，一换网络就断连，所有请求得重来。

> 💡 **术语解释｜0-RTT（Zero Round-Trip Time）**
> 对于之前连接过的服务器，客户端可以在**第一条消息里就带上数据**，不用等握手完成，省掉一个 RTT。
>
> ⚠️ **代价**：0-RTT 数据可能被**重放攻击**（攻击者截获后重复发送）。所以 0-RTT 只用于**幂等的 GET 请求**，不能用于支付等敏感操作。

**版本选择建议：**

```
新项目/公网服务：HTTP/3（QUIC）优先，HTTP/2 兜底
内网/兼容性要求高：HTTP/1.1 + HTTP/2
老旧系统：HTTP/1.1
```

> 📌 **一句话总结演进**：
> **HTTP/1.1 是"一条路多辆车排队"；HTTP/2 是"一条路多车道并行，但路上有块大石头（TCP 丢包）会堵死全部"；HTTP/3 是"每辆车自己开路（QUIC 流独立），石头只堵一条道"。**

## 8. HTTPS 与 TLS：给 HTTP 上锁

### 8.1 HTTP 的三大安全缺陷

| 缺陷 | 后果 |
|---|---|
| **明文传输** | 中间人（运营商、WiFi 热点、黑客）能直接看到账号密码、聊天内容 |
| **无法验证身份** | 你访问的"银行网站"可能是钓鱼站，你无从分辨 |
| **无法保证完整性** | 传输内容可被中途篡改（如插入广告、改支付账号） |

**HTTPS = HTTP + TLS**，用来同时解决这三个问题。

> 💡 **术语解释｜HTTPS（HTTP Secure）**
> 严格说 HTTPS **不是一个独立协议**，而是"**HTTP 跑在 TLS 之上**"的组合：
>
> ```
>   ┌─────────────────┐
>   │      HTTP       │  ← 还是那个 HTTP，报文格式不变
>   ├─────────────────┤
>   │      TLS        │  ← 新增的安全层（加密、认证、完整性）
>   ├─────────────────┤
>   │      TCP        │
>   ├─────────────────┤
>   │       IP        │
>   └─────────────────┘
> ```
>
> **默认端口 443**（HTTP 是 80）。

> 💡 **术语解释｜TLS（Transport Layer Security，传输层安全）**
> HTTPS 背后的加密协议。前身是 **SSL**（Secure Sockets Layer），SSL 3.0 后更名为 TLS。现在说的"SSL 证书"其实就是"TLS 证书"，**SSL 各版本已全部废弃**，务必用 **TLS 1.2+**。

### 8.2 两种加密方式：各有短板

**① 对称加密（Symmetric Encryption）**

> 💡 **术语解释｜对称加密**
> **加密和解密用同一把密钥**。代表算法：**AES**、ChaCha20。
>
> **优点**：**极快**（CPU 有硬件加速指令，AES-GCM 处理流量几乎无感）。
> **致命缺点**：**密钥怎么安全地给对方？** 直接在网上传，会被中间人截获。

```
明文 + 同一把密钥 → 密文 → 同一把密钥 → 明文
         ↑
    问题：这把密钥怎么安全送到对方手里？
```

**② 非对称加密（Asymmetric Encryption）**

> 💡 **术语解释｜非对称加密**
> 用**一对密钥**：**公钥（Public Key）** 公开，**私钥（Private Key）** 保密。
>
> - 公钥加密 → 只有私钥能解
> - 私钥签名 → 只有公钥能验
>
> **代表算法**：RSA、ECC（椭圆曲线）。
>
> **优点**：**解决了密钥分发问题**——公钥随便公开，不怕被截获。
> **缺点**：**慢**（比对称加密慢几个数量级），扛不住大数据量传输。

> 📌 **生活类比**：公钥像一个**带投信口的信箱**，谁都能往里投信，但只有拿着钥匙的你能打开。你只要把信箱位置公开就行，不用偷偷递钥匙。

### 8.3 混合加密：HTTPS 的答案

**只用对称**：快，但密钥送不出去。
**只用非对称**：密钥送得出去，但太慢。

**HTTPS 的答案：两者结合。**

```
【握手阶段】用非对称加密，安全地协商出一把临时"会话密钥"
                    │
                    ▼
【传输阶段】用这把会话密钥（对称加密）加密所有实际数据
```

> **一句话**：**用"慢"的握手，换来"快"的全程加密。**

### 8.4 TLS 握手流程

**TLS 1.2 完整握手（两次往返，2-RTT）：**

```
客户端                                          服务器
  │                                                │
  │ ① ClientHello ───────────────────────────────▶ │
  │    · 支持的 TLS 版本                             │
  │    · 支持的加密套件列表                          │
  │    · 客户端随机数（Client Random）               │
  │                                                │
  │ ◀─────────────────────────────── ② ServerHello │
  │    · 选定的加密套件                              │
  │    · 服务器随机数（Server Random）               │
  │                                                │
  │ ◀────────────────────────── ③ Certificate       │
  │    · 服务器数字证书（含网站公钥）                 │
  │                                                │
  │ ◀────────────────── ④ ServerKeyExchange（可选）  │
  │    · ECDHE 交换参数（用于前向保密）               │
  │                                                │
  │ ◀──────────────────────── ⑤ ServerHelloDone     │
  │                                                │
  │ ⑥ 验证证书 → 生成 pre-master secret             │
  │                                                │
  │ ⑦ ClientKeyExchange ─────────────────────────▶ │
  │    · 用服务器公钥加密的 pre-master secret         │
  │                                                │
  │ ⑧ ChangeCipherSpec + Finished ───────────────▶ │
  │    · "我这边切到加密了，这是验证数据"             │
  │                                                │
  │ ◀──────── ⑨ ChangeCipherSpec + Finished ─────── │
  │                                                │
  │ ⑩ 双方开始用会话密钥加密传输 HTTP 数据            │
```

**会话密钥怎么来的？**

```
会话密钥 = f( 客户端随机数 + 服务器随机数 + pre-master secret )
```

> 💡 **为什么需要"两个随机数 + 一个秘密"？**
> - **客户端随机数 + 服务器随机数**：保证**每次会话的密钥都不同**（即使 pre-master 相同，结果也不同）
> - **pre-master secret**：提供**真正不可预测的熵**
>
> 三个要素缺一不可，任何一方被干扰，最终密钥就对不上，握手失败。

> 💡 **术语解释｜加密套件（Cipher Suite）**
> 一组算法的组合，格式如 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`：
> - `ECDHE`：密钥交换算法
> - `RSA`：身份认证（签名）算法
> - `AES_128_GCM`：对称加密算法
> - `SHA256`：消息认证码（MAC）算法

### 8.5 前向保密（PFS）：一次泄露 ≠ 全盘皆输

> 💡 **术语解释｜前向保密（Perfect Forward Secrecy, PFS）**
> 即使**服务器私钥将来泄露**，**过去被记录的历史会话**依然无法被解密。

**为什么需要它？**

- **旧方式（RSA 密钥交换）**：客户端用服务器证书里的**公钥**加密 pre-master secret。如果服务器私钥事后泄露 → 攻击者能解出所有历史 pre-master → **还原所有历史会话密钥 → 十年抓包全部解密**。
- **新方式（ECDHE 密钥交换）**：客户端和服务器**各自生成临时密钥**，通过 DH 交换算出共享秘密。**服务器私钥只用来签名（证明身份），不参与解密**。私钥泄露，历史会话依然安全。

> 📌 **结论**：**现代部署必须用 ECDHE 类套件**（`TLS_ECDHE_*`），放弃纯 RSA 密钥交换。用命令 `openssl s_client -connect example.com:443` 可以查看服务器实际使用的套件。

### 8.6 数字证书与 CA：给公钥上"户口"

**问题**：非对称加密解决了"密钥怎么送"，但没解决"**你给的公钥到底是不是你的**"。

**中间人攻击（MITM）：**

```
        客户端                    攻击者                    真实服务器
          │                        │                          │
          │  我要 example.com 的公钥 │                          │
          │ ──────────────────────▶ │                          │
          │                        │  攻击者把自己的公钥给你   │
          │ ◀────────────────────── │                          │
          │  用攻击者的公钥加密       │                          │
          │ ──────────────────────▶ │ 用自己私钥解开看明文      │
          │                        │ ────────────────────────▶ │
          │                        │ ◀──────────────────────── │
          │ ◀────────────────────── │ 原样转发
          │                        │
       两头都被蒙在鼓里，明文全被偷看
```

**根源**：用户**无法判断拿到的公钥属于谁**。

> 💡 **术语解释｜CA（Certificate Authority，证书颁发机构）**
> 双方**共同信任的第三方**。负责**验证网站身份，并用 CA 自己的私钥为网站公钥签名**，签发数字证书。

> 💡 **术语解释｜数字证书（Digital Certificate）**
> CA 签发的"公钥身份证"，包含：
>
> | 字段 | 内容 |
> |---|---|
> | 版本 | X.509 v3 |
> | 序列号 | 证书唯一编号 |
> | **签名算法** | CA 用哪种算法签名 |
> | **签发者（Issuer）** | 哪个 CA 签的 |
> | **有效期** | 起止时间（现在一般 ≤ 398 天） |
> | **主体（Subject）** | 证书归属的域名/组织 |
> | **公钥** | 网站的公钥 |
> | **SAN** | 该证书适用的所有域名列表 |
> | **数字签名** | CA 用私钥对以上内容的签名 |

**证书本质**：**CA 用自己的私钥，对"域名 + 网站公钥 + 有效期 + 签发者信息"做了一次数字签名。**

**浏览器如何验证证书？**

```
收到证书后，浏览器依次检查：
① 用内置的 CA 公钥验签 → 证书是不是伪造的？
② 检查证书里的域名与访问域名是否一致（看 SAN）
③ 检查有效期是否在范围内
④ 查询吊销状态（CRL / OCSP）→ 证书有没有被提前作废
   全部通过 → 地址栏亮起小锁 🔒
   任一失败 → 弹出证书告警
```

### 8.7 证书链：根证书为什么"轻易不出山"

> 💡 **术语解释｜证书链（Certificate Chain）**
> 根证书 → 中间证书 → 站点证书 的信任传递链。

**为什么要分级？** 因为**根证书私钥一旦泄露，整个互联网的信任体系瞬间崩塌**。所以：

```
    根证书（Root CA）
    · 存放在高度隔离的离线环境
    · 系统/浏览器内置其公钥（预装信任名单）
    · 极少直接签发站点证书
           │ 签发
           ▼
    中间证书（Intermediate CA）
    · 日常使用，可随时吊销
           │ 签发
           ▼
    站点证书（Leaf / End-Entity）
    · 发给具体的网站
```

**验证时**：浏览器从站点证书向上找到中间证书，再向上找到根证书，**直到链条顶端落在系统内置的信任根上**。

> ⚠️ **安全警示**：任何叫你"信任此证书"的弹窗都要慎重！**手动信任一个不明来源的 CA，等于亲手拆掉 HTTPS 的这道门。** 攻击者可以自建 CA，诱导你信任后，它签发的所有证书都被当作合法。

### 8.8 TLS 1.3 的改进

| 特性 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| 握手往返 | 2-RTT | **1-RTT**（会话恢复可 0-RTT） |
| 前向保密 | 可选（看套件） | **强制默认** |
| 不安全算法 | 还保留（如 RC4、CBC、纯 RSA 交换） | **全部删除** |
| 加密范围 | 部分握手消息明文 | **大部分握手消息加密** |
| 密钥交换 | RSA / DH / ECDHE | **仅 ECDHE / DHE** |

> 📌 **落地建议**：公网新服务**优先启用 TLS 1.3**，同时**保留 TLS 1.2 + ECDHE 兜底**，给老设备留兼容通道。别为了"看起来最强"把旧版本全关死，否则会把老客户端流量挡在门外。

### 8.9 抓包工具为什么能解密 HTTPS

很多人以为抓包工具"破解了 HTTPS"——**并没有**。

**原理**：工具让你**先安装一个本地 CA 证书**到系统信任库，然后它**动态生成一张"由你刚信任的 CA 签发"的站点证书**。浏览器验证证书链时，发现顶端落在被信任的根上，于是校验通过，客户端就同意和工具建立加密隧道；工具再以自己的身份和真实服务器建立另一条隧道。

**这本质上是一次"经你授权的中间人攻击"。** 它没攻破任何加密算法，只是把你的信任从"真实站点"扩展到了"工具本身"。

> 💡 **术语解释｜SSLKEYLOGFILE**
> 另一种解密方式：让浏览器把**会话密钥**写到一个日志文件里，Wireshark 读取该文件后就能解密。**仅用于本地调试，绝不能在他人设备上使用。**

### 8.10 一表串起 HTTPS 全链路

| 机制 | 解决什么问题 | 仍不能做什么 |
|---|---|---|
| **对称加密** | 大数据量快速加密 | 无法安全分发密钥 |
| **非对称加密** | 安全传递会话密钥、支持签名 | 无法确认公钥归属、速度慢 |
| **混合加密** | 兼顾性能与安全 | 无法防止公钥被调包 |
| **CA 认证** | 为公钥实名背书，防替换 | 用户主动信任恶意 CA 时形同虚设 |
| **TLS 1.3 + PFS** | 降低延迟、保证历史安全 | 仍需正确部署 |

> **核心记忆**：**HTTPS = 对称加密的性能 + 非对称加密的密钥交换 + CA 的公钥背书 + 用户的信任决策。**

## 9. DNS：互联网的电话簿

### 9.1 为什么需要 DNS

人类记得住 `www.baidu.com`，记不住 `110.242.68.66`。DNS 就是**把域名翻译成 IP** 的系统。

> 💡 **术语解释｜DNS（Domain Name System，域名系统）**
> 分布式的**域名 → IP 地址**映射系统。它运行在 **UDP 53 端口**（区域传送用 TCP 53），是一个**全球分布、分层协作**的巨型数据库。

**关键点**：DNS 不是一个中心服务器，而是**成千上万台服务器分层协作**的结果。

### 9.2 域名的层级结构

```
                     .（根域）
                     │
        ┌────────────┼────────────┐
       com          org          cn        ← 顶级域（TLD）
        │
    ┌───┴───┐
  baidu   google                            ← 二级域
    │
  ┌─┴──┐
 www  map                                   ← 主机名/子域

完整域名（FQDN）：www.baidu.com.
（最后那个点代表根域，平时省略）
```

> 💡 **术语解释｜FQDN（Fully Qualified Domain Name，完全限定域名）**
> 从主机名一路写到根域的完整名称，如 `www.baidu.com.`。末尾的点表示根。

**域名从右往左读**，范围从大到小：
`www.baidu.com` → `com`（商业顶级域）→ `baidu`（百度）→ `www`（具体主机）。

### 9.3 DNS 查询过程：递归 vs 迭代

> 💡 **术语解释｜递归查询（Recursive Query）**
> **"你帮我查到底。"** 客户端只问一次本地 DNS 服务器，服务器负责把最终答案拿回来。**客户端 ↔ 本地 DNS 之间是递归查询。**

> 💡 **术语解释｜迭代查询（Iterative Query）**
> **"你告诉我下一步该问谁。"** 被问的服务器如果不知道答案，就返回"去找 XX"。**本地 DNS ↔ 各级权威服务器之间是迭代查询。**

**完整解析过程（以 `www.example.com` 为例）：**

```
① 用户输入 www.example.com
   │
② 查浏览器缓存 → 系统 hosts 文件 → 本地 DNS 缓存
   │（都没有）
   ▼
③ 客户端 → 本地 DNS 服务器（递归："帮我查到底"）
   │
④ 本地 DNS → 根域名服务器（迭代）
   │  ◀── "我不知道，但 .com 的服务器地址是…"
   │
⑤ 本地 DNS → .com 顶级域服务器
   │  ◀── "我不知道，但 example.com 的服务器地址是…"
   │
⑥ 本地 DNS → example.com 权威服务器
   │  ◀── "www.example.com 的 IP 是 93.184.216.34"
   │
⑦ 本地 DNS 缓存结果（按 TTL）并返回给客户端
   │
⑧ 客户端拿到 IP，发起 TCP 连接
```

> 📌 **记忆**：**客户端对本地 DNS 是"递归"（要结果），本地 DNS 对各级服务器是"迭代"（要线索）。**

> 💡 **术语解释｜DNS 缓存与 TTL**
> 每级都会缓存查询结果，**缓存时长由记录的 TTL（Time To Live）决定**。
>
> - TTL 大 → 查询快、但域名变更后生效慢
> - TTL 小 → 变更生效快、但查询压力大
>
> **常见缓存层级**：浏览器缓存 → 操作系统缓存 → hosts 文件 → 本地 DNS 缓存 → 各级服务器缓存。
>
> 📌 **改域名后不生效？** 十有八九是**各级缓存还没过期**。等 TTL 到期，或清本地 DNS 缓存（Windows：`ipconfig /flushdns`；macOS：`sudo dscacheutil -flushcache`）。

### 9.4 DNS 记录类型

| 记录类型 | 全称 | 作用 | 示例 |
|---|---|---|---|
| **A** | Address | 域名 → IPv4 地址 | `www.example.com → 93.184.216.34` |
| **AAAA** | Address (IPv6) | 域名 → IPv6 地址 | `www.example.com → 2606:2800:...` |
| **CNAME** | Canonical Name | 域名别名 | `www.example.com → example.com` |
| **MX** | Mail Exchange | 邮件服务器（带优先级） | `example.com → mail.example.com (10)` |
| **NS** | Name Server | 该域的权威 DNS 服务器 | `example.com → ns1.example.com` |
| **TXT** | Text | 文本记录，常用于邮件安全验证 | SPF / DKIM / DMARC |
| **PTR** | Pointer | **反向解析**：IP → 域名 | `93.184.216.34 → www.example.com` |
| **SOA** | Start of Authority | 区域权威起始记录（管理信息） | 主 NS、管理员邮箱、序列号 |
| **SRV** | Service | 指定服务的主机与端口 | `_sip._tcp.example.com` |
| **CAA** | Certification Authority Authorization | 指定哪些 CA 可为本域签证书 | 防误签 |

> 💡 **术语解释｜CNAME 的作用与限制**
> CNAME 让一个域名"指向"另一个域名。**典型用途**：把 `www.example.com` 指向 CDN 提供的域名，这样 CDN 换 IP 时你无需改动。
>
> ⚠️ **限制**：CNAME 不能和 MX、NS 等其他记录共存于同一名称（因为 CNAME 是"别名"，不能再定义其他类型）。

> 💡 **术语解释｜TXT 记录与邮件安全三件套**
> TXT 记录常用来存**邮件防伪**信息：
> - **SPF**：声明哪些 IP 有权代表本域发邮件
> - **DKIM**：用签名验证邮件未被篡改
> - **DMARC**：规定 SPF/DKIM 失败时怎么处理（拒绝/隔离）
>
> **三者配合，能大幅减少"伪造你域名发垃圾邮件"的问题。**

### 9.5 DNS 的安全与隐私

| 威胁 | 说明 | 防御 |
|---|---|---|
| **DNS 劫持** | 篡改解析结果，把你导向钓鱼站 | DNSSEC、使用可信 DNS |
| **DNS 缓存投毒** | 污染 DNS 缓存，让大量用户被误导 | DNSSEC、随机化查询 ID/端口 |
| **DNS 欺骗** | 伪造 DNS 响应 | DNSSEC |
| **DNS 监听** | 运营商/中间人能看到你访问哪些域名 | DoH / DoT |

> 💡 **术语解释｜DNSSEC（DNS Security Extensions）**
> 给 DNS 记录**加数字签名**，让客户端能验证"这个解析结果确实来自权威服务器，且未被篡改"。
>
> **关键记录**：`RRSIG`（签名）、`DNSKEY`（公钥）、`DS`（委派签名，连接父子域）。**注意：DNSSEC 只保证"不被篡改"，不保证"不被看到"（不加密）。**

> 💡 **术语解释｜DoH / DoT**
> - **DoH（DNS over HTTPS）**：把 DNS 查询封装在 HTTPS 里（走 443 端口），**看起来和普通网页流量一样**，难被识别和阻断
> - **DoT（DNS over TLS）**：用 TLS 加密 DNS（走 853 端口），**端口固定，易被识别**
>
> 两者都能**防止 DNS 查询被监听**，保护隐私。

### 9.6 常用 DNS 工具

```bash
# 查询 A 记录
nslookup www.example.com
dig www.example.com A

# 查询指定类型
dig example.com MX
dig example.com TXT

# 追踪完整解析过程（从根开始迭代）
dig +trace www.example.com

# 指定 DNS 服务器查询
dig @8.8.8.8 www.example.com

# 反向解析（IP → 域名）
dig -x 93.184.216.34

# Windows 查看/刷新缓存
ipconfig /displaydns
ipconfig /flushdns
```

> 📌 **`dig +trace` 是学习 DNS 的神器**——它会**从根服务器开始，一步步展示迭代查询的全过程**，让你亲眼看到第 9.3 节的流程。

## 10. DHCP：让设备自动上线

### 10.1 为什么需要 DHCP

如果每台设备都要手动配 IP、子网掩码、网关、DNS——**在几十台设备的公司还行，在星巴克、机场、你家 WiFi 里根本不可能**。

> 💡 **术语解释｜DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）**
> 自动给网络中的设备**分配 IP 地址、子网掩码、默认网关、DNS 服务器**等参数。运行在 **UDP 67（服务器）/ 68（客户端）端口**。

**DHCP 能下发哪些参数？**

| 参数 | 说明 |
|---|---|
| IP 地址 | 核心，动态分配 |
| 子网掩码 | 判断网络范围 |
| 默认网关 | 出网的门 |
| DNS 服务器 | 域名解析 |
| 租约时间 | 多久后需要续约 |
| 其他（Option 43/66/67…） | 厂商自定义（如无线 AP 地址） |

### 10.2 DORA 四步交互

> 💡 **术语解释｜DORA**
> DHCP 获取地址的四个步骤：**D**iscover → **O**ffer → **R**equest → **A**CK。

```
客户端（0.0.0.0）                          DHCP 服务器
  │                                            │
  │ ① DHCP Discover ──────────────────────────▶ │  （广播）
  │    源 IP: 0.0.0.0（我还没 IP）              │   目的: 255.255.255.255
  │    目的: 255.255.255.255                   │   "有没有 DHCP 服务器？"
  │                                            │
  │ ◀────────────── ② DHCP Offer ───────────── │  （可单播/广播）
  │    "这个 IP 给你用（如 192.168.1.100）"      │
  │                                            │
  │ ③ DHCP Request ───────────────────────────▶ │  （广播）
  │    "我就要 192.168.1.100 这个！"             │   （Option 54 指明服务器）
  │                                            │
  │ ◀────────────── ④ DHCP ACK ─────────────── │
  │    "确认，地址归你了，附带网关/DNS/租期"      │
  │                                            │
  │ ⑤ 客户端配置好 IP，网络可用                   │
```

> ⚠️ **为什么 Discover 要用广播、源 IP 是 0.0.0.0？**
> 因为客户端**还没有 IP**，也不知道 DHCP 服务器在哪，只能"喊一嗓子"（广播）。源 IP 用 `0.0.0.0` 表示"我暂时没地址"。

> ⚠️ **为什么 Request 也要广播？**
> 因为可能**有多台 DHCP 服务器**都发了 Offer，客户端选定一台后，需要**广播告知所有服务器"我选了谁"**，让其他服务器收回它们的 Offer。

> 💡 **术语解释｜DHCP NAK（Negative Acknowledgment）**
> 如果服务器拒绝客户端的 Request（如请求的 IP 已被占用），会返回 **DHCP NAK**，客户端必须**重新从 Discover 开始**。

### 10.3 租约与续约

> 💡 **术语解释｜租约（Lease）**
> DHCP 分配的 IP 是**"租"的，不是"给"的**。到期要续约，否则 IP 会被回收给其他设备。

**两个关键计时器：**

| 计时器 | 触发时间 | 动作 |
|---|---|---|
| **T1** | 租期的 **50%** | **单播**向原服务器请求续约（DHCP Request） |
| **T2** | 租期的 **87.5%** | 原服务器没响应，**广播**向任意服务器请求续约 |
| 到期 | 租期 **100%** | 停止使用该 IP，重新 DORA |

```
租期 = 24 小时
  0h ────────── 12h ────────── 21h ────────── 24h
                T1(50%)        T2(87.5%)      到期
             单播续约        广播续约       重新 DORA
```

> 📌 **实用价值**：**为什么换网络后 IP 有时还"记得"旧地址？** 因为租约未到期且设备会尝试续约。**想立即重新获取**：`ipconfig /release`（释放）再 `ipconfig /renew`（重新申请）。

### 10.4 无 DHCP 时的自分配：APIPA

> 💡 **术语解释｜APIPA（Automatic Private IP Addressing，自动专用 IP 寻址）**
> 当设备**拿不到 DHCP 响应**时，Windows 会自动给自己配一个 **169.254.x.x**（169.254.0.0/16）的地址。
>
> **典型症状**：`ipconfig` 看到 `169.254.x.x` → **说明 DHCP 失败**（网线没插好、DHCP 服务器挂了、VLAN 配错）。

> ⚠️ **排查口诀**：**看到 169.254 开头的 IP，先查 DHCP 链路，别去查别的。**

### 10.5 DHCP 中继：跨网段分配

**问题**：DHCP 的 Discover 是**广播**，而**路由器默认不转发广播**。那跨网段的客户端怎么拿到 IP？

**答案**：**DHCP 中继（DHCP Relay）。**

> 💡 **术语解释｜DHCP 中继（DHCP Relay Agent）**
> 路由器/三层交换机上的功能：把**本网段的 DHCP 广播**转换成**单播**，转发给**另一个网段的 DHCP 服务器**，再把响应转回来。
>
> **关键字段**：中继在转发时，会把**接收接口的 IP 填进 `GIADDR`（Gateway IP Address）字段**，DHCP 服务器据此**判断客户端属于哪个网段，从而分配对应网段的地址池**。

```
客户端         中继（路由器）              DHCP 服务器（另一网段）
  │                │                          │
  │ Discover(广播)  │                          │
  │ ──────────────▶ │ 转成单播 + 填 GIADDR     │
  │                │ ────────────────────────▶ │
  │                │                          │ 按 GIADDR 选地址池
  │                │ ◀──────────────────────── │ Offer
  │ ◀────────────── │ 转回广播/单播             │
```

### 10.6 DHCP 的安全问题

| 威胁 | 说明 | 防御 |
|---|---|---|
| **私接 DHCP 服务器（Rogue DHCP）** | 攻击者架设假 DHCP，把网关/DNS 指向自己，实施中间人 | **DHCP Snooping** |
| **DHCP 饥饿攻击（Starvation）** | 攻击者伪造大量 MAC 地址，把地址池耗光，让正常用户拿不到 IP | **DHCP Snooping + 端口限速** |
| **DHCP 欺骗** | 伪造 DHCP 响应，篡改网关 | **DHCP Snooping** |

> 💡 **术语解释｜DHCP Snooping（DHCP 监听）**
> 交换机上的安全功能，把端口分为两类：
> - **信任端口（Trusted）**：连接**合法的 DHCP 服务器**或上行链路，允许 DHCP 响应通过
> - **非信任端口（Untrusted）**：连接**普通用户**，**丢弃**来自这些端口的 DHCP 响应（Offer/ACK）
>
> **效果**：私接的假 DHCP 服务器发出的响应会被丢弃 → 防御 Rogue DHCP 和欺骗。
>
> 同时它会**建立"IP-MAC-端口"绑定表**，供 DAI（动态 ARP 检测）等其他安全功能使用。

> 💡 **术语解释｜Option 字段**
> DHCP 报文里可携带大量可选参数（Option），常见：
>
> | Option | 用途 |
> |---|---|
> | 3 | 默认网关 |
> | 6 | DNS 服务器 |
> | 51 | 租约时间 |
> | 53 | 报文类型（Discover/Offer/Request/ACK） |
> | 54 | 服务器标识（Request 时指明选哪台） |
> | 55 | 参数请求列表 |
> | 66 / 67 | TFTP 服务器名 / 启动文件名（PXE 网络启动） |
> | 43 | 厂商特定信息（如无线 AP 地址） |

## 11. 其他常用应用层协议

### 11.1 FTP：文件传输

> 💡 **术语解释｜FTP（File Transfer Protocol）**
> 文件传输协议。**特点：使用两条 TCP 连接**——**控制连接（21 端口）** + **数据连接（20 端口或临时端口）**。

**两种模式：**

| 模式 | 谁发起数据连接 | 场景 |
|---|---|---|
| **主动模式（Active）** | **服务器**主动连客户端（服务器 20 → 客户端随机端口） | 客户端有公网 IP 时 |
| **被动模式（Passive）** | **客户端**主动连服务器（服务器开临时端口等连接） | **客户端在 NAT/防火墙后**（现代默认） |

> ⚠️ **主动模式的问题**：服务器从 20 端口主动连客户端，会被**客户端的防火墙/NAT 拦截**。所以**现代几乎都用被动模式**。

> 📌 **FTP 的替代者**：
> - **SFTP**：基于 SSH，加密，走 22 端口（**推荐**）
> - **FTPS**：FTP over TLS，加密
> - **TFTP**：简单文件传输，走 **UDP 69**，用于网络设备升级、PXE 启动

### 11.2 电子邮件协议：SMTP / POP3 / IMAP

**邮件发送与接收用了不同的协议：**

```
  发件人                    发件人邮件服务器            收件人邮件服务器              收件人
    │                            │                          │                        │
    │ ① SMTP ──────────────────▶ │ ② SMTP ────────────────▶ │                        │
    │  （发送/投递）              │  （服务器间转发）          │                        │
    │                            │                          │ ③ POP3/IMAP ◀────────── │
    │                            │                          │   （收件人拉取）          │
```

| 协议 | 端口 | 方向 | 作用 |
|---|---|---|---|
| **SMTP** | 25（明文）/ 587（提交）/ 465（SSL） | **发** | 发送邮件、服务器间投递 |
| **POP3** | 110 / 995（SSL） | **收** | **下载**邮件到本地，**默认从服务器删除** |
| **IMAP** | 143 / 993（SSL） | **收** | **同步**邮件，**邮件保留在服务器**，多设备一致 |

> 💡 **POP3 vs IMAP 一句话**：
> - **POP3**：把信"取回家"，服务器上就没了（**单设备**思维）
> - **IMAP**：信留在"邮局"，你在哪个设备看都一样（**多设备同步**，现代首选）

> ⚠️ **SMTP 的致命弱点**：**默认不加密、不验证发件人身份** → 这就是**垃圾邮件泛滥**的根源。所以有了 **SPF / DKIM / DMARC**（第 9.4 节的 TXT 记录）来给邮件"验明正身"。

### 11.3 WebSocket：真正的实时双向通信

**问题**：HTTP 是"一问一答"，服务器**不能主动推**消息。做聊天、实时行情怎么办？

**老办法（低效）**：
- **轮询（Polling）**：客户端每隔几秒问一次"有新消息吗？" → 大量无用请求
- **长轮询（Long Polling）**：服务器把请求"挂住"，有消息才返回 → 稍好，但仍要反复重建连接

**新办法：WebSocket。**

> 💡 **术语解释｜WebSocket**
> 在**一次 HTTP 握手之后**，把连接**升级**为**全双工、持久**的 TCP 连接。之后**双方可以随时主动发消息**，无需反复握手。
>
> **端口**：`ws://`（80）/ `wss://`（443，加密）。

**握手过程（基于 HTTP 升级）：**

```
客户端                                          服务器
  │  GET /chat HTTP/1.1                           │
  │  Host: example.com                            │
  │  Upgrade: websocket                           │
  │  Connection: Upgrade                          │
  │  Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==  │
  │  Sec-WebSocket-Version: 13 ─────────────────▶ │
  │                                               │ 计算 Accept 值
  │ ◀──────── 101 Switching Protocols ─────────── │
  │    Upgrade: websocket                         │
  │    Connection: Upgrade                        │
  │    Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYG...  │
  │                                               │
  │  === 之后连接升级为 WebSocket，全双工通信 ===   │
```

> 📌 **状态码 101** = `Switching Protocols`，表示"协议切换成功"。这就是 1xx 状态码最常见的用途。

> 💡 **WebSocket vs HTTP**：
> | 维度 | HTTP | WebSocket |
> |---|---|---|
> | 通信方向 | 请求-响应（半双工） | **全双工** |
> | 服务器主动推 | ❌ | ✅ |
> | 连接 | 每次请求可能新建 | 一次握手，长期保持 |
> | 头部开销 | 每次都有完整头部 | 帧头很小（2～14 字节） |
> | 适用 | 网页、API | 聊天、实时行情、协同编辑、游戏 |

### 11.4 CDN：把内容搬到用户身边

> 💡 **术语解释｜CDN（Content Delivery Network，内容分发网络）**
> 在全球部署大量**边缘节点**，把**静态资源（图片、视频、JS/CSS）缓存到离用户最近的节点**，用户就近获取，而不是每次回源站。

**CDN 如何工作（结合 DNS）：**

```
① 用户访问 www.example.com（该域名 CNAME 到 CDN）
② CDN 的智能 DNS 根据用户 IP 判断地理位置
③ 返回离用户最近的边缘节点 IP
④ 用户从边缘节点获取资源
   · 节点有缓存 → 直接返回（快）
   · 节点无缓存 → 回源站拉取，缓存后再返回
```

> 📌 **CDN 的价值**：
> - **降低延迟**（就近访问）
> - **减轻源站压力**（大部分请求被边缘节点消化）
> - **抗流量攻击**（分散流量、可清洗 DDoS）
> - **提高可用性**（某节点故障自动切换）

| **HPACK** | Header Compression for HTTP/2 | HTTP/2 头部压缩 | 压缩 HTTP/2 头部 |
| **QPACK** | Header Compression for HTTP/3 | HTTP/3 头部压缩 | 压缩 HTTP/3 头部 |

## 13. 常见误区

**误区 1：HTTP 和 HTTPS 的区别只是"加了个 S"**
✅ 正确理解：HTTPS 在 HTTP 与 TCP 之间加了 **TLS 层**，实现了**加密、身份认证、完整性校验**三件事。它不只是"加密"，还能防止中间人冒充服务器。

**误区 2：GET 和 POST 的区别就是"参数放 URL 还是放 body"**
✅ 正确理解：核心区别在**语义**——GET 是**幂等、安全**的读取，POST 是**非幂等**的提交。参数位置只是表现形式。GET 也可以有 body（少见），POST 也可以把参数放 URL。

**误区 3：JWT 的 Payload 是加密的，放敏感信息没关系**
✅ 正确理解：JWT 的 Payload 只是 **Base64URL 编码**，**任何人解码就能看到明文**。它保证的是"不可篡改"，不是"不可读"。**绝不能放密码、身份证号等敏感信息。**

**误区 4：`no-cache` 就是不缓存**
✅ 正确理解：`no-cache` 是**可以缓存，但每次用之前必须向服务器验证**；**完全不缓存**是 `no-store`。两者完全不同。

**误区 5：HTTP/2 已经完全解决了队头阻塞**
✅ 正确理解：HTTP/2 只解决了**应用层**队头阻塞。因为所有流共享**一条 TCP 连接**，**底层 TCP 一丢包，所有流都会被阻塞**。这个"传输层队头阻塞"要靠 **HTTP/3（QUIC）** 解决。

**误区 6：证书就是用来加密的**
✅ 正确理解：**证书本身不加密任何数据**。它的作用是**身份背书**——证明"这个公钥确实属于这个域名"。加密是 TLS 握手协商出的会话密钥干的活。

**误区 7：看到 `169.254.x.x` 是 IP 冲突**
✅ 正确理解：`169.254.x.x` 是 **APIPA 地址**，表示**没拿到 DHCP**。应排查 DHCP 链路（网线、DHCP 服务器、VLAN 配置），而不是查冲突。

**误区 8：DNS 查询全程都是递归**
✅ 正确理解：**客户端到本地 DNS 是递归**（要最终结果），**本地 DNS 到各级权威服务器是迭代**（要线索）。两者角色不同。

**误区 9：HTTP/1.1 的域名分片、资源合并是好习惯**
✅ 正确理解：这些是**被队头阻塞逼出来的优化手段**。在 HTTP/2/3 时代，**多路复用让它们变成反模式**——分片会破坏连接复用，合并会导致缓存粒度变粗。

**误区 10：HTTPS 就一定安全**
✅ 正确理解：HTTPS 保证**传输安全**，但**不保证网站本身可信**。钓鱼网站也能申请证书（用真证书骗你输入密码）。看到小锁 ≠ 网站可信，还要看**域名是否正确**。

### 任务 4：手工搭一个 HTTPS 服务并观察证书

```bash

```

### 任务 5：用 Python 观察 Cookie 与 HTTP 请求

```python
import requests

# 会话对象会自动管理 Cookie
s = requests.Session()

# 访问会 Set-Cookie 的网站
r = s.get('https://www.baidu.com')
print("=== 响应头中的 Set-Cookie ===")
for k, v in r.headers.items():
    if 'ookie' in k or 'ookie' in v.lower():
        print(f"{k}: {v}")

print("\n=== 会话中保存的 Cookie ===")
for cookie in s.cookies:
    print(f"{cookie.name} = {cookie.value}")
    print(f"  domain={cookie.domain}, path={cookie.path}")
    print(f"  expires={cookie.expires}, secure={cookie.secure}")

print(f"\n=== 状态码: {r.status_code} ===")
print(f"=== Content-Type: {r.headers.get('Content-Type')} ===")
print(f"=== Server: {r.headers.get('Server')} ===")
```

**观察要点**：
- `Session` 自动保存和携带 Cookie 的机制
- Cookie 的 domain/path/secure 等属性
- 响应头里的 Server、Content-Type 等字段
