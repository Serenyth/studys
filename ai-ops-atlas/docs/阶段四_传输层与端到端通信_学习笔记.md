## 1. 传输层到底在解决什么问题

### 1.1 从网络层的"甩锅"说起

阶段三提到，IP 协议是**"尽力而为（Best Effort）"**的——它只承诺"我会努力送到"，但不承诺：

- ❌ 不保证送达（可能丢包）
- ❌ 不保证顺序（可能乱序）
- ❌ 不保证不重复
- ❌ 不保证不出错

**为什么 IP 要这么"不负责任"？** 因为这是刻意的设计选择：**把复杂性推给需要它的上层。** 看视频丢一帧无所谓，但传文件丢一个字节就全废了。让 IP 保持简单，上层按需选择——这才是互联网能扩展的原因。

**那么问题来了：**

> 数据包到了对端主机，但一台主机上同时开着浏览器、微信、邮件客户端、游戏……**系统怎么知道这个包该交给哪个程序？**

> 如果丢了包、顺序乱了，**谁来负责重传和排序？**

**这就是传输层要解决的两个核心问题：进程寻址 + 可靠性（可选）。**

### 1.2 传输层的两大核心功能

| 功能 | 说明 |
|---|---|
| **复用（Multiplexing）** | 发送方：多个应用进程的数据，都通过传输层封装后交给 IP 层发送 |
| **分用（Demultiplexing）** | 接收方：传输层根据端口号，把数据交付给正确的应用进程 |

> 💡 **术语解释｜复用与分用**
> - **复用**是"多合一"：多个应用的数据汇到一条 IP 通道上发出
> - **分用**是"一拆多"：收到的数据按端口号分发给对应应用
> - 这两个功能都靠**端口号**实现。

### 1.3 端口号：进程的"门牌号"

> 💡 **术语解释｜端口号（Port Number）**
> 一个 **16 位**无符号整数，范围 **0～65535**。用来标识一台主机上的**具体应用程序**。
>
> **类比**：IP 地址是"小区地址"，端口号是"门牌号"。数据先靠 IP 找到小区，再靠端口号找到具体的门。

**关键点：端口号是"进程"的标识，不是"设备"的标识。**

同一台服务器上：
- Nginx 监听 80 端口
- SSH 服务监听 22 端口
- MySQL 监听 3306 端口

数据包到达时，操作系统根据**目的端口号**把数据交给对应的进程。

### 1.4 套接字 Socket 与四元组

> 💡 **术语解释｜套接字（Socket）**
> 网络编程中的抽象概念，是"IP 地址 + 端口号"的组合。它是应用程序与网络协议栈之间的接口。

> 💡 **术语解释｜四元组（Four-Tuple）**
> 唯一标识一条 TCP 连接的四要素：**（源 IP，源端口，目的 IP，目的端口）**。
>
> **任意一个元素不同，就是不同的连接。** 这就是为什么同一台服务器能同时处理成千上万个客户端连接——它们的四元组各不相同。

**示例：**

```
连接 1：192.168.1.10:50001  →  93.184.216.34:443
连接 2：192.168.1.10:50002  →  93.184.216.34:443
连接 3：192.168.1.11:50001  →  93.184.216.34:443
```

这三条连接**目的 IP 和端口相同**，但源端口（或源 IP）不同，所以服务器能把它们区分开。

> 💡 **术语解释｜五元组**
> 四元组 + **协议号**（TCP=6 / UDP=17）。在防火墙规则、云安全组里常用五元组来定义规则。

### 1.5 传输层的两大协议

| 协议 | 全称 | 定位 |
|---|---|---|
| **TCP** | Transmission Control Protocol，传输控制协议 | **可靠**、面向连接、面向字节流 |
| **UDP** | User Datagram Protocol，用户数据报协议 | **不可靠**、无连接、面向报文 |

**一句话对比：TCP 是"挂号信"（有确认、可追踪），UDP 是"平信"（丢了自己负责）。**

## 2. 端口号详解

### 2.1 端口分类

IANA 把 0～65535 分成三段：

| 类型 | 范围 | 说明 | 例子 |
|---|---|---|---|
| **知名端口**（Well-Known Ports） | **0 ～ 1023** | IANA 统一分配给标准服务，**普通用户程序无法占用** | 80（HTTP）、443（HTTPS）、22（SSH） |
| **注册端口**（Registered Ports） | **1024 ～ 49151** | 用户程序向 IANA 注册后使用 | 3306（MySQL）、8080（Tomcat） |
| **动态端口 / 私有端口**（Dynamic/Private Ports） | **49152 ～ 65535** | **客户端临时使用**，用完释放 | 浏览器访问网站时的源端口 |

> ⚠️ **两个容易混的点**：
> 1. **服务端用的是知名端口或注册端口**（固定监听，如 80、3306）
> 2. **客户端用的是动态端口**（每次连接随机分配，如 50001）
>
> 所以一条连接的两端端口号"性质"不同——一边是固定的服务端口，一边是随机的客户端端口。

### 2.3 查看端口占用的命令

```bash
# Windows
netstat -ano | findstr :80          # 查看 80 端口被哪个 PID 占用
netstat -ano | findstr LISTENING    # 查看所有监听端口
tasklist | findstr <PID>            # 根据 PID 找进程名

# Linux
netstat -tunlp                      # 查看所有 TCP/UDP 监听端口（需 root）
ss -tunlp                           # 更现代的替代品，速度快
lsof -i :80                         # 查看 80 端口被谁占用
```

> 💡 **术语解释｜netstat vs ss**
> `netstat` 是传统工具，通过读取 `/proc` 文件系统获取信息，**连接数多时非常慢**。`ss`（Socket Statistics）是新一代工具，直接从内核获取信息，**速度快得多**。现代 Linux 建议用 `ss`。

## 3. UDP：简单直接

### 3.1 UDP 首部（仅 8 字节）

UDP 首部极其简单，只有 **4 个字段、共 8 字节**：

```
┌──────────────────┬──────────────────┐
│   源端口(16位)    │   目的端口(16位)  │
├──────────────────┼──────────────────┤
│   长度(16位)      │   校验和(16位)    │
└──────────────────┴──────────────────┘
```

| 字段 | 位数 | 作用 |
|---|---|---|
| **源端口** | 16 | 发送方端口（可省略，用全 0 表示不需要回复） |
| **目的端口** | 16 | 接收方端口 |
| **长度** | 16 | **首部 + 数据**的总长度，最小值 8（只有首部） |
| **校验和** | 16 | 校验首部和数据（IPv4 中可选，IPv6 中必选） |

**对比 TCP 的 20 字节首部，UDP 只有 8 字节——这就是它"轻量"的根源。**

### 3.2 UDP 的四大特性

| 特性 | 说明 |
|---|---|
| **无连接** | 不需要握手，直接发。省掉了建连的 1 个 RTT |
| **不可靠** | 不确认、不重传、不排序。丢了就丢了 |
| **面向报文** | 应用层给一个报文，UDP 原样发出去，**不合并也不拆分** |
| **无流量/拥塞控制** | 想发多快就发多快，不管网络承不承受得住 |

> 💡 **术语解释｜面向报文（Message-Oriented）**
> UDP 把应用层交下来的数据**整体**作为一个报文发送，**保留边界**。
> 应用层给 100 字节，UDP 就发一个 100 字节的包；给 1000 字节，就发一个 1000 字节的包。
> **所以 UDP 不会出现"粘包"问题**——每个包自带边界。

### 3.3 UDP 的适用场景

UDP 的"缺点"在某些场景恰恰是优点：

| 场景 | 为什么用 UDP |
|---|---|
| **DNS 查询** | 一问一答，数据量小。用 TCP 建连的开销比查询本身还大 |
| **实时音视频** | 丢一帧无所谓，重传反而造成卡顿。**延迟比完整性重要** |
| **在线游戏** | 位置信息必须最新，重传旧位置毫无意义 |
| **DHCP** | 客户端还没有 IP，无法建立 TCP 连接 |
| **SNMP 网络管理** | 周期性查询，简单快速 |
| **QUIC / HTTP/3** | 在 UDP 上**自己实现**可靠传输和拥塞控制，避开 TCP 的队头阻塞 |

> 💡 **术语解释｜队头阻塞（Head-of-Line Blocking, HOL）**
> TCP 要求数据**严格按序交付**。如果前面的包丢了，后面收到的包必须等前面的重传到了才能交给应用层——**即使后面的数据早就到了**。
> 在 HTTP/2 多路复用下，这个问题尤其严重：一个包丢了，所有流都被堵住。**HTTP/3 改用 UDP 就是为了绕开这个限制。**

### 3.4 UDP 的"不可靠"不等于"没用"

**关键认知**：可靠性可以**由应用层自己实现**。

比如 QUIC（HTTP/3 的传输层）就在 UDP 之上实现了：
- 自己的序号与确认机制
- 自己的重传逻辑
- 自己的拥塞控制
- 还顺手加上了 TLS 加密

**好处**：可以针对具体场景优化，不受 TCP 内核实现的限制；而且**改协议不用改内核**，升级容易。

## 4. TCP 报文段结构

### 4.1 首部结构总览

TCP 首部**固定部分 20 字节**，加上选项**最多 60 字节**。

```
┌──────────────┬──────────────┬────────────────────────────┐
│ 源端口(16位) │ 目的端口(16位)│                            │
├─────────────────────────────┴────────────────────────────┤
│                    序号 Sequence Number (32位)             │
├──────────────────────────────────────────────────────────┤
│                 确认号 Acknowledgment (32位)               │
├────────┬──────┬──────────┬───────────────────────────────┤
│数据偏移 │ 保留 │  标志位   │        窗口 Window (16位)      │
│ (4位)  │(6位) │  (6位)   │                               │
├────────┴──────┴──────────┴───────────────────────────────┤
│      校验和(16位)      │      紧急指针(16位)               │
├──────────────────────────────────────────────────────────┤
│              选项 Options（0～40 字节）                    │
└──────────────────────────────────────────────────────────┘
```

> 📌 **注意**：第 4 行的字段布局是"数据偏移(4位) + 保留(6位) + 标志位(6位) + 窗口(16位)"，加起来正好 32 位。**别记错顺序。**

### 4.2 逐字段详解

| 字段 | 位数 | 作用 |
|---|---|---|
| **源端口** | 16 | 发送方端口 |
| **目的端口** | 16 | 接收方端口 |
| **序号（Seq）** | 32 | **本报文段数据第一个字节的序号** |
| **确认号（Ack）** | 32 | **期望收到的下一个字节的序号**（表示它之前的数据都收到了） |
| **数据偏移** | 4 | 首部长度，**单位是 4 字节**。最小 5（20 字节），最大 15（60 字节） |
| **保留** | 6 | 保留待用，置 0 |
| **标志位** | 6 | URG / ACK / PSH / RST / SYN / FIN |
| **窗口（Window）** | 16 | **接收窗口大小**，告诉对方"我还能收多少字节" |
| **校验和** | 16 | 校验首部 + 数据（要加 12 字节伪首部） |
| **紧急指针** | 16 | 指出紧急数据的末尾位置，配合 URG 使用 |
| **选项** | 可变 | MSS、窗口扩大、时间戳、SACK 等 |

> ⚠️ **最容易搞混的两个字段**：
> - **序号（Seq）**：我这一包数据的**第一个字节**的编号 → "我发到哪了"
> - **确认号（Ack）**：我**期望收到**的下一个字节编号 → "我收到哪了，接下来要哪个"
>
> **关键**：确认号是"下一个期望值"，不是"最后收到的值"。所以确认号 = 最后收到的字节序号 + 1。

### 4.3 六个标志位

| 标志 | 全称 | 含义 | 何时置 1 |
|---|---|---|---|
| **URG** | Urgent | 紧急指针有效 | 有紧急数据要优先处理 |
| **ACK** | Acknowledgment | **确认号有效** | 连接建立后，**所有报文都置 1** |
| **PSH** | Push | 推送，要求接收方**立即交付**应用层 | 交互式应用（如 SSH） |
| **RST** | Reset | **复位连接**，表示严重错误 | 拒绝连接、异常中断 |
| **SYN** | Synchronize | **同步序号，请求建立连接** | 三次握手的前两次 |
| **FIN** | Finish | **结束，请求释放连接** | 四次挥手 |

> 💡 **术语解释｜RST（复位）**
> 当 TCP 收到一个"不属于任何已建立连接"的报文时，会回一个 RST。常见场景：
> - 连接已关闭，对方还在发数据
> - 端口没有服务监听
> - 防火墙主动阻断连接
> **排障时看到大量 RST，通常意味着连接被拒绝或异常中断。**

> 💡 **术语解释｜PSH（推送）**
> 正常情况下 TCP 会缓冲数据，攒够一定量再交给应用层。PSH=1 表示"别等了，立即交付"。
> SSH、Telnet 这类交互式应用会置 PSH，让用户的每次按键立刻生效。

### 4.4 常用选项字段

| 选项 | 作用 |
|---|---|
| **MSS** | 最大报文段长度，**只表示数据字段的最大长度**（不含 TCP 首部）。以太网典型值 1460 |
| **窗口扩大（Window Scale）** | 16 位窗口最大只有 65535，高带宽高延迟场景不够用。该选项把窗口值**左移**若干位，最大可放大到 2³⁰ |
| **时间戳（Timestamp）** | 用于精确计算 RTT、防止序号回绕 |
| **SACK** | 选择性确认，告诉对方"我收到了哪些不连续的段" |

> 💡 **术语解释｜窗口扩大选项为什么必要**
> 假设链路带宽 1 Gbps、RTT 100 ms。按"时延带宽积"算，链路上同时在飞的数据量是：
> `1 Gbps × 0.1 s = 100 Mbit = 12.5 MB`
> 而 16 位窗口最大只有 **65535 字节 ≈ 64 KB**，**远远填不满这条链路**。
> 所以需要窗口扩大选项，把窗口放大到能覆盖链路容量。**这是长肥管道（LFN）性能优化的关键。**

## 5. TCP 的可靠传输机制

TCP 实现"可靠"靠的是四套机制的组合：**序号 + 确认 + 重传 + 校验和**。

### 5.1 面向字节流：序号与确认号

> 💡 **术语解释｜面向字节流（Byte-Stream Oriented）**
> TCP **把应用层的数据看成一连串无结构的字节**，不保留任何"消息边界"。
> 应用层发 3 次 100 字节，TCP 可能合成 1 个 300 字节的段发出，也可能拆成 6 个 50 字节的段。**应用层无法感知发送方的切分方式。**

**关键机制：TCP 为每一个字节编号，而不是为每一个报文段编号。**

```
应用层数据：1000 字节
TCP 编号：  0 ~ 999

假设分成 3 段发送：
段 1：序号 = 0，   数据 = 字节 0~399   （400 字节）
段 2：序号 = 400， 数据 = 字节 400~799 （400 字节）
段 3：序号 = 800， 数据 = 字节 800~999 （200 字节）
```

**接收方回复的确认号：**

```
收到段 1（0~399）   → 回 ACK = 400   （期望下一个是 400）
收到段 2（400~799） → 回 ACK = 800
收到段 3（800~999） → 回 ACK = 1000
```

> ⚠️ **重要细节**：**SYN 和 FIN 各消耗一个序号**。
> 三次握手时，客户端发 `SYN, seq=x`，服务器回 `ack=x+1`——因为 SYN 占用了序号 x。这是考试常考的点。

### 5.2 累计确认

> 💡 **术语解释｜累计确认（Cumulative Acknowledgment）**
> 确认号 `N` 表示"**N 之前的所有字节我都收到了**"，而不是"我只收到了第 N 个字节"。

**示例：**

```
发送方发出：段1(0~99)、段2(100~199)、段3(200~299)

情况 A：三个都收到 → 回 ACK = 300

情况 B：段2 丢了 → 接收方收到段1 和 段3
        段3 到了，但不能确认（因为 100~199 还缺）
        → 接收方仍然回 ACK = 100（重复确认）
        → 发送方看到重复 ACK，知道段2 丢了
```

**累计确认的优点**：即使某个 ACK 丢了，后面的 ACK 也能覆盖它，不必重传。
**缺点**：一次只能告诉对方"我连续收到哪了"，无法表达"我收到了 200~299 但缺 100~199"——这就是 SACK 要解决的问题。

### 5.3 超时重传与 RTO 计算

> 💡 **术语解释｜RTO（Retransmission Timeout，重传超时时间）**
> 发送方发出数据后启动一个计时器。如果在 RTO 时间内没收到 ACK，就认为数据丢了，重传。

**RTO 必须动态计算**，因为它取决于网络状况：

- **RTO 太短** → 数据其实没丢，却触发无谓重传 → 加剧拥塞
- **RTO 太长** → 真丢了也要等很久才重传 → 响应慢

**Jacobson / Karels 算法（经典 RTO 计算）：**

```
1. 测量 RTT 得到 SampleRTT

2. 计算平滑往返时间 SRTT（加权移动平均）：
   SRTT = (1 − α) × SRTT + α × SampleRTT      （α = 1/8）

3. 计算 RTT 偏差 RTTVAR：
   RTTVAR = (1 − β) × RTTVAR + β × |SRTT − SampleRTT|   （β = 1/4）

4. 计算 RTO：
   RTO = SRTT + 4 × RTTVAR
```

**直观理解**：RTO = "平均往返时间" + "4 倍的波动幅度"。**网络越不稳定（波动越大），RTO 就越大。**

> 💡 **术语解释｜Karn 算法**
> **重传的报文段不参与 RTT 计算。**
> 为什么？因为如果重传了，你不知道收到的 ACK 是对原始报文还是对重传报文的确认——算出来的 RTT 会是错的（可能是原始报文的 RTT，也可能是重传后的 RTT）。
> **解决方案**：重传的段不算 RTT；但每重传一次就把 RTO 翻倍（指数退避）。

### 5.4 快速重传

**超时重传的问题是"慢"**——必须等 RTO 超时，可能是几百毫秒甚至几秒。

**快速重传的思路**：接收方发现中间有洞时，会**反复发送同一个 ACK**。发送方收到 **3 个重复 ACK（duplicate ACK）**，就立即重传，不等超时。

**示例：**

```
发送方发出：段1(1~1000)、段2(1001~2000)、段3(2001~3000)、段4(3001~4000)

段2 丢失，段3、段4 正常到达

接收方：
  收到段1 → 回 ACK = 1001
  收到段3 → 缺段2，仍回 ACK = 1001   ← 重复 ACK #1
  收到段4 → 缺段2，仍回 ACK = 1001   ← 重复 ACK #2
  （再收到一个后续段）              ← 重复 ACK #3

发送方：连续收到 3 个 ACK=1001 → 立即重传段2（不等 RTO 超时）
```

> 💡 **为什么是"3 个"重复 ACK？**
> 因为网络可能出现**乱序**（段3 比段2 先到）。如果只等 1 个重复 ACK 就重传，可能误判。**等 3 个能过滤掉大部分乱序情况，同时又能快速响应真正的丢包。**

### 5.5 SACK 与 D-SACK

**SACK（选择性确认）**：

累计确认只能告诉对方"我连续收到哪了"。如果丢的是中间的段，发送方不知道该重传哪一段，**可能把丢包之后的所有段都重传一遍**（浪费带宽）。

SACK 允许接收方明确告诉发送方：**"我收到了哪些不连续的段。"**

```
接收方通过 SACK 选项告知：
  "我已经收到了 2001~3000 和 3001~4000，缺 1001~2000"

发送方：只重传 1001~2000，不用重传后面的 ✓
```

> 📌 **SACK 需要双方都支持**，通过握手时的选项协商。现代操作系统基本默认开启。

**D-SACK（Duplicate SACK）**：SACK 的扩展，用于告诉发送方"**你重传的这个包我早就收到了**"。

**用途**：帮助发送方判断网络异常类型。比如发现大量 D-SACK，说明发送方的 RTO 可能设得太短，导致不必要的重传。

### 5.6 校验和

TCP 校验和覆盖**首部 + 数据 + 12 字节伪首部**。

> 💡 **术语解释｜伪首部（Pseudo-Header）**
> 一个假的、只用于计算校验和的 12 字节结构，包含源 IP、目的 IP、协议号、TCP 长度。
> **为什么需要它？** 因为 TCP 校验和要能发现"数据包被送错了主机"这种错误——如果 IP 地址在传输中被改错，仅校验 TCP 首部和数据是发现不了的，加上伪首部就能覆盖到 IP 地址。

## 6. 三次握手与四次挥手

### 6.1 三次握手完整过程

```
        客户端                                    服务器
      (CLOSED)                                  (LISTEN)
          │                                         │
          │  ① SYN=1, seq=x                         │
          │────────────────────────────────────────→│
          │                                         │
      (SYN_SENT)                                (SYN_RCVD)
          │                                         │
          │  ② SYN=1, ACK=1, seq=y, ack=x+1         │
          │←────────────────────────────────────────│
          │                                         │
     (ESTABLISHED)                                  │
          │                                         │
          │  ③ ACK=1, seq=x+1, ack=y+1              │
          │────────────────────────────────────────→│
          │                                         │
          │                                    (ESTABLISHED)
          │                                         │
          │←──────────── 数据传输 ─────────────────→│
```

**逐次说明：**

| 次数 | 方向 | 报文 | 关键字段 | 状态变化 |
|---|---|---|---|---|
| ① | C → S | SYN | `SYN=1, seq=x` | C: CLOSED → **SYN_SENT** |
| ② | S → C | SYN+ACK | `SYN=1, ACK=1, seq=y, ack=x+1` | S: LISTEN → **SYN_RCVD**<br>C: SYN_SENT → **ESTABLISHED** |
| ③ | C → S | ACK | `ACK=1, seq=x+1, ack=y+1` | S: SYN_RCVD → **ESTABLISHED** |

> 💡 **为什么第二次要同时带 SYN 和 ACK？**
> 因为这是**双向的**：ACK 是对客户端 SYN 的确认，SYN 是服务器自己也请求同步序号。**这两件事可以合并成一个报文**，所以三次握手实际上只用了 3 个报文而不是 4 个。

### 6.2 为什么必须三次（不能两次）

**核心原因：防止"失效的连接请求"突然到达，导致服务器建立无效连接。**

**反例：假设只有两次握手**

```
1. 客户端发出 SYN（seq=x），但这个包在网络里滞留了很久
2. 客户端超时，重发 SYN，这次正常到达，连接建立、通信、关闭
3. 此时，那个滞留很久的旧 SYN 终于到达服务器

服务器视角：这是一个新的连接请求！
→ 回复 SYN+ACK 并直接进入 ESTABLISHED（两次握手的规则）
→ 服务器分配资源，等待客户端发数据

但客户端视角：我根本没发过这个请求，不理会
→ 服务器一直傻等，资源被白白占用 ✗
```

**有了第三次握手，服务器就能避免这个问题**：

服务器发完 SYN+ACK 后进入 `SYN_RCVD`，**必须等到客户端的 ACK 才算建立连接**。对于那个失效请求，客户端不会回 ACK，服务器等到超时就释放资源。✓

**三次握手的三个目的（面试常问）：**

1. **确认双方的收发能力**：
   - 客户端确认：我能发（①）、能收（②）、对方能收（①被响应）、对方能发（②）
   - 服务器确认：我能收（①）、能发（②）、对方能收（②被响应）、对方能发（③）
2. **协商初始序列号**：双方交换 ISN，为后续的可靠传输打基础
3. **防止历史失效连接请求**：上面说的场景

### 6.3 SYN 洪泛攻击（SYN Flood）

**攻击原理**：利用三次握手的"半开连接"状态。

```
攻击者伪造大量源 IP，向服务器发送大量 SYN 包
服务器为每个 SYN 分配资源、回复 SYN+ACK、进入 SYN_RCVD，等待第三次 ACK
但攻击者（或伪造的 IP）永远不回 ACK
→ 服务器的半连接队列被占满
→ 正常用户无法建立连接（拒绝服务）
```

**防御手段：**

| 手段 | 原理 |
|---|---|
| **SYN Cookie** | 服务器**不立即分配资源**，而是把连接信息编码进 SYN+ACK 的序号里。收到 ACK 后能验证出这是合法请求才分配资源 |
| **减少 SYN_RCVD 超时时间** | 让半开连接更快释放 |
| **增大半连接队列** | 治标 |
| **防火墙 / 抗 DDoS 设备** | 在边界拦截异常 SYN 流量 |

> 💡 **术语解释｜SYN Cookie**
> 服务器收到 SYN 时，**不保存任何状态**，而是用"源 IP、目的 IP、源端口、目的端口、时间戳"等信息经过哈希算出一个值，作为自己的初始序号（ISN）放进 SYN+ACK。
> 收到客户端的 ACK 后，服务器用同样算法再算一遍，验证 ACK 中的值是否匹配。**匹配才分配资源。**
> **好处**：服务器在握手完成前**不消耗任何存储**，SYN 洪泛就失效了。

### 6.4 四次挥手完整过程

```
        客户端                                    服务器
     (ESTABLISHED)                             (ESTABLISHED)
          │                                         │
          │  ① FIN=1, seq=u                         │
          │────────────────────────────────────────→│
          │                                         │
     (FIN_WAIT_1)                                (CLOSE_WAIT)
          │                                         │
          │  ② ACK=1, seq=v, ack=u+1                │
          │←────────────────────────────────────────│
          │                                         │
     (FIN_WAIT_2)                                     │
          │                                     （服务器继续发送剩余数据）
          │                                         │
          │  ③ FIN=1, ACK=1, seq=w, ack=u+1         │
          │←────────────────────────────────────────│
          │                                         │
     (TIME_WAIT)                                 (LAST_ACK)
          │                                         │
          │  ④ ACK=1, seq=u+1, ack=w+1              │
          │────────────────────────────────────────→│
          │                                         │
     （等 2MSL）                                  (CLOSED)
          │
      (CLOSED)
```

**逐次说明：**

| 次数 | 方向 | 报文 | 状态变化 |
|---|---|---|---|
| ① | C → S | FIN | C: ESTABLISHED → **FIN_WAIT_1**<br>S: ESTABLISHED → **CLOSE_WAIT** |
| ② | S → C | ACK | C: FIN_WAIT_1 → **FIN_WAIT_2** |
| ③ | S → C | FIN+ACK | S: CLOSE_WAIT → **LAST_ACK**<br>C: FIN_WAIT_2 → **TIME_WAIT** |
| ④ | C → S | ACK | S: LAST_ACK → **CLOSED**<br>C: TIME_WAIT →（等 2MSL）→ **CLOSED** |

### 6.5 为什么必须四次（不能三次）

**因为 TCP 是全双工的，关闭连接是"两个方向分别关闭"。**

```
第 ①② 次：客户端说"我发完了"（FIN），服务器说"知道了"（ACK）
           → 客户端 → 服务器 这个方向关闭

第 ③④ 次：服务器说"我也发完了"（FIN），客户端说"知道了"（ACK）
           → 服务器 → 客户端 这个方向关闭
```

**关键点**：服务器收到客户端的 FIN 后，**可能还有数据没发完**（比如网页还没传完）。所以它只能先回 ACK 表示"我知道你要关了"，等自己数据发完了再发 FIN。

**这就是 ② 和 ③ 不能合并的原因**——中间可能隔着很长一段"服务器继续发数据"的时间。

> 📌 **特殊情况**：如果服务器收到 FIN 时恰好也没有数据要发了，它可以把 ACK 和 FIN 合并成一个报文发（这时看起来像"三次挥手"）。但**理论上仍算四次挥手**，因为这是两个独立的动作恰好合并了。

### 6.6 TIME_WAIT 与 2MSL（重点）

**主动关闭方在发完最后一个 ACK 后，必须进入 TIME_WAIT 状态，等待 2MSL 才能彻底关闭。**

> 💡 **术语解释｜MSL（Maximum Segment Lifetime，报文最大生存时间）**
> 一个 TCP 报文在网络中能存活的最长时间。RFC 建议 **2 分钟**，Linux 实现中通常按 **60 秒** 处理。
> 所以 **2MSL 通常是 1～4 分钟**。

**TIME_WAIT 存在的两个原因：**

#### 原因一：确保最后一个 ACK 能到达服务器

```
如果第 ④ 次 ACK 丢失了：
  服务器会以为客户端没收到 FIN，重发第 ③ 次 FIN
  客户端还在 TIME_WAIT 状态 → 能重新发一次 ACK
  服务器收到后正常关闭 ✓

如果客户端发完 ACK 就立刻关闭：
  服务器重发的 FIN 到达时，客户端已经"不认识"这个连接了
  → 回一个 RST
  → 服务器收到 RST，认为连接异常 ✗
```

**2MSL 足够覆盖"服务器重发 FIN + 客户端重发 ACK"这个来回。**

#### 原因二：让本次连接的所有报文在网络中消失

```
如果不等 2MSL 就复用同样的四元组建立新连接：
  上一次连接的残留报文可能到达
  → 新连接会误以为这是自己的数据
  → 数据混乱 ✗

等 2MSL 后，旧连接的所有报文都已超时被网络丢弃
→ 新连接不会受到干扰 ✓
```

> ⚠️ **TIME_WAIT 是"正常且必要"的状态，不是 bug。** 服务器上看到几千个 TIME_WAIT 通常无需惊慌——它是协议设计的必然结果。**但如果数量异常大，就要检查是不是有大量短连接。**

### 6.7 CLOSE_WAIT 状态（要警惕）

**被动关闭方（服务器）在收到 FIN 后进入 CLOSE_WAIT，等待自己发 FIN。**

> ⚠️ **大量 CLOSE_WAIT 几乎一定是应用程序的 bug。**
>
> 因为 CLOSE_WAIT 的结束**只取决于应用层有没有调用 `close()`**。如果代码里忘了关闭 socket（比如异常路径没释放资源、连接池泄漏），连接就会一直卡在 CLOSE_WAIT，**且永远不会自动消失**。

**排查思路：**

```bash
# 统计各状态的连接数
netstat -n | awk '/^tcp/ {++S[$NF]} END {for(a in S) print a, S[a]}'

# 或
ss -s
```

**对比记忆：**

| 状态 | 出现在哪一方 | 是否正常 | 原因 |
|---|---|---|---|
| **TIME_WAIT** | **主动关闭方** | ✅ 正常 | 协议要求等 2MSL，会**自动消失** |
| **CLOSE_WAIT** | **被动关闭方** | ❌ **异常** | 应用层没调 `close()`，**不会自动消失** |

> 💡 **一句话记忆**：
> **TIME_WAIT 是"我关了，等一会儿"——正常，会自己好。**
> **CLOSE_WAIT 是"你关了，我没关"——异常，要改代码。**

### 6.8 TCP 的 11 种状态

| 状态 | 含义 |
|---|---|
| **CLOSED** | 初始状态，无连接 |
| **LISTEN** | 服务器监听中，等待连接请求 |
| **SYN_SENT** | 客户端已发 SYN，等待 SYN+ACK |
| **SYN_RCVD** | 服务器已收 SYN 并回 SYN+ACK，等待 ACK |
| **ESTABLISHED** | 连接已建立，可以传数据 |
| **FIN_WAIT_1** | 主动方已发 FIN，等待对方 ACK |
| **FIN_WAIT_2** | 主动方已收到 ACK，等待对方的 FIN（半关闭） |
| **CLOSE_WAIT** | 被动方已收到 FIN 并回 ACK，等待应用层关闭 |
| **CLOSING** | 双方同时发 FIN 的特殊状态（少见） |
| **LAST_ACK** | 被动方已发 FIN，等待最后一个 ACK |
| **TIME_WAIT** | 主动方等待 2MSL 后彻底关闭 |

**状态迁移全景图：**

```
                          ┌──────── CLOSED ────────┐
                          │                        │
              主动打开 connect()          被动打开 listen()
                          ↓                        ↓
                      SYN_SENT                  LISTEN
                          │                        │
                收到 SYN+ACK│              收到 SYN│
                          ↓                        ↓
                    ESTABLISHED ←──────────  SYN_RCVD
                          │                        │
              主动关闭 close()│             收到 FIN│
                          ↓                        ↓
                    FIN_WAIT_1                CLOSE_WAIT
                          │                        │
                收到 ACK  │              应用层 close()
                          ↓                        ↓
                    FIN_WAIT_2                LAST_ACK
                          │                        │
                收到 FIN  │                收到 ACK│
                          ↓                        ↓
                    TIME_WAIT                  CLOSED
                          │
                  等 2MSL  ↓
                       CLOSED
```

### 6.9 排查：连接状态异常

**排查命令：**

```bash
# 按状态统计连接数（最常用）
ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn

# 查看 TIME_WAIT 数量
netstat -an | grep TIME_WAIT | wc -l

# 查看 CLOSE_WAIT 数量
netstat -an | grep CLOSE_WAIT | wc -l

# 查看某个端口的状态分布
netstat -an | grep :80 | awk '{print $6}' | sort | uniq -c
```

**常见异常模式与原因：**

| 异常现象 | 根本原因 | 解决方向 |
|---|---|---|
| **大量 TIME_WAIT** | 大量短连接（如 HTTP 短连接、未启用 keep-alive） | 启用长连接、调优内核参数 |
| **大量 CLOSE_WAIT** | **应用程序未正确调用 `close()`**（连接泄漏） | **修代码**，检查异常路径和连接池 |
| **大量 SYN_RCVD** | 可能是 SYN 洪泛攻击 | 开启 SYN Cookie |
| **大量 SYN_SENT** | 对端不可达或被防火墙拦截 | 检查网络连通性和防火墙策略 |
| **大量 FIN_WAIT_2** | 对方不发送 FIN（可能是 bug 或异常关闭） | 缩短 `tcp_fin_timeout` |

**TIME_WAIT 过多的缓解手段（Linux）：**

```bash
# 允许 TIME_WAIT 状态的 socket 被新连接复用（最有效）
net.ipv4.tcp_tw_reuse = 1

# 缩短 FIN_WAIT_2 的超时
net.ipv4.tcp_fin_timeout = 30

# 扩大 TIME_WAIT 上限
net.ipv4.tcp_max_tw_buckets = 20000

# 增加可用端口范围
net.ipv4.ip_local_port_range = 10000 65000
```

> ⚠️ **`tcp_tw_recycle` 已被废弃**，不要在 Linux 4.12+ 上使用——它在 NAT 环境下会导致连接失败。**用 `tcp_tw_reuse` 更安全。**

## 7. 流量控制：滑动窗口

### 7.1 为什么需要滑动窗口

**如果没有窗口机制**：每发一个包就要等一个 ACK 才发下一个（这叫"停止-等待协议"）。

```
发送方 ──包1──→ 接收方
发送方 ←──ACK1── 接收方      ← 这段时间发送方在干等
发送方 ──包2──→ 接收方
发送方 ←──ACK2── 接收方
```

**问题**：链路大部分时间在"空跑"。假设 RTT = 100 ms，每个包 1000 字节，那实际速率只有：

```
1000 字节 / 0.1 秒 = 10 KB/s = 80 Kbps
```

**这条 1 Gbps 的链路，只被用到了 0.008%。** 太浪费了。

**滑动窗口的解决思路**：**一次发多个包，不用等每个包都确认。**

### 7.2 滑动窗口的工作机制

> 💡 **术语解释｜滑动窗口（Sliding Window）**
> 允许发送方在**未收到确认**的情况下，连续发送多个报文段。窗口"滑动"指的是：随着 ACK 到达，窗口的左边界右移，可以发送新的数据。

**窗口的四个部分：**

```
     已发送已确认    已发送未确认   可发送未发送    不可发送
    ┌─────────────┬─────────────┬─────────────┬───────────┐
    │  已确认数据   │  在途数据     │  窗口内可用   │  窗口外     │
    └─────────────┴─────────────┴─────────────┴───────────┘
                  ↑             ↑             ↑
              窗口左边界     发送指针      窗口右边界
```

**随着 ACK 到达，左边界右移，窗口整体向前"滑动"。**

**示例：**

```
初始：窗口 = 4 个段
  发送 [1][2][3][4]

收到 ACK=2（确认了段1）：
  窗口右移 1 位 → 可以发段5
  发送 [5]

收到 ACK=4（确认了段2、3）：
  窗口右移 2 位 → 可以发段6、7
  发送 [6][7]
```

### 7.3 接收窗口 rwnd

> 💡 **术语解释｜接收窗口（rwnd, Receive Window）**
> 接收方在 TCP 首部的**窗口字段**里告诉发送方："**我的缓冲区还能接收多少字节**"。
> 发送方据此调整自己的发送节奏——**这就是流量控制。**

**流量控制的目的**：**防止发送方发得太快，把接收方的缓冲区撑爆。**

**关键公式：**

```
实际发送窗口 = min(rwnd, cwnd)
               └─┬─┘  └─┬─┘
            流量控制   拥塞控制
           （接收方）  （网络）
```

**这是本阶段最重要的公式之一**：
- **rwnd** 由**接收方**决定（"我还能收多少"）
- **cwnd** 由**发送方**根据网络拥塞情况决定（"网络还能承受多少"）
- **两者取小**，谁的限制更严就听谁的

### 7.4 零窗口与窗口探测

**当接收方缓冲区满了**，它会通告 `rwnd = 0`。发送方收到后**停止发送**。

**但这里有个陷阱**：如果接收方后来腾出空间，发了一个"窗口更新"通知，**而这个通知丢了**——那发送方和接收方就会互相死等（死锁）。

**解决方案：零窗口探测（Zero Window Probe）**

发送方在收到 `rwnd = 0` 后，启动一个**持续计时器（Persist Timer）**，定期（指数退避）发送**窗口探测报文**（只带 1 字节数据），逼接收方回复当前的窗口大小。

```
发送方：窗口探测（1 字节数据）→
接收方：← ACK，窗口 = 0（还没空间）
发送方：（等待，再探测）
发送方：窗口探测 →
接收方：← ACK，窗口 = 4096（有空间了！）
发送方：开始正常发送 ✓
```

### 7.5 糊涂窗口综合征与 Nagle 算法

> 💡 **术语解释｜糊涂窗口综合征（SWS, Silly Window Syndrome）**
> 接收方每次只腾出**很小**的空间（比如 1 字节）就通告窗口，发送方就发一个**很小的包**。结果是网络里塞满了"大首部 + 小数据"的包，**传输效率极低**。

**两个方向的解决方案：**

| 问题方 | 解决方案 |
|---|---|
| **接收方**（别急着通告小窗口） | **等缓冲区腾出足够空间再通告**：要么达到 MSS 大小，要么达到缓冲区一半 |
| **发送方**（别急着发小包） | **Nagle 算法** |

> 💡 **术语解释｜Nagle 算法**
> 目的：**减少网络中的小包数量**，提高带宽利用率。
>
> **两条规则**：
> 1. 如果还有**未被确认**的数据，就先把要发的小数据**缓存起来**，不立即发
> 2. 等到收到 ACK，或者缓存攒够了一个 MSS，才发送
>
> **效果**：把多个小包合并成一个大的发出。
> **副作用**：**增加延迟**。因为要等 ACK 或攒够 MSS 才发，交互式应用（SSH、游戏、实时通信）会感觉"卡"。

**什么时候要关闭 Nagle 算法？**

```python
# Python 示例
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

| 场景 | 是否禁用 Nagle |
|---|---|
| 批量数据传输（文件、日志） | ❌ 保留（提高吞吐） |
| 交互式应用（SSH、游戏、RPC） | ✅ **禁用**（降低延迟） |
| 实时通信 | ✅ 禁用 |

### 7.6 延迟确认（Delayed ACK）

**与 Nagle 算法方向相反的一个优化**：

> 💡 **术语解释｜延迟确认（Delayed ACK）**
> 接收方收到数据后**不立即回 ACK**，而是等一段时间（通常 **200 ms**），或者等到**自己有数据要发时"捎带"一个 ACK**。
>
> **目的**：减少 ACK 报文数量，降低网络开销。

> ⚠️ **Nagle 算法 + 延迟确认 = 经典性能陷阱**
>
> 两者同时开启时可能产生约 **200 ms** 的额外延迟：
>
> ```
> 发送方（Nagle）：我有个小包，但要等 ACK 才能发 → 等
> 接收方（延迟ACK）：我收到数据了，但要等 200ms 或等有数据要发才回 ACK → 等
> → 双方互相等，白白多出 200ms 延迟 ✗
> ```
>
> **解决方案**：交互式场景**禁用 Nagle**（设 `TCP_NODELAY`），或者调整延迟确认的超时。
> **这是很多"网络明明很快但应用就是慢"问题的根源。**

## 8. 拥塞控制

### 8.1 流量控制 vs 拥塞控制

这是最容易混的一对概念：

| 对比项 | 流量控制 | 拥塞控制 |
|---|---|---|
| **关注点** | **接收方**的承受能力 | **网络**的承受能力 |
| **防止什么** | 接收方缓冲区溢出 | 网络拥塞崩溃 |
| **谁决定** | 接收方（通告 rwnd） | 发送方（维护 cwnd） |
| **机制** | 滑动窗口、零窗口探测 | 慢启动、拥塞避免、快重传、快恢复 |
| **类比** | 别把水倒太快，杯子会溢 | 别往水管里灌太多，管子会爆 |

**一句话：流量控制是"照顾对方"，拥塞控制是"照顾网络"。**

### 8.2 拥塞窗口 cwnd

> 💡 **术语解释｜拥塞窗口（cwnd, Congestion Window）**
> 发送方维护的一个状态变量，**反映当前网络的拥塞程度**。发送方用它来限制自己一次能发多少数据。

**变化规则：**

- 网络没拥塞 → **cwnd 增大**（可以发更多）
- 网络出现拥塞 → **cwnd 减小**（要收敛）

**怎么判断"拥塞"？** ——**没在 RTO 内收到 ACK，就认为网络拥塞了。**

**发送窗口公式（再强调一次）：**

```
swnd = min(cwnd, rwnd)
```

### 8.3 慢启动（Slow Start）

**连接刚建立时，发送方不知道网络能承受多少，所以要"试探"。**

**规则：每收到一个 ACK，cwnd 增加 1 个 MSS。**

**效果：每经过一个 RTT，cwnd 翻倍（指数增长）。**

```
初始：cwnd = 1 MSS     → 发 1 个段
收到 1 个 ACK：cwnd = 2 → 发 2 个段
收到 2 个 ACK：cwnd = 4 → 发 4 个段
收到 4 个 ACK：cwnd = 8 → 发 8 个段
收到 8 个 ACK：cwnd = 16 → 发 16 个段
...
```

```
cwnd
 16 │                          ●
    │                        ╱
  8 │                    ●
    │                 ╱
  4 │             ●
    │          ╱
  2 │       ●
    │    ╱
  1 │ ●
    └────────────────────────────→ RTT
```

> ⚠️ **"慢启动"不慢！** 名字叫"慢"，但增长是**指数级**的，很快就涨上去了。所谓"慢"是指**起点低（从 1 开始）**，而不是增长速度慢。
>
> **关于初始值**：经典教材说 cwnd 初始为 1 MSS。但 **RFC 5681 建议 2～4 MSS，现代 Linux 默认 10 MSS**（`tcp_init_cwnd`）。考试按教材答 1，实际理解知道是 10 即可。

### 8.4 拥塞避免（Congestion Avoidance）

**cwnd 不能无限指数增长**，否则很快就会把网络压垮。所以设了一个**门槛**。

> 💡 **术语解释｜慢启动门限（ssthresh, slow start threshold）**
> 一个阈值。`cwnd < ssthresh` 用慢启动；`cwnd ≥ ssthresh` 切换到拥塞避免。

**规则：每收到一个 ACK，cwnd 增加 1/cwnd 个 MSS。**

**效果：每经过一个 RTT，cwnd 增加 1 个 MSS（线性增长）。**

```
假设 ssthresh = 8：
收到 8 个 ACK → 每个 +1/8 → 总共 +1 → cwnd = 9
收到 9 个 ACK → 每个 +1/9 → 总共 +1 → cwnd = 10
...
```

```
cwnd
    │                              ╱ ← 拥塞避免（线性）
    │                           ╱
    │                        ╱
 ssthresh ────────────────●
    │              ╱  ← 慢启动（指数）
    │          ╱
    │       ╱
  1 │ ● ╱
    └────────────────────────────→ RTT
```

**所以整个增长曲线是：先指数、后线性。**

### 8.5 拥塞发生（超时重传）

**当发生超时重传**（说明网络已经严重拥塞），TCP 的反应很激烈：

```
ssthresh = cwnd / 2      ← 门槛降到当前窗口的一半
cwnd = 1                 ← 窗口直接归 1
```

**然后重新进入慢启动。**

**这个反应太激烈了**——一旦超时，发送速率瞬间掉到最低，然后再慢慢涨上去。会造成明显的"卡顿感"。

```
cwnd
    │        ●
    │      ╱   ╲
    │    ╱       ╲
    │  ╱           ╲
  1 │●             ● ← 归 1，重新慢启动
    └────────────────────────→ RTT
      ↑ 超时
```

### 8.6 快速重传与快速恢复

**TCP 认为：如果只是收到 3 个重复 ACK（而不是超时），说明网络只是"轻微拥塞"**——大部分数据还是通的，只有个别包丢了。**没必要这么激烈。**

**所以引入了快速恢复（Fast Recovery）：**

```
1. 快速重传：
   收到 3 个重复 ACK → 立即重传丢失的段（不等 RTO 超时）

2. 快速恢复：
   ssthresh = cwnd / 2      ← 门槛减半
   cwnd = ssthresh + 3      ← 窗口减半，但加 3（因为已有 3 个包被确认收到了）
   重传丢失的段

3. 在快速恢复期间：
   每再收到一个重复 ACK → cwnd += 1（窗口略微膨胀，允许继续发新数据）

4. 收到新数据的 ACK（说明丢失的段已补齐）：
   cwnd = ssthresh          ← 回到门槛值
   进入拥塞避免（线性增长）
```

**对比两种反应：**

```
                超时重传                     快速重传
                （严重拥塞）                 （轻微拥塞）
                    │                           │
ssthresh:      cwnd/2                      cwnd/2
cwnd:            1                        ssthresh + 3
下一步:        慢启动                      拥塞避免
              （从最低重新爬）              （从半山腰继续）
```

**快速恢复的核心价值**：**不用"一夜回到解放前"**，而是从半山腰继续，避免了剧烈的性能波动。

### 8.7 完整的拥塞控制状态图

```
                     连接建立
                        │
                   cwnd = 1（或 10）
                        │
                        ↓
              ┌──── 慢启动 ────┐
              │ cwnd < ssthresh │
              │ 每 ACK +1 MSS   │
              │ （指数增长）     │
              └────────┬────────┘
                       │ cwnd ≥ ssthresh
                       ↓
              ┌──── 拥塞避免 ───┐
              │ 每 ACK +1/cwnd  │ ←──────────┐
              │ （线性增长）     │            │
              └────────┬────────┘            │
                       │                     │
            ┌──────────┴──────────┐          │
            │                     │          │
      超时重传                 3 个重复 ACK    │
            │                     │          │
            ↓                     ↓          │
    ssthresh = cwnd/2      ssthresh = cwnd/2│
    cwnd = 1               cwnd = ssthresh+3 │
            │              重传丢失段         │
            │                     │          │
            │              每重复 ACK +1      │
            │                     │          │
            │              收到新 ACK        │
            │              cwnd = ssthresh ──┘
            ↓
        回到慢启动
```

### 8.8 常见拥塞控制算法

| 算法 | 特点 | 说明 |
|---|---|---|
| **Tahoe** | 最早期版本 | 只有慢启动 + 拥塞避免 + 快速重传，**没有快恢复**。一丢包就归 1 |
| **Reno** | 最经典的版本 | 加入**快速恢复**，就是上面讲的那套 |
| **NewReno** | Reno 改进 | 优化了"一个窗口内丢多个包"的恢复速度 |
| **CUBIC** | **Linux 默认**（2.6.19+） | 用三次函数控制窗口增长，**高带宽高延迟场景表现好** |
| **BBR** | Google 提出 | **不看丢包，看带宽和 RTT**。在有一定丢包的链路上吞吐远高于 CUBIC |

> 💡 **术语解释｜BBR（Bottleneck Bandwidth and RTT）**
> Google 2016 年提出的拥塞控制算法。传统算法（Reno/CUBIC）都**把"丢包"当作拥塞信号**——但现代网络里丢包不一定意味着拥塞（可能是链路误码）。
> BBR 换了个思路：**主动测量链路的最大带宽和最小 RTT，把发送速率控制在这个"管道容量"附近**。结果是**在有丢包的链路上吞吐量大幅提升，同时延迟更低**。

**查看和修改当前算法（Linux）：**

```bash
# 查看当前算法
sysctl net.ipv4.tcp_congestion_control

# 查看可用算法
sysctl net.ipv4.tcp_available_congestion_control

# 切换为 BBR
sysctl -w net.ipv4.tcp_congestion_control=bbr
```

## 9. TCP 粘包问题

### 9.1 为什么会有粘包

**根本原因：TCP 面向字节流，没有消息边界。**

```
应用层发出两次数据：["Hello"] ["World"]

TCP 视角：只是一串字节 H e l l o W o r l d
         它不知道哪里是"一条消息"的结束

接收方可能收到：
  ["HelloWorld"]        ← 粘包（两条消息合成一条）
  ["Hel"]["loWorld"]    ← 拆包（一条消息被拆开）
  ["Hello"]["World"]    ← 正好对上（但这是运气）
```

**注意：这不是 TCP 的"bug"，而是"面向字节流"的必然结果。** UDP 因为面向报文，不会粘包。

### 9.2 粘包的三种成因

| 成因 | 说明 |
|---|---|
| **TCP 面向字节流** | 最根本原因。TCP 不保留应用层的消息边界 |
| **发送方 Nagle 算法** | 把小包缓存合并成大包发送 |
| **接收方读取不及时** | 数据到达时应用层没及时 `read()`，多个包堆在缓冲区里 |

### 9.3 三种解决方案

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **固定长度** | 每条消息长度固定（如 100 字节），不足补齐 | 简单，但浪费带宽，不灵活 |
| **特殊分隔符** | 用 `\n`、`\r\n` 等特殊字符标记消息结束 | 简单，但消息内容不能含分隔符（需要转义） |
| **长度字段**（最常用） | 消息头里声明消息长度，先读头再读体 | 灵活高效，**工业界标准做法** |

**长度字段方案（TLV 格式）：**

```
┌────────────┬──────────────────────┐
│ Length(4B) │      Payload         │
│  长度字段   │      实际数据         │
└────────────┴──────────────────────┘

接收方逻辑：
1. 先读 4 字节，解析出长度 N
2. 再读 N 字节，得到完整消息
3. 循环
```

**实际应用中的协议都用这种方式**：

- HTTP：`Content-Length` 头
- WebSocket：帧头里带长度
- 各种 RPC 框架（gRPC、Dubbo）：都有自定义的帧结构

> ⚠️ **一个重要认知**：**"粘包"是应用层的问题，不是 TCP 的问题。** TCP 只负责把字节流可靠地送到，至于怎么切分消息，是应用层协议的责任。

## 10. TCP vs UDP 对比

| 对比项 | TCP | UDP |
|---|---|---|
| **连接方式** | 面向连接（需三次握手） | 无连接 |
| **可靠性** | **可靠**（确认、重传、排序、去重） | **不可靠**（尽力而为） |
| **传输方式** | **面向字节流** | **面向报文** |
| **首部大小** | **20～60 字节** | **8 字节** |
| **传输效率** | 较低（开销大） | 高（开销小） |
| **速度** | 较慢 | 快 |
| **是否有序** | 保证有序 | 不保证 |
| **流量控制** | ✅ 有（滑动窗口） | ❌ 无 |
| **拥塞控制** | ✅ 有（四大算法） | ❌ 无 |
| **连接数** | 只能一对一 | 支持一对一、一对多、多对多 |
| **数据边界** | 无（会粘包） | 有（不会粘包） |
| **资源占用** | 高 | 低 |
| **典型应用** | HTTP、HTTPS、FTP、SMTP、SSH | DNS、DHCP、音视频、游戏、QUIC |

**记忆口诀：**

- **要可靠、有序、不能丢 → TCP**
- **要快、要实时、丢一点无所谓 → UDP**

**选型建议：**

```
数据完整性要求高？
├─ 是 → 用 TCP
│      （文件传输、网页、邮件、数据库）
└─ 否 → 实时性要求高？
       ├─ 是 → 用 UDP
       │      （音视频、游戏、直播）
       └─ 否 → 数据量很小且一问一答？
              ├─ 是 → 用 UDP（DNS、DHCP）
              └─ 否 → 用 TCP（保险起见）
```

| 术语 | 英文 / 缩写 | 一句话解释 |
|---|---|---|
| 传输层 | Transport Layer | 提供端到端（进程到进程）通信 |
| 端到端 | End-to-End | 从源主机进程到目的主机进程，而不是主机到主机 |

## 12. 八个常见误区

### 误区 1："TCP 可靠，所以一定不丢数据"

**不严谨。** TCP 保证的是"**在连接正常的情况下**，数据不丢、不重、有序"。如果连接被 RST 中断、或者长时间重传失败，TCP 会**放弃并通知应用层出错**。**TCP 的可靠性有边界。**

### 误区 2："慢启动真的很慢"

**错误。** "慢"指的是**起点低（cwnd 从 1 或 10 开始）**，而不是增长速度慢。慢启动阶段 cwnd **每个 RTT 翻倍**，是**指数增长**，很快就涨上去了。

### 误区 3："流量控制和拥塞控制是一回事"

**错误。**
- **流量控制**关注**接收方**的承受能力（rwnd）
- **拥塞控制**关注**网络**的承受能力（cwnd）
- 两者**取最小值**决定实际发送窗口

### 误区 4："TIME_WAIT 是故障，要尽快消除"

**错误。** TIME_WAIT 是**协议要求且必要**的状态，用来保证最后一个 ACK 能送达、旧报文能消散。**少量 TIME_WAIT 完全正常。** 只有在数量异常大（大量短连接）时才需要优化。

### 误区 5："CLOSE_WAIT 和 TIME_WAIT 差不多，等等就没了"

**错误。**
- **TIME_WAIT 会自己消失**（2MSL 后）
- **CLOSE_WAIT 不会自己消失**——它等的是**应用程序调用 `close()`**。如果代码有 bug，连接会一直卡在那里。
- **大量 CLOSE_WAIT = 代码有连接泄漏，必须改代码。**

### 误区 6："三次握手可以改成两次，效率更高"

**错误。** 两次握手无法防止"失效的连接请求"导致的无效连接，会浪费服务器资源。**第三次握手不是多余的，它是必要的。**

### 误区 7："粘包是 TCP 的 bug"

**错误。** TCP 是**面向字节流**的，本来就没有"消息"的概念，**不存在"应该分开"这回事**。粘包是**应用层需要自己处理的问题**——通过定义消息边界（长度字段、分隔符）来解决。

### 误区 8："UDP 不可靠，所以不能用在对数据有要求的场景"

**错误。** 可靠性可以**由应用层自己实现**。QUIC（HTTP/3 的传输层）就是在 UDP 上实现了完整的可靠传输和拥塞控制，而且比 TCP 更灵活——**可以针对具体场景优化，还能绕过 TCP 的队头阻塞。**
