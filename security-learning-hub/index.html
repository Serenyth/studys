分层模型与数据封装

安全工作中 80% 的问题，都能归结为"某个协议在设计时没有考虑某种情况"

OSI 七层是教学模型，TCP/IP 四层是实际实现——但"分层"这个思维方式极其有用：每一层只信任上一层交给它的数据，只负责"送到"，不验证"送的是什么"。这就是为什么 SQL 注入在网络层完全看不出来。

ENCAPSULATION· 数据如何一层层穿上"信封"
WHY IT MATTERS

抓包时看到的"多层头部嵌套"就是封装的结果。数据从上往下，每层加一个头；接收端反向拆开。应用数据 → 段(+TCP头) → 包(+IP头) → 帧(+以太网头) → 比特流。

OSITCP/IP典型协议数据单元典型攻击
应用/表示/会话应用层HTTP DNS TLS报文SQL注入、XSS、DNS劫持
传输层传输层TCP UDP段/数据报SYN Flood、端口扫描
网络层网络层IP ICMP ARP包IP欺骗、ICMP隧道
数据链路层网络接口层以太网 Wi-Fi帧ARP欺骗、MAC Flooding
物理层—双绞线、光纤比特物理接入、窃听

数据从上往下传时，每层在原有数据前加上自己的头部。接收端反向解封装。抓包时看到的多层头部嵌套，就是封装的结果。

每一层只负责"送到"，不负责"送的是什么"。应用层的攻击（如 SQL 注入）在网络层完全看不出来——这既是分层的优雅，也是检测的难题：想在网络层看见应用层威胁，就必须做深度解析（DPI），这正是 IDS/IPS 存在的理由。

TCP 连接的生命周期

三次握手 · 四次挥手 · SYN Flood 攻击演示

为什么握手是三次而不是两次？因为需要双方都确认对方的收发能力——两次只能让服务器确认"客户端能发、我能收"，无法让客户端确认"服务器能发"。三次握手同时交换并确认了双方的初始序号（ISN），防止历史连接的旧报文被误认。

SEQUENCE LAB· 时序图实验台
NOTE

点击「播放」观察报文流动与双方状态机的迁移。切换到 SYN Flood 模式，观察半连接队列如何被占满。

主动关闭方发完最后一个 ACK 后等待 2MSL（Linux 固定 60s）。两个作用：① 保证最后的 ACK 能到达，丢了还能重发；② 让旧连接的残留报文在网络中消亡。

被动关闭方收到 FIN 后进入 CLOSE_WAIT，必须由应用程序调用 close() 才会离开。口诀：大量 TIME_WAIT 是主动关闭方的正常现象；大量 CLOSE_WAIT 一定是代码 bug。

攻击者伪造大量源 IP 发送 SYN，服务器回 SYN+ACK 后进入 SYN_RCVD 等待永远不来的 ACK，半连接队列被占满，正常用户无法建立连接。防御：SYN Cookie（不保存状态，把信息编码进 seq）、增大队列、缩短超时、抗 D 设备。切到上方「SYN Flood」模式直观感受。

状态出现在含义
LISTEN服务端等待连接
SYN_RCVD服务端半连接——SYN Flood 占满的就是它
ESTABLISHED双方连接已建立
CLOSE_WAIT被动关闭方已回 ACK，等应用调用 close()
TIME_WAIT主动关闭方等 2MSL，保证可靠收尾

[ L1 / APPLICATION / TLS ]

TLS 握手与前向保密

HTTPS = HTTP + TLS · 机密性 / 完整性 / 身份认证

TLS 1.3 把握手从 2-RTT 压缩到 1-RTT：客户端在第一个消息里就带上密钥份额（key_share）。更关键的变化——强制 (EC)DHE、删除 RSA 密钥交换，换来前向保密：即使服务器私钥将来泄露，历史流量也无法被解密。

TLS 1.3 HANDSHAKE· 注意哪些消息已加密 🔒
RTT 对比

TLS 1.2 握手需要 2 个往返；1.3 只要 1 个。会话恢复时还支持 0-RTT——但 0-RTT 数据有重放攻击风险，只能用于幂等请求。

每次会话临时生成密钥对（ECDHE 的 E = Ephemeral），用完即弃。RSA 密钥交换不具备前向保密——私钥泄露 = 历史流量全部可解。TLS 1.3 已强制 (EC)DHE。

服务器证书（叶子）→ 中间 CA → 根 CA。浏览器内置受信任的根证书列表，逐级验证签名直到锚定。证书用 SAN 字段列出适用域名（CN 已被忽略）。

  • TLS 1.2 及以前：证书明文传输，可以看到服务器域名
  • TLS 1.3：证书已加密，但 SNI 仍明文（除非 ECH），仍可推断访问的域名
  • 应用数据完全加密——但包大小、时序、方向仍暴露，流量分析依然能推断服务类型

[ L1 / OS / LINUX ]

Linux 权限模型

rwx 八进制 · SUID/SGID/Sticky · 提权排查的核心

这是 Linux 部分最重要的一节——提权、横向、权限维持全建立在这个模型上。八进制：r=4, w=2, x=1。注意目录的 w 意味着可以删除目录内的任何文件（与文件本身权限无关），这正是 Sticky Bit 存在的理由。

PERMISSION FORGE· 权限位实验台
READING ls -l

点击任意开关位，观察八进制与 ls 显示的联动。特殊位会把 x 显示成 s/t（有执行权）或 S/T（无执行权）。

可执行文件被运行时，进程的有效用户 ID（EUID）变为文件属主而非调用者。权限检查看的是 EUID——SUID 的作用就是把 EUID 从调用者改成属主。

把 root 特权拆成几十个细粒度单元：CAP_NET_RAW（抓包）、CAP_NET_BIND_SERVICE（绑低端口）、CAP_DAC_READ_SEARCH（绕过读检查）。程序只需被授予所需的那几项，而不是整个 root。排查：getcap -r /

/usr/bin/passwd 需要改 /etc/shadow（仅 root 可写），所以它是 SUID root。如果某个 SUID root 程序的功能可被滥用，就等于送出 root Shell：

  • 内部调用 system()/popen() 且参数可控 → 命令注入
  • 提供读/写/编辑/分页/解压能力 → 任意文件读写
  • 加载当前目录的动态库 → LD_PRELOAD/RPATH 劫持

排查流程：find / -perm -4000 -type f 列出所有 SUID 文件，再对照 GTFOBins（收录"哪些合法程序可被滥用"的数据库）逐条比对。sudo 配置不当是提权第二大来源，同样查 GTFOBins。

Linux 主机运营面

FHS 目录地图 · 进程与服务 · 定时任务 · 日志与审计

上一节回答"能不能"，这一节回答"从哪看"。FHS 把"什么文件放哪里"变成了一条约定——正因为所有发行版都遵守它，应急响应脚本、基线检查工具才能靠固定路径定位关键文件。入侵排查的第一步，永远是按目录走一遍。

FHS MAP· 目录即排查地图
HOST TRIAGE

点击任意目录查看安全关注点。红色=高频攻击面（凭据、持久化、可写目录），琥珀=需重点核对权限，青色=常规但不可忽略。

系统启动后创建的第一个用户态进程，负责拉起其余服务并回收孤儿进程。现代发行版中 PID 1 通常是 systemd。容器里的 PID 1 往往就是你的应用本身——没人回收孤儿，这是容器里僵尸进程堆积的根源。

僵尸（Z）：子进程已退出，父进程还没 wait() 回收，只占 PID 不占 CPU/内存。孤儿：父进程先退出，子进程被 PID 1 接管——正常现象，无害。两者常被混淆。

持久化位置正常用途攻击者怎么用
/etc/systemd/system/*.service管理员自定义服务新建 unit，ExecStart 指向 /tmp 或编码命令
/etc/systemd/system/*.timer替代 cron 的定时器比 cron 更隐蔽，很多排查清单会漏掉
/etc/crontab · /etc/cron.d/系统级定时任务多一个"执行用户"字段，可直接指定 root
/var/spool/cron/<user>crontab -e 写入用户级，常被忽略
~/.bashrc · ~/.profile登录初始化登录即执行，最容易被漏检
/etc/ld.so.preload全局预加载库用户态 rootkit 的标准手法

1. 可被清除——root 下 > /var/log/auth.log 或 journalctl --rotate --vacuum-time=1s 就能抹掉。所以关键日志必须实时转发到远端，本地日志只当缓存。

2. 默认记录不足——很多发行版默认不开 auditd，命令执行、文件访问压根没记录。查不到不等于没发生。

3. 时间不准——多机时区/时钟漂移会让时间线对不上。取证前先确认 NTP 状态，否则"先后顺序"的结论全是猜的。

set -e 出错即停、set -u 未定义变量报错、set -o pipefail 管道中任一环节失败都算失败。默认行为下 Bash 会带着错误状态继续跑下去——一个失败的清理命令后面跟着 rm -rf "$DIR"/，变量为空时就变成了删根。

另一个高频坑：cron 的 PATH 很短，脚本里用相对路径调用命令，就可能被 PATH 劫持执行攻击者的同名程序。

HTTP 报文与安全响应头

无状态协议 · 状态码泄露 · 一行响应头就是一道浏览器级防线

HTTP 是无状态的——每个请求独立，服务器默认不记得上一个请求。所以"登录状态"必须靠 Cookie / Session / Token 外挂（§11 展开）。而响应头里藏着一类特殊的东西：它们不是给用户看的，是给浏览器下的强制指令。缺一条，对应的整类攻击就没有任何浏览器侧阻力。

HEADER LAB· 关掉一条头，看哪类攻击被打通
BROWSER ENFORCED

这些头的共同点：服务器说一句，浏览器就照做。它们不能替代服务端校验，但能把"一个 XSS"限制成"一次弹窗"，而不是"一次会话劫持"。

告诉浏览器"以后访问我这个域，一律先用 HTTPS"，在浏览器内部把 http:// 改写成 https://，请求根本不会明文发出去。这是防 SSL Stripping（中间人把 https 降级成 http）的唯一浏览器侧手段。max-age 要足够长，配合 includeSubDomains 和 preload 列表才完整。

限制页面能加载/执行哪些来源的脚本。思路是"默认全禁，按需放行"：default-src 'self' 之后，内联脚本默认不执行——这一条就能让大量 XSS 载荷失效。进阶用 nonce- 或 strict-dynamic 替代 unsafe-inline。

GET获取资源是参数在 URL 里 → 进日志、Referer、浏览器历史
POST创建 / 提交否CSRF 的主要目标；可被第三方页面自动提交
PUT / PATCH替换 / 局部更新PUT 是常被错误地开放给普通用户 → 越权改数据

OPTIONS查询支持的方法是CORS 预检的载体，见 §11

403（存在但无权限）与 404（不存在）的差异，可以直接用来枚举资源：扫一遍就知道哪些用户 ID、哪些后台路径是真实存在的。

500 常带堆栈信息，泄露框架版本与代码路径。登录接口返回"用户名不存在"还是"密码错误"，就是标准的用户名枚举漏洞。正确做法：统一返回"用户名或密码错误"，且响应时间也要拉平。

HPACK 侧信道：头压缩让"压缩后长度"携带信息，攻击者能注入内容并观察长度，就能逐字节推断出密文——这是 CRIME / BREACH 类攻击的家族。长度本身就是信息。

§9
[ L1 / NETWORK / BOUNDARY ]

代理 · CDN · NAT：信任边界的错位

你以为在跟服务器说话，其实在跟代理说话

现代架构里，请求到应用之前平均要穿过 CDN → WAF → 负载均衡 → 反向代理 四层。每一层都要重新解析一次 HTTP——只要两层的解析规则有一点不一致，就产生了可以夹带的缝隙。绝大多数"WAF 被绕过"的故事，根因不是规则不够，而是层次之间对同一个请求的理解不一样。

PROXY CHAIN· 同一份字节，两种理解
PARSER DIFF

走私的本质：前端按 Content-Length 切分，后端按 Transfer-Encoding: chunked 切分，多出来的那段字节会被后端当成下一个请求的开头——而那个请求，是攻击者写的。

代理站在客户端这边。客户端把请求交给代理，代理替它去访问目标；目标看到的源 IP 是代理。用途：突破访问限制、隐藏来源、企业上网审计。渗透里的 proxychains、Burp Suite 都是正向代理。

代理站在服务器这边，客户端不知情。用途：负载均衡、TLS 卸载、缓存、隐藏后端拓扑、WAF 前置。Nginx / HAProxy / Traefik 是典型实现。安全代价：应用看到的"客户端 IP"可能全是代理的。

让内网主机共用少量公网 IP。SNAT 改写源地址（内网访问外网），DNAT 改写目的地址（端口映射，把内网服务暴露出去）。安全意义：NAT 顺带隐藏了内网拓扑，但它不是防火墙——一旦做了端口映射，那条通路就是双向的。

在公网上建加密隧道，把远程设备接入内网；工作在网络层（IPsec）或应用层（OpenVPN / WireGuard）。安全意义：远程办公与跨地域组网。它的问题正是"一次认证、全内网可达"——一台设备失陷就等于站在了内网里，这也正是零信任要取代它的原因。

代理转发时会追加 X-Forwarded-For: 真实IP, 上一跳IP。问题是这个头没有任何密码学保护，客户端可以自己先塞一个进去。如果应用直接取 XFF 的第一个值做 IP 白名单或限流，攻击者随便写 X-Forwarded-For: 127.0.0.1 就绕过了。

正确做法：只信任最靠近自己的那一层代理写入的值（按跳数从右往左取），或者干脆由边缘节点用 X-Real-IP 覆盖式写入；内网入口上禁止客户端直连。

变体还有：%2e%2e%2f（编码一次）、%252e%252e%252f（编码两次）、..;/（Tomcat 的分号截断）、/static/..%5cadmin（Windows 反斜杠）。防御方式只有一个：规范化之后再做判断，且判断与执行用同一个字符串。

§11
[ L1 / WEB / SESSION ]

会话 · 同源 · CORS

无状态协议怎么记住你，浏览器又怎么拦住别人读你

这一节是 XSS / CSRF / 越权三类漏洞的共同地基。两条主线：① 服务器怎么在无状态协议上维持"你已登录"；② 浏览器凭什么阻止 A 站读取 B 站的数据。理解了 Cookie 的三个属性，就理解了一半的 Web 攻防。

COOKIE LAB· 三个属性决定三种攻击
DEFENSE IN DEPTH

属性只决定"浏览器肯不肯配合"，真正的防线仍是服务端：输出编码防 XSS、CSRF Token 防跨站请求、HttpOnly 只是把损失从"会话劫持"降到"页面被改"。

维度Session（服务端状态）JWT（自包含令牌）
状态存哪服务端（内存 / Redis）客户端，服务端不存
可撤销性立即失效（删掉即可）签发后无法撤销，只能维护黑名单
扩展性多实例需共享存储天然水平扩展
内容保密客户端看不到Payload 只是 Base64，不是加密

① 把 Payload 当密文。 手机号、内部 ID、角色放进 JWT 等于明文公开——任何人 base64 解码就能看。

② alg: none。 服务端若不校验算法，攻击者把 header 改成 {"alg":"none"} 并删掉签名即可伪造。

③ 算法混淆。 服务端本用 RS256（非对称），攻击者改成 HS256（对称）并把公钥当 HMAC 密钥去签名——实现不严谨就能通过。

协议 + 域名 + 端口三者完全相同才算同源。https://a.com 与 http://a.com 不同源（协议不同）；与 https://b.a.com 也不同源（域名不同）。注意：它限制的是"读取"，不是"发送"——所以 CSRF 能发出请求，只是读不到响应。

非简单请求（PUT、自定义头、application/json）浏览器会先发 OPTIONS 问一句"我能这样请求吗"，服务器用 Access-Control-Allow-* 回答。预检是浏览器行为，不是服务器强制的——绕过浏览器直接发包，预检根本不存在。

Access-Control-Allow-Origin: * 与 Allow-Credentials: true 同时出现是无效的，浏览器会直接拒绝。于是很多开发者改成"把请求里的 Origin 原样回写"：

Access-Control-Allow-Origin: <反射请求头> + Allow-Credentials: true

这等于允许任意站点带着用户 Cookie 读取本站数据——比 * 更糟。正确做法是严格白名单比对（且不要用 startsWith/includes 这种能被 evil-a.com 骗过的写法）。

字符编码与数据表示

同一个字符有多种写法 —— 大量绕过技巧就长在这上面

这一节最容易被跳过，却是绕过类漏洞的总开关。核心事实只有一句：「字符」和「字节」不是一一对应的。同一个 '，在 UTF-8 里是 27，在 GBK 里可以被"吃掉"半个汉字；同一个字母 a，在西里尔字母表里有一个长得一模一样的兄弟。

ENCODING LAB· 一个字符的多种身份

编码结构安全场景

UTF-8变长 1–4 字节，兼容 ASCIIWeb 默认；超长编码（overlong）可绕过过滤器

URL 编码%XX多重编码绕过只解一层 WAF
HTML 实体 / Unicode 转义&#x3C; / \u003cXSS 上下文绕过

所有输入都必须走完「解码 → 规范化 → 校验 → 使用」四步，且校验与使用必须针对同一个字符串。

只做其中一步就会留缝：只校验不解码 → 编码绕过；校验前解码、使用前再解码一次 → 双重解码绕过；校验前规范化、使用时不规范化 → é（U+00E9）与 e+U+0301 被当成两个不同的东西。这也是"同一个字符串"这句话的分量。

0.0–10.0 分。基础指标（固有属性）+ 时序指标（利用代码是否公开）+ 环境指标（资产重要性）。只按 CVSS 排序是新手最常见的错误——会导致修一堆永远不会被打的漏洞。

实施所有控制措施之后仍然存在的风险。安全的目标是把它降到可接受水平，而不是消灭它。这个概念能同时纠正两种极端："上了这么多设备应该没问题了"（错，仍需持续验证）、"还有风险说明安全没做好"（错，在可接受范围内就是合格）。

EPSS 是 0–1 的概率，预测"未来 30 天被在野利用的可能性"。KEV 是 CISA 的"已确认被利用"清单，属于确定性信号。实用公式：优先级 ≈ CVSS × 资产重要性 × 可利用性。

很多团队的真实做法是"发现问题 → 提工单 → 没人修 → 一直挂着"。这既不是接受也不是缓解，而是风险失控。

规范的接受需要三样东西：① 书面记录（风险是什么、影响多大、为什么现在不修）；② 明确责任人（谁签字谁承担）；③ 复审机制（什么条件下重新评估，比如业务量翻倍、出现新的利用方式）。没有这三样，"接受"只是"忘记"的体面说法。

密码学基础

不要求实现算法，但要求能判断一个加密方案是否靠谱

对称加密：同一把密钥加解密，快，但密钥分发困难。AES 是主流；ChaCha20 用于移动端。分组模式比算法更容易出错：ECB 绝对禁用（相同明文块产生相同密文块，泄露数据模式）；GCM 推荐（AEAD，同时提供加密与完整性）。

非对称加密：公钥加密、私钥解密。RSA 基于大整数分解；ECC 密钥更短；DH/ECDHE 专用于密钥交换。TLS 1.3 已强制 (EC)DHE——为前向保密。

哈希：单向性、抗碰撞、雪崩效应。MD5/SHA-1 已破解，禁用于安全场景。口令存储绝不能用快速哈希——GPU 每秒数十亿次 SHA-256，8 位口令几小时穷举完。必须用慢哈希 KDF：Argon2id（首选）、bcrypt——故意设计得慢且内存硬，让爆破成本高到不可行。

DIFFIE-HELLMAN· 颜色混合类比 · 窃听者推不回原料
WHY IT WORKS

双方在不安全信道上协商出只有彼此知道的共享密钥。颜色混合是"单向"的——混合容易，分离极难，正如离散对数。ECDHE 的 E（Ephemeral）表示每次会话临时生成、用完即弃，这正是前向保密的实现基础。

HS256 签发方与验证方共享同一密钥——微服务架构中意味着每个验证方都能伪造 token。RS256 只有认证中心持私钥，其他服务只持公钥验证，推荐多服务场景。这也是"算法混淆攻击"的成因：服务端用 RS256 但不限定算法时，攻击者把 header 改成 HS256，用公开的公钥当 HMAC 密钥签名即可伪造。另外记住：JWT 的 Payload 只是 Base64，不是加密——放手机号等于明文公开。

密码学工程细节

算法选对了，模式用错了，一样等于没加密

上一节讲的是"该用哪个算法"，这一节讲工程上真正出错的地方。AES 是分组密码——一次只能加密 16 字节，更长数据怎么切、块与块之间怎么关联，由"模式"决定。现实中的密码学事故，绝大多数不是算法被攻破，而是模式、IV、随机数用错了。

BLOCK MODE· ECB 泄露轮廓，CBC 打散它
WHY IT MATTERS

左边是明文图案，中间 ECB 加密后相同颜色仍是相同颜色——轮廓完好可辨；右边 CBC 因为每块都混入了前一块的密文，相同明文得到不同密文，图案被彻底打散。点「重新加密」：ECB 永远不变，CBC 每次都不同。

模式原理安全性踩坑点
ECB每块独立加密不安全相同明文块 → 相同密文块，泄露数据模式
CBC前一块密文与当前明文异或需正确用 IVIV 必须随机且不可预测；有 Padding Oracle 风险
CTR计数器生成密钥流异或较好计数器绝不能重用，否则密钥流重用
GCMCTR + GHASH 认证推荐AEAD：同时给机密性与完整性；nonce 同样不可重用

作用不是保密，而是保证"相同明文每次加密得到不同密文"。规则：CBC 下必须随机且不可预测（防选择明文攻击）；CTR/GCM 下绝对不能重用——重用等于密钥流重用，两组密文异或就把明文异或结果直接泄露出来。

同时提供机密性与完整性，GCM / CCM / ChaCha20-Poly1305 都属于此类。它的价值是防篡改：纯 CBC 的密文被改动后，解密可能只得到乱码，系统无法察觉——Padding Oracle 正是靠这一点逐字节解密。

普通随机数（C 的 rand()、Python 的 random）是可预测的——给定种子就能复算出整个序列。用它生成 Session ID 或密码重置令牌，攻击者可以推算出别人的令牌。真实案例：某路由器用时间戳作 WPS PIN 的种子，导致 PIN 可被预测，几分钟就被破解。

对照表：Python random → secrets.token_hex()；Java java.util.Random → SecureRandom；PHP rand()/mt_rand() → random_bytes()；Node Math.random() → crypto.randomBytes()。

OAuth 2.0 回答的是"这个应用能否访问我的数据"，不是"我是谁"。把 OAuth 当认证用（拿 access_token 调用户信息接口就当登录）会出严重问题。要认证，用构建在其上的 OIDC——它提供 JWT 格式的 id_token，明确表达用户是谁、何时认证、用什么方式。

用票据代替反复传密码：客户端 → AS 取 TGT → 拿 TGT 向 TGS 换服务票据 → 访问服务。TGT 是域渗透的终极目标（拿到即可伪造任意服务票据，即"黄金票据"）；服务票据可被离线破解（Kerberoasting）。

很多系统点退出只是删浏览器 Cookie，服务端 Session 依然有效——攻击者复制过 Session ID 就能继续用。正确的登出做三件事：① 服务端销毁 Session（或 JWT 进黑名单）② 客户端清除 Cookie/Storage ③ 短 TTL + Refresh Token 轮换。另外：登录成功后必须重新生成 Session ID，否则会话固定攻击等着你。

① 编码绕过：多重 URL 编码、Unicode、大小写混写。② 语法等价：SELECT 可以写成 SeLeCt、SEL/**/ECT、/*!50000SELECT*/。③ 协议层绕过：分块传输、请求走私、HTTP/2 降级。④ 业务层绕过：逻辑漏洞 WAF 完全看不见——改个参数就能越权，没有任何攻击特征。

所以正确的心态是：WAF 用来提高攻击成本、挡住自动化扫描器，真正的安全靠代码本身。如果一家公司说"我们有 WAF 所以安全"，那基本可以判断他们不懂安全。

① 加密流量看不见。 全站 HTTPS 之后，基于内容的检测基本失效。解法是 TLS 解密（有隐私与合规问题）或转向流量元数据分析（Zeek：看连接行为而非内容）。

② 误报淹没真警。 默认规则集动辄几万条，直接开就是灾难，必须按环境裁剪。

③ 规则不更新等于没有。 新漏洞的检测规则需要持续跟进。

漏洞管理与优先级

不是扫一次出报告，而是一个持续循环

漏洞管理不是"扫一次出个报告"，而是 资产发现 → 扫描 → 验证 → 定级 → 分派 → 修复 → 复测 → 度量 的循环。下面这个实验台回答一个真实问题：500 个漏洞，按什么排序能让业务方愿意动手？

PRIORITY MATRIX· 同样的漏洞，两种排序
HELP THEM SAY NO

漏洞管理的本质是帮助业务做减法，不是把问题全部抛给业务。按 CVSS 排序，业务方看到"300 个高危"直接躺平；按矩阵排序，业务方看到"这周要修 8 个"，才有可能执行。

扫描类型说明频率
外部扫描从互联网视角扫描暴露面每周
内部扫描内网全段扫描每月
认证扫描提供凭据，能看到补丁级别每季度
Web 扫描（DAST）针对应用每次发布
镜像扫描容器镜像的依赖漏洞每次构建
SCA代码依赖的已知漏洞每次提交

逻辑漏洞（越权、支付篡改、流程绕过）没有任何特征；业务配置问题（如"这个接口没做限流"）不在扫描器的知识库里；需要多步交互的漏洞（存储型 XSS、登录后才可见的功能）覆盖不到；供应链问题（引入的恶意包）也不在传统扫描范围内。

所以漏洞管理必须和渗透测试、代码审计、人工评审结合，不能只靠扫描器。

① 明确的责任人：每个资产有且只有一个 owner。② SLA 与升级机制：超时自动升级。③ 例外流程：确实修不了的走书面风险接受。④ 度量指标：平均修复时间（MTTR）、按期修复率、重开率、高危漏洞存量趋势。

资产发现→"影子资产"永远扫不到；扫描→漏掉云资源与容器镜像；验证→把扫描器误报直接发给业务，失去信任；定级→只看 CVSS 不看资产；分派→找不到负责人；修复→没有 SLA；复测→修了不验证，或验证了不记录。

方法论与授权边界

PTES FLOW· 七阶段 · 点击查看目标与产出
WHY ENGAGEMENT FIRST

第一阶段"前期交互"决定了这次测试是合规的安全服务还是违法犯罪：范围（明确写出"不包含"的部分）、时间窗口、技术限制（是否允许 DoS / 社工 / 物理）、数据处理、应急联系人（24 小时可达）、中止条件。

在中国法律框架下，《刑法》第 285 条（非法侵入计算机信息系统罪、非法获取计算机信息系统数据罪）、第 286 条（破坏计算机信息系统罪）、《网络安全法》第 27 条都覆盖相关行为。"我只是扫描了一下没做别的"也可能构成违法——未经授权的端口扫描、漏洞探测、目录爆破，在司法实践中都可能被认定为"侵入"的预备或实行行为。

合法的渗透测试必须具备：① 书面授权（合同或授权书，明确范围、时间窗口、允许的技术手段）；② 明确的联系人，出现意外可立即中止；③ 测试范围外的资产一律不碰。

类型测试方掌握的信息优点缺点
黑盒只知道目标名称最接近真实攻击覆盖不全，耗时
灰盒部分信息（测试账号、架构文档）效率与真实性平衡需要客户配合
白盒全部信息（源码、架构、账号）覆盖最全，能发现深层问题不模拟真实场景

Kill Chain（侦察 → 武器化 → 投递 → 利用 → 安装 → 命令与控制 → 达成目标）强调"在哪一环可以打断攻击"，适合做防御规划；ATT&CK 强调"具体用了什么技术"，适合做检测覆盖度评估。

实际工作中两者配合：用 Kill Chain 定战略（在哪一环投入资源），用 ATT&CK 定战术（具体检测什么）。

① 先理解，再动手。 每用一个工具，都要能说清它发了什么包、触发了什么行为、为什么能成功。② 先手工，再自动化。 自动化工具只能发现它认识的漏洞；手工测试才能发现逻辑问题。③ 先记录，再继续。 渗透过程会产生大量零散信息（端口、路径、凭据、失败尝试），不记录就等于白做。

接口是否只在前端隐藏按钮、后端没校验？是否用可预测的 ID（自增数字、用户名）？改 HTTP 方法（GET→POST、POST→PUT）能否绕过？改路径（/api/user/1 → /api/user/1/../2）能否绕过？改 X-Forwarded-For、X-Original-URL 等头能否绕过？

每一项都应该在同一个账号持有另一个对象的前提下试一遍，而不只是在浏览器里换页面。

注入

数据被当成了代码 · 参数化查询之外没有解药

注入的本质是数据被当成了代码：应用把不可信输入拼接进解释器上下文（SQL、命令、模板、LDAP），输入中的特殊字符就改变了原有的语义结构。在左侧输入载荷，看黑名单变形后的结果——以及第二种防护为什么无解。

BYPASS LAB· 黑名单追着语法跑，参数化从根上断链
ROOT CAUSE

黑名单永远列不全：SELECT 可以写成 SeLeCt、SEL/**/ECT、/*!50000SELECT*/；空格可用 /**/、%09、() 替代；字符串可用 CHAR()、十六进制构造。参数化查询让 SQL 结构与数据在协议层就分离——数据永远不可能被解析为语法，这才是唯一根本解法。

SQL 注入类型特点检测方式
联合查询（UNION）直接把结果拼到页面上手工构造 UNION SELECT
报错注入通过错误信息回显数据构造会报错的函数
布尔盲注页面只返回"真/假"构造条件，观察页面差异
时间盲注页面无任何差异构造延时函数，观察响应时间
其他注入类型场景特点
NoSQL 注入MongoDB传对象而非字符串，如 {"$ne":null}
模板注入（SSTI）Jinja2、Twig、FreeMarker输入被当作模板表达式求值
LDAP 注入目录服务查询类似 SQL，用 *、)( 构造
表达式注入SpEL、OGNL常直接导致 RCE

输入一个能改变逻辑的值，看响应是否随之变化。

正常 ?id=1 → 返回 id=1 的内容；测试 ?id=1' → 报错（说明单引号被带进了 SQL）；测试 ?id=1 AND 1=1 → 正常；测试 ?id=1 AND 1=2 → 异常（说明条件被求值了，注入成立）。

命令注入同理：连接符 ;、|、||、&&、$()、反引号、换行——把 payload 垫在参数后面即可。

跨站脚本（XSS）

危害不是弹窗，而是在别人的浏览器里以别人的身份运行你的代码

XSS 的本质是用户输入被当作 HTML/JS 解析，而不是文本。一旦成立，攻击代码就跑在受害者域下——能读到该域的一切：Cookie、Token、DOM、已登录的接口。切换下面的三种类型，看注入的代码分别怎么到达浏览器。

XSS TYPES· 恶意脚本的三条通路
SEVERITY

反射型需要诱导点击，影响单次会话；DOM 型全程不经过服务端，WAF 根本看不到；存储型危害最高——代码存在数据库里，任何访问该页面的人都会中招，无需任何诱导，因此可以被写成蠕虫自我传播（典型如 2005 年的 Samy 蠕虫，20 小时内感染 100 万账号）。

类型存储位置触发方式危害
反射型（Reflected）不存储，随请求返回诱导受害者点击特制链接中
存储型（Stored）存在数据库任何人访问该页面即触发高（可蠕虫化）
DOM 型（DOM-based）不经过服务端前端 JS 把不可信数据写入 DOM中高
危险 Sink

innerHTML 会把字符串当作 HTML 解析；document.write()、eval()、setTimeout(str)、new Function()、jQuery 的 $(location.hash) 同理。

Vue 的 v-html 与 React 的 dangerouslySetInnerHTML——名字已经把危险写在脸上了。

相对安全的 Sink

textContent / innerText 只当文本，浏览器不会解析其中的标签。

现代框架的默认插值（{{ }} / JSX 表达式）也是自动转义的——除非你主动调用危险 API。

防御手段说明缓解什么
输出编码按上下文编码：HTML、属性、JS、URL、CSS 各不相同根本（让脚本永远无法被解析）
CSP限制可执行脚本的来源与内联即使注入也跑不起来（纵深）
HttpOnly Cookie禁止 JS 读取 Cookie注入成功后偷不到会话
输入校验白名单优于黑名单辅助（不能替代输出编码）

因为触发点太多：每一个把用户数据渲染到页面的位置都是潜在入口——用户名、搜索词、评论、文件名、错误回显、跳转 URL、甚至 UA 头写进日志后台。

而且现代前端框架默认转义，但 dangerouslySetInnerHTML、v-html 又把门打开了；富文本编辑器这类"必须渲染 HTML"的场景，永远需要单独的白名单过滤。

所以实战中，XSS 的发现主要靠人工测试 + 代码审计，扫描器只能覆盖最基础的 <script> 反射。

PATTERN

系统渗透与提权

找"以更高权限运行的东西"，然后滥用它

拿到一个 low-priv shell 只是开始。提权不是"找一个漏洞"，而是"找一条路径"——而且配置类问题（sudo、SUID、定时任务）远比内核漏洞常见、稳定、不易被发现。点击排查顺序中的每一步，看它查什么、怎么被滥用。

PRIVESC PATH· 从 shell 到 root
ORDER

合理顺序：先 sudo -l（最快）→ 再看 SUID + GTFOBins → 再看定时任务与服务 → 最后才考虑内核漏洞。新手常犯的错误是死磕内核漏洞（编译、试错、把机器搞崩），而实际上 80% 的提权来自权限配置错配，不是代码 bug。

Shell 的选择

反弹 Shell：目标主动连接攻击者监听端口。因为目标通常有出站权限、入站被防火墙挡住——这是默认选择。

Bind Shell：目标监听端口，攻击者连进去。适用于入站开放、出站受限的场景。

TTY 升级：反弹得到的通常不是 TTY，su/vim/top 用不了、Ctrl+C 会杀掉 Shell。需要用 python3 -c 'import pty;pty.spawn("/bin/bash")' 之类的方式升级。

Windows 高频入口

同样以配置错配为主：某服务以 SYSTEM 运行但程序目录普通用户可写；某计划任务以 SYSTEM 运行但脚本可改；某注册表自启动键普通用户可写。

SeImpersonatePrivilege：允许进程模拟 SYSTEM 令牌，IIS/SQL Server 服务账号默认持有——"土豆"系列（JuicyPotato、PrintSpoofer、GodPotato）就是让系统连接攻击者控制的命名管道，再模拟连接者令牌。

快速收集：whoami /all、systeminfo、schtasks /query /v、cmdkey /list。

密码攻击

在线爆破：针对登录接口（Hydra、Medusa、Burp Intruder）。密码喷洒：少量弱口令试大量账号，避开单账号锁定。离线破解：拿到哈希后本地跑（Hashcat、John）。彩虹表：查预计算表，对加盐无效。凭据填充：用泄露库试其他系统。

破解速度

MD5（Hashcat 0）：百亿/秒。NTLM（1000）：极快。SHA-256（1400）：快。bcrypt（3200）：千/秒。Kerberos TGS etype23（13100）：快（RC4-HMAC）。

这就是"口令存储必须用慢哈希"的原因——把破解时间从几小时拉长到几百年。

常见提权路径

Linux：SUID 滥用（GTFOBins）· sudo 可执行 vim/less/find · 内核漏洞（DirtyPipe、PwnKit）· 定时任务脚本可写 / PATH 劫持 / 通配符注入 · systemd 服务文件可写 · LD_PRELOAD 劫持 · 可写 /etc/passwd · NFS no_root_squash · 在 docker 组等于 root。

① 确认漏洞存在（版本匹配、PoC 验证）② 选择载荷（反弹 shell / 命令执行 / 上传文件）③ 执行并建立通道 ④ 稳定 Shell（TTY 升级）⑤ 收集信息（whoami、系统版本、网络、进程）⑥ 提权 ⑦ 持久化。授权测试中第 ⑦ 步通常不做，除非明确要求。

[ L4 / INTNET / AD · KERBEROS ]

内网与域渗透

进入内网后，防线往往比边界弱得多

内网是渗透测试中最能体现水平的部分。域控（DC）集中存储所有凭据，域控沦陷就等于整个域沦陷——即使改掉所有用户口令，攻击者仍能用黄金票据回来。点击攻击链中的环节，看从普通域用户到域管的经典路径。

KERBEROS CHAIN· 票据即凭据
WHY IT WORKS

Kerberoasting 之所以任何域用户都能发起，是因为请求服务的 TGS 票据本身就是正常业务行为。票据用服务账号的 NTLM 哈希加密，攻击者拿回去离线破解——服务账号往往是"服务专用"，口令长期不换且权限偏高。相比之下 DCSync 直接模拟 DC 间的目录复制，一步拉取全部账号哈希。

Kerberos 攻击原理前提
Kerberoasting请求某服务的 TGS 票据，票据用服务账号哈希加密，可离线破解任意域用户
AS-REP Roasting对未开启预认证的账号请求 AS-REP，可离线破解目标账号关闭预认证
黄金票据伪造 TGT，用 krbtgt 哈希签名拿到 krbtgt 哈希
白银票据伪造 TGS，用服务账号哈希签名拿到服务账号哈希
委派滥用利用非约束/约束/RBCD 委派获取高权限存在委派配置
凭据在哪里

LSASS 进程内存：明文口令、NTLM 哈希、Kerberos 票据。SAM：本地账号哈希。NTDS.dit：域内所有账号哈希（DC 上）。GPP 的 cpassword：组策略首选项里的本地管理员口令，可解密。浏览器保存的密码、web.config、appsettings.json、.env、页面文件与崩溃转储、.kirbi 票据缓存。

进内网后第一优先级就是拿到更多凭据——凭据是横向移动的钥匙。

传递的两种形式

Pass-the-Hash：用 NTLM 哈希直接认证，无需明文口令。因为 NTLM 挑战-响应中客户端只需要哈希就能算出响应值——拿到哈希等于拿到口令。

Pass-the-Ticket：用窃取的 TGT/TGS 直接访问服务，连哈希都不需要。

因此防御上要：禁用 NTLM、启用 Credential Guard、定期轮换 krbtgt（需重置两次）、限制 LSASS 读取。

横向移动技术说明检测特征
PsExec通过 SMB 创建服务执行7045 服务安装、PSEXESVC
WMI远程执行命令4688 进程创建，父进程为 WmiPrvSE
WinRMPowerShell 远程5985 端口连接、4104 脚本块

ACL 滥用

AD 的权限关系极其复杂（几万对象、几十万条 ACL），人脑无法穷举，而攻击路径常藏在一条不起眼的 ACL 里。

GenericAll（完全控制：改密码、加组、设 SPN）· GenericWrite（写属性：设 SPN 后 Kerberoasting）· WriteDacl（给自己加权限）· WriteOwner（接管对象）· ForceChangePassword（重置目标口令）· AddMember（加入高权限组）。

单独看都没问题，串起来就是一条通往域管的路。

隧道与代理

只有一台机器能出网时，要把流量带进去：SSH 动态转发（ssh -D 1080，最简单的 SOCKS5）· Chisel（反向 SOCKS）· ligolo-ng（基于 TUN 接口，建虚拟网卡直接路由，不需要 proxychains）· HTTP 隧道（只允许 HTTP 出网）· DNS 隧道（极端受限，慢）。

配合使用：proxychains4 nmap -sT -Pn 10.0.0.0/24。

检测重点因此非常明确：4624 登录类型 3（网络登录）的源 IP 与目标不匹配（如工作站 → 工作站）；4648 显式凭据登录；4672 特殊权限分配出现在非管理员常规操作时间；短时间内同一账号登录多台机器；服务安装事件（7045）集中在非维护窗口。

BloodHound 的真正价值不只是给攻击者找路径，更是让防御方看清自己域内的隐形信任关系——很多企业分析后才发现：一个实习生账号，通过 4 层跳转就能拿到域管。

报告撰写

客户买的不是"你打进去了"，而是一份能指导修复的报告

报告是渗透测试的最终交付物，也是唯一会被留存、被传阅、被拿去申请预算的东西。左边的写法客户看完不知道有多严重、影响什么、怎么修；右边的写法每一项都可验证、可执行。切换对比看差距。

REPORT QUALITY· 同样的发现，两种写法
READER

一份报告至少要服务三类读者：管理层要看整体风险评级与关键发现（执行摘要，1–2 页）；技术管理者要看范围、方法与攻击路径；开发人员要看完整、可复现的漏洞详情。写之前先想清楚"这段是给谁看的"。

章节内容读者
执行摘要整体风险评级、关键发现、核心建议（1–2 页）管理层
测试范围与方法测试了哪些资产、用了什么方法、时间窗口技术管理
风险统计各等级漏洞数量、分布管理层
漏洞详情每个漏洞的完整描述技术人员
攻击路径从入口到目标的完整链条技术管理
修复建议汇总按优先级排列的整改清单项目负责人
附录工具清单、原始数据、术语表备查
漏洞描述六要素

① 名称：准确具体（"SQL 注入"优于"注入漏洞"）。② 风险等级：CVSS 分数 + 业务影响说明。③ 位置：完整 URL / 参数 / 组件。④ 复现步骤：让客户自己也能复现。⑤ 影响：用业务语言而非技术语言描述后果。⑥ 修复建议：具体、可执行、分层（根本修复 + 临时缓解）。

最常见的五个问题

只写技术细节不写业务影响 → 管理层看不懂，不批预算。风险等级虚高 → 客户失去信任，报告被弃用。修复建议写"加强安全意识" → 无法执行。没有复现步骤 → 开发无法验证。漏洞数量堆砌 → 掩盖了真正重要的问题。

渗透测试的水平，不体现在"能打穿多少靶机"，而体现在两件事：一是遇到打不动的地方，知道下一步该查什么；二是打穿之后，能说清楚这意味着多大的业务风险。

前者靠方法论，后者靠对业务的理解。两者都不是靠刷靶机能刷出来的。

如何选择方向

三个判断维度 · 两周低成本验证 · 兴趣 > 基础 > 市场

专项能力的价值，体现在"别人做不到的事"上。学每个方向时都要问自己：这个方向里，什么事情是只有做过大量实践的人才能做到的？那就是你的目标，而不是"我会用这个工具"。

DIRECTION PICKER· 拖动三个维度，看推荐方向
HOW TO READ THIS

三个维度不是"打分越高越好"，而是权重的排序。当三者冲突时，优先级是 兴趣 > 基础 > 市场：安全是长周期行业，靠"市场热"驱动的人通常在第二年就转行了。把兴趣调到最低、市场调到最高，你会发现推荐结果变成"岗位多但天花板中等"的方向——这正是很多人三年后卡住的原因。

方向岗位数量入门难度天花板适合什么人
云安全多（增长最快）中高有运维/开发背景，喜欢系统性思考

先用两周做一次小验证，用真实体感替代想象：恶意代码分析 —— 分析 3 个公开样本，写 3 份报告，感受"能不能忍受这种枯燥"；逆向 —— 完成 picoCTF 的 5 道 reversing 题；云安全 —— 用 CloudGoat 打完 5 个场景；移动 —— 用 jadx 反编译 3 个 App，找出 1 个硬编码密钥；工控 —— 用 Conpot 搭环境，抓包解析 Modbus。

两周后只问一个问题：这个过程是"痛苦但有趣"，还是"纯粹痛苦"？ 前者可以继续，后者趁早换——沉没成本远小于三年的机会成本。

兴趣决定能不能坚持 3 年：不看教程的时候，你会主动研究什么？基础决定入门速度：你之前的经验更贴近哪个方向？市场决定能不能就业：你所在城市/目标行业，哪个方向有岗位？

注意"市场"这一项的时效性：岗位数量是当下的，而你要投入的是未来三年。云安全现在岗位最多，但五年后可能已经饱和；工控岗位少，却因为稀缺而难以替代。

恶意代码分析：流程与环境

六步流程 · 隔离环境的四条硬性要求 · 反分析对抗

核心产出永远是三样：这是什么、它做了什么、怎么检测它。所有工具都服务于这三句话——写不出这三句，分析就没有完成。

ANALYSIS PIPELINE· 点击每一步看输入 / 产出 / 陷阱
ISOLATION FIRST

第一步永远是隔离：Host-Only 网络、分析前打快照、不挂载宿主机目录、不共享剪贴板。再加一层假网络（INetSim / FakeNet）模拟 DNS 与 HTTP——很多样本检测不到网络就直接退出，你以为它"无害"，其实它只是没醒。

岗位日常
病毒分析工程师分析样本，输出家族归属、行为、IOC
威胁情报分析师从样本中提取 TTP，关联 APT 组织
检测工程师把分析结果转成 YARA / Sigma 规则
应急响应支持判断"这台机器上的东西是不是恶意的"

① 完全隔离：Host-Only 网络，不能访问生产环境。② 可回滚：分析前打快照，分析后回滚——样本改的东西可能包括引导区。③ 无共享：不挂载宿主机目录、不共享剪贴板，否则样本可以直接写到你的真实磁盘。④ 假网络：用 INetSim 或 FakeNet 模拟 DNS/HTTP，让样本"以为"自己联网了，避免它因断网而不触发行为。

很多样本有反分析检测：看 MAC 前缀、注册表、进程名、CPU 核数。所以环境要尽量"像真的"——这也是为什么专业团队会维护多套不同配置的分析机。

PE 结构与静态分析

不要相信扩展名 · 节表与熵 · 导入表推断意图 · CAPA

不要相信扩展名。先 file 看真实类型、sha256sum 算哈希去查情报、strings -n 8 抓明显线索——这三步三十秒，能省掉半小时的无效分析。

PE ANATOMY· 点击节区看熵与异常 · 点选 API 组合推断行为
ENTROPY TELLS THE TRUTH

熵衡量数据随机性，范围 0–8：正常代码约 5–6，加密或压缩数据接近 7.5–8.0。一个节的熵突然很高，通常意味着它被加密了。但注意——高熵也可能是正常的资源（图标、压缩过的字符串表），所以要看"哪个节"高，而不是"文件"高。

节名内容异常信号
.text代码可写（W+X）是加壳特征
.data已初始化数据—
.rdata只读数据（含导入表）—
.rsrc资源（图标、字符串）藏有额外 PE 文件
.reloc重定位信息—
异常节名如 .UPX0、.aspack、.malz加壳或手工构造

导入表记录程序调用了哪些外部 DLL 的哪些函数。从 API 组合能推断程序意图，而且这个推断不依赖你是否看得懂汇编：VirtualAlloc + VirtualProtect + CreateThread 说明要在内存里执行代码；CreateRemoteThread + WriteProcessMemory 是进程注入；CryptEncrypt + 遍历文件是勒索；URLDownloadToFile + WinExec 是下载执行。

反调试的 IsDebuggerPresent 出现在导入表里，本身就是一条情报：这个样本预期会被分析。

CAPA 由 Mandiant 开源，基于规则识别可执行文件的能力（capability）：创建进程、注入代码、持久化、反调试……输出直接映射到 ATT&CK 技术。它的价值是把"读汇编"这件高成本的事，换成"读能力清单"，让你在几分钟内决定这个样本值不值得深入。

① 加壳/混淆后看不到真实逻辑——字符串被加密、导入表被隐藏。② 动态加载的 API 看不到——样本用 LoadLibrary + GetProcAddress 在运行时解析函数，导入表里只有这两个。③ 代码可以在运行时生成——内存中的代码在静态文件里根本不存在。所以静态分析只能"猜意图"，要确认必须做动态分析。

动态分析与沙箱对抗

动态分析看的是行为，不是代码。样本可以把自己加密得面目全非，但一旦运行就必须落地文件、改注册表、连网络——这些动作藏不住。

SANDBOX EVASION LAB· 勾选样本会做的检测，看它是否执行

"沙箱没报毒"不等于"样本无害"。样本可能只是没醒：检测到虚拟化、等过了观察窗口、或者需要一个特定的用户交互才触发。专业做法是换环境复跑（不同 CPU 核数、不同用户名、带鼠标移动），而不是相信单次结果。

① 进程树：谁启动了谁——Office → cmd → powershell 是典型恶意链。② 落地文件：写到哪些路径——%TEMP%、%APPDATA%、ProgramData 是高频位置。③ 注册表：改了哪些键——Run、Services、IFEO。④ 网络：连了哪些 IP/域名，用了什么协议。⑤ 权限：有没有尝试提权、有没有访问 LSASS。

YARA 规则与加壳脱壳

规则三要素 · 好规则与坏规则 · 熵与 OEP · 脱壳五步

分析的最后一步是把结论变成可执行的检测。写不出规则的分析，只完成了一半——因为下一个人还得从头再来一遍。

YARA BUILDER· 勾选特征，看规则如何拼出来、命中哪些样本
FALSE POSITIVE IS THE REAL COST

一条规则写出来只要十分钟，验证误报要一整天。上线前必须拿几百个正常文件跑一遍；在 EDR 里一条误报规则可能让整个公司的终端告警爆炸，最终导致"规则被整体关掉"——这比没有规则更糟。

好规则坏规则
匹配稳定的特征（算法常量、独特字符串）匹配容易变的（C2 域名、IP）
组合多个条件单字符串匹配（误报高）
有 meta 说明来源与用途无任何说明
在良性样本集上测试过没测过误报
区分家族/变种一条规则覆盖所有

识别特征：节名异常（.UPX0、.aspack、.themida）；节数量少但虚拟大小远大于原始大小；导入表极小（只有 LoadLibrary、GetProcAddress）；入口点不在 .text 节；熵值接近 8.0。

脱壳五步：① 识别壳类型（DIE / PEiD）→ ② 已知壳用专用工具（UPX -d）→ ③ 未知壳动态调试找 OEP（ESP 定律、内存断点、单步跟踪）→ ④ dump 内存镜像 → ⑤ 修复导入表（Scylla、ImportREC）。

基本信息（文件名、MD5/SHA1/SHA256、大小、类型、编译时间）→ 静态特征（节信息、导入表、字符串、加壳、签名）→ 行为分析（进程、文件、注册表、网络、权限）→ 能力映射（ATT&CK 编号）→ IOC（域名、IP、路径、注册表键、互斥量）→ 家族归属 → 检测建议（YARA / Sigma / 狩猎思路）→ 结论（这是什么、危害多大、影响范围）。

逆向基础：调用约定与栈帧

寄存器传参 · 栈帧结构 · ret 为什么是溢出的核心

逆向是安全领域门槛最高的方向：要能读汇编、理解编译器优化、掌握内存布局与调用约定，还要有极强的耐心——一个函数可能要看几小时。回报也是最高的：能发现别人发现不了的漏洞。

STACK FRAME LAB· 切换 Windows / Linux 约定，拖动输入长度看覆盖
WHY RET MATTERS

ret 从栈上取返回地址并跳转——如果栈被溢出覆盖，就能控制执行流。这是栈溢出的本质：不是"程序崩了"，而是"程序按你写的地址跳了"。理解这一点，后面所有的保护机制（Canary、ASLR、NX）才有意义——它们防的都是"让你写不进、或写进去也用不了"。

第 2 个参数RDX
第 3 个参数R8
第 4 个参数R9

push rbp 保存调用者的栈基址 → mov rbp, rsp 建立当前栈帧 → sub rsp, 0x40 分配局部变量空间 → … → leave（等于 mov rsp, rbp; pop rbp）→ ret 弹出返回地址并跳转。

安全意义全在最后一条：返回地址存在栈上，和局部变量是邻居。所以一个没有边界检查的 strcpy，就能把"数据"写成"下一条指令的地址"。

缓冲区溢出（写入越界，覆盖相邻数据）· UAF（释放后仍被使用，攻击者可重新占用该内存）· 堆溢出（堆上缓冲区越界写）· 整数溢出（运算超范围，导致分配大小算错）· 格式化字符串（printf(user_input) 导致任意读写）· 类型混淆（把 A 类型对象当 B 用）。

保护机制 · Fuzzing · 漏洞利用

现代漏洞利用不是"写 shellcode 跳过去"，而是一层层拆掉保护。先看清楚哪几层开着，再决定用哪条路——这比背 exploit 模板重要得多。

MITIGATION MATRIX· 开关保护，看攻击路径怎么被堵住 / 被绕过
DEFENSE IN DEPTH, IN ONE PICTURE

五种保护不是"随便开几个"，而是各自堵一条路：NX 堵"直接执行栈上代码"，ASLR/PIE 堵"写死地址"，Canary 堵"悄悄改返回地址"，RELRO 堵"改 GOT 表"。全部开启时，攻击者必须先泄露、再 ROP、再绕过 canary——每一步都会留下更多痕迹。

四类：基于变异（对已有样本随机变异）· 基于生成（按格式规范生成）· 覆盖率引导（用插桩反馈引导变异方向，AFL 系列）· 协议感知（理解协议结构，效率更高）。

流程：确定目标 → 准备种子 → 编译插桩（afl-clang-fast）→ 运行 → 监控 crashes 目录 → 去重分类复现 → 评估可利用性。现实是：大部分崩溃不可利用（空指针、断言失败占多数），找到有价值的漏洞可能要几天到几周，种子质量直接决定效率。

发现崩溃只是起点。判断可利用性要看四件事：崩溃时寄存器是否可控（特别是 RIP/EIP）；是否能控制写入的地址和内容；是否有信息泄露（绕过 ASLR）；目标进程的权限（是否值得利用）。

真实项目中，90% 的崩溃最后被判定为"不可利用"。这也是这个方向"投入产出比低"的原因——但反过来，能做出可利用链的人也就极其稀缺。

这是最危险的想法。云上 95% 以上的安全事件，根因在客户侧配置：存储桶设为公开、安全组开放 0.0.0.0/0 到 3389、IAM 用户拥有 *:*、访问密钥硬编码在代码里并推到 GitHub、元数据服务未限制。

共享责任模型一句话：厂商负责"云的安全"，客户负责"云中的安全"。越往上（IaaS → SaaS），厂商承担越多；但数据和身份，永远是客户的责任。

云上推荐的凭据形式是临时凭据：有效期短（几分钟到几小时）、自动轮换、权限受限。实现方式：实例角色（EC2 Instance Profile）、任务角色（ECS Task Role）、工作负载身份（K8s ServiceAccount + IRSA / OIDC）。

判断一个云账号是否成熟，最简单的指标就是：还有没有长期 AccessKey 在用。

Modbus 设计于 1979 年，假设运行在物理隔离的串行总线上。它没有任何认证机制——任何能连上 502 端口的人，都可以读取所有寄存器、写入任意值。这意味着：如果一台 PLC 暴露在公网（Shodan 上大量存在），任何人都能让它停机或改变设定值。

防护只能靠网络隔离，协议本身无法加固。这是"设计时没考虑安全"的典型代价——四十年后仍然无法修补。

事件发生的那一刻，现场只有两样东西可用：你手上已有的数据，和你能联系到的人。四句反问就能测出一个组织的应急水位——

① 有没有资产清单？不知道有哪些机器，就无法评估范围，只能一台台问。② 有没有日志？没有日志就无法还原时间线，只能靠猜。③ 有没有联系人？不知道找谁（业务负责人、法务、云厂商、监管），黄金时间就耗在内部找人上。④ 有没有演练过？第一次处理必然手忙脚乱——演练的唯一目的，就是把「第一次」提前到没有压力的时候。

一份好的 Playbook 会把「遇到这种情况该做什么」从「靠人临场判断」变成「按清单执行」，但真正体现经验的不是那 19 条动作，而是每条动作前面的判断条件。

例如：「如果备份在域内且可写 → 视为已污染，不可用于恢复」；「如果失陷主机有域管登录记录 → 立即评估全域凭据重置」；「如果样本检测到虚拟化环境 → 换环境复跑，不要直接判定无害」。这些条件写不出来，Playbook 就只是一份好看的操作手册。

另一个常被忽略的点：Playbook 必须写「谁有权做这个决定」。断网、禁用高管账号、全公司改密码——这些动作的授权人必须在事前就定好，而不是在凌晨三点临时打电话找人签字。

检测与分析

研判五问 · 时间线的三个陷阱 · 影响范围的四个方向

拿到一条告警，第一件事不是立刻处置，而是判断真假。误报处置的代价不只是浪费人力——你会在无关的机器上断网、禁号、重装，然后真正的失陷主机继续安静地外传数据。

TRIAGE & TIMELINE· 回答五个问题得出结论 · 切到时间线看时区陷阱
TIME IS A LIAR

同一分钟内，防火墙、DNS、EDR、文件系统给出的时间可能完全不同：设备时区不一致、NTP 没同步、日志写的是本地时间。如果你直接按日志里打印的时钟排序，会得到一个因果颠倒的故事——「DNS 查询」排在「进程启动」前面，看起来像先解析域名再执行，实际上正好相反。构建时间线的第一步永远是统一时区。

① 员工报告。很多事件最早是员工发现的——电脑卡、弹窗、文件打不开、鼠标自己动。但如果没有一个「往哪报」的渠道，这些信号就消失了。建立一条「可疑邮件 / 电脑异常」的上报入口，成本极低，回报极高。

② 外部通报。客户说「你们的数据在暗网」，往往比内部检测更早。这也意味着：你的检测能力可能还不如外部观察者。收到这类通报时，第一个动作不是辩解，而是去验证。

第 ⑤ 问最容易被跳过，但它决定了你有多紧急。同一个「可疑外联」，发生在测试机和生产数据库上，是完全不同的两件事。

遏制、根除与恢复

五种遏制策略的取舍 · 为什么建议重装 · 恢复后二次失陷

遏制是整个响应里唯一必须同时向业务和技术交代的环节。断网能止住扩散，也会停掉产线；禁号能阻断凭据滥用，也可能禁掉正在签合同的高管。没有标准答案，只有权衡。

CONTAINMENT MATRIX· 选一种遏制方式，看它的阻断力与业务代价
EVIDENCE BEFORE ACTION

「先断网」是最常见的错误直觉。断网会让攻击者发现失联，可能立即触发破坏逻辑（勒索软件马上加密）；同时重启或断网会改变内存里的证据。正确顺序是：先采易失数据 → 再决定遏制方式 → 遏制时保留一条调查通道。顺序错了，你可能既没止住损失，也丢了唯一能说清「发生了什么」的证据。

策略优点缺点适用
隔离主机快速止住扩散影响该主机业务确认失陷的单机
隔离网段阻断横向影响面大多台失陷
禁用账号阻断凭据滥用影响用户工作账号确认失陷
阻断 C2切断控制通道攻击者可能换地址已知 C2
全量断网最彻底业务全停极端情况（勒索扩散中）

遏制分短期与长期：短期是立即止血（隔离、断网、禁用账号），长期是临时加固（加规则、加监控），在恢复前维持住。只做短期不做长期，攻击者换个入口就回来了。

断网有三个副作用：① 攻击者发现失联，可能触发破坏逻辑（勒索软件检测不到 C2 就立刻加密）；② 丢失内存证据，重启或断网会让内存里的连接、密钥、无文件载荷消失；③ 业务损失可能超过攻击本身。

所以正确顺序通常是：先采集关键易失数据（内存、网络连接、进程列表）→ 再决定遏制方式 → 遏制时保留远程访问通道（用于后续调查）。第三点常被忘：把机器隔离得干干净净，然后自己也进不去了。

根除 · 检查项内容

对确认失陷的主机，业界共识是重装系统。原因很朴素：你无法 100% 确认找到了所有后门。攻击者可能有你不知道的持久化方式——固件、UEFI、隐藏分区、合法工具的配置文件。清理后的机器在心理上仍然「可疑」，没人敢把它放回生产。

例外是业务无法重装的核心系统（老旧工控机、无法停机的数据库）：只能做深度清理 + 加强监控 + 网络层严格隔离，并接受「它仍然可能被控」这个风险。

恢复的三个前提：① 威胁已根除（不是「暂时没活动」）；② 备份是干净的（备份可能已被污染）；③ 入口已修复（否则恢复后会被再次打穿）。三条缺一条，恢复就是在给攻击者第二次机会。

真实案例里，「恢复后一周又被加密」非常常见，原因几乎总是这四个：入口没修（漏洞还在、弱口令没改）、凭据没全改（攻击者用旧凭据回来）、备份本身带毒（恢复了被感染的系统）、还有未被发现的其他失陷主机（重新横向）。

所以恢复前必须做一次入口验证：明确说出「最初进来的那个通道，现在为什么关上了」，说不出来就不要恢复。

事后产出内容读者

改进项清单具体、可执行、有责任人与时限项目负责人

复盘的目的是改进系统，不是追责。如果复盘变成批斗会，下次就没人愿意报告事件了——这会导致更严重的后果：事件被隐瞒，直到藏不住的那天。

好的复盘只问三个问题：① 这次事件中，我们做对了什么？（要保留）② 哪些环节比预期慢？为什么？③ 如果再来一次，我们会怎么改？

主机取证：易失性顺序与内存

RFC 3227 采集顺序 · 内存里有什么磁盘上没有的 · Volatility 3

取证的第一原则是不能修改原始证据，第二个原则是按易失性从高到低采集——因为最值钱的东西，往往最先消失。一次重启，就把「攻击者执行了什么命令」变成永远查不出来的谜。

VOLATILITY LAB· 点易失性层级看能取到什么 · 选插件看内存里的输出
PSLIST LIES, PSSCAN DOESN'T

pslist 沿着内核的进程链表走，攻击者把进程从链表里摘掉（DKOM）它就看不见；psscan 直接扫内存池，按进程对象的结构特征去找——已终止的、被隐藏的进程都会浮出来。两者的差集，就是「有人不想让你看到的进程」。这也是内存取证最经典的一招。

1. 寄存器、CPU 缓存 2. 内存（RAM） 3. 网络连接、ARP 缓存、路由表 4. 运行中的进程 5. 临时文件系统 6. 磁盘 7. 远程日志 8. 归档介质（备份、磁带）

内存里有磁盘上根本没有的东西：① 明文口令与密钥（LSASS 里的哈希、Kerberos 票据、TLS 会话密钥）；② 解密后的恶意代码（无文件攻击的载荷只在内存里存在过）；③ 网络连接（含已关闭连接的残留，能看到它连过哪里）；④ 进程注入的证据（合法进程里多出来的可执行内存段）；⑤ 命令行参数（攻击者执行的完整命令，包括那些没有落到任何日志里的）。

一旦重启，这五样全部消失。所以「先重启试试」是取证里最贵的四个字。

磁盘取证与证据链

写保护 · Windows / Linux 关键取证位置 · Prefetch 与 USN · 哈希与证据链

磁盘取证解决的是「过去发生过什么」。它不像内存那样一断电就没，但也正因如此，它更容易被取证动作本身污染——挂载即修改，访问即留下时间戳。

ARTIFACT MAP· 切换系统点目录看取证价值 · 试着篡改证据看哈希断裂
HASH OR IT DIDN'T HAPPEN

采集前算一次哈希，分析前再算一次，两者一致才能证明「证据没被改动」。很多真实案例里，证据因为没有哈希记录而在内部调查中失去说服力——不是因为它被改过，而是因为无法证明它没被改过。这就是证据链的全部意义。

哈希不是「防篡改」，而是「可证明有没有被篡改」。采集前算一次，分析前再算一次，两者一致，就能证明从采集到分析这段路上证据没被动过。

这条链一旦断了，技术上再漂亮的分析也站不住：你无法向管理层、法务或法庭证明「你分析的就是现场的那份数据」。所以哈希要在采集的第一分钟算，而不是在写报告的时候补。

网络取证

主机取证回答「这台机器上发生了什么」，网络取证回答「它和谁说过话」。后者的价值在于：主机上的日志可以被清除，但网络设备的记录通常不在攻击者能碰到的范围内。

威胁情报

情报四级金字塔 · 为什么 IOC 最不值钱 · STIX / TAXII 与情报落地

情报的价值不在于「知道得多」，而在于能改变你的某个决定。一份没有落地成规则、没有改变优先级、没有指导狩猎的情报，只是一篇读物。

INTEL PYRAMID· 点层级看使用者、生命周期与「半衰期」
TACTICAL DECAY

越往塔底，情报越具体、越好用，也越快过期：一个 IP 可能几小时就失效，一个哈希重新编译就变。越往塔顶，越抽象、越难直接用，但能管好几年——「这个组织习惯用 Kerberoasting 拿服务账号」这种判断，不会因为换个域名而失效。所以真正值钱的是 TTP，这也是 ATT&CK 存在的理由。

层级内容使用者生命周期
战略情报威胁趋势、行业态势、攻击者动机管理层年
运营情报攻击活动、campaigns、TTP安全运营月
战术情报攻击者使用的技术与工具检测工程周–月
技术情报IOC（IP、域名、哈希）自动化系统小时–天

因为 IOC 极易变化：攻击者换个域名、重新编译样本，IOC 就失效了。你把一百个 IP 加进黑名单，攻击者换一批就全废了——而且你还会有一种「我做了防护」的错觉。

真正有价值的是 TTP——攻击者的行为模式。一个实用的判断：如果一份情报只给了你一堆 IP，它的价值是「小时级」；如果它告诉你「这个组织习惯用 X 方式建立持久化」，价值是「年级」。

这不是说 IOC 没用——它便宜、可自动化、能挡住「没换基础设施」的那批攻击者。正确的做法是把 IOC 当消耗品，把 TTP 当资产。

四条路径对应四种不同的「动作」：阻断（IOC）、检测（TTP）、搜索（画像）、投资（态势）。一条情报如果一条路径都走不通，那它对你的组织就没有价值——不管它看起来多专业。

[ L6 / HUNTING ]

威胁狩猎

假设驱动 · 六步流程 · 成熟度 L0–L4 · 「没发现」也是产出

威胁狩猎的前提假设是：已经有攻击者在你网络里，只是你的检测没发现。它和监控的根本区别只有一句话——监控是「等告警」，狩猎是「主动去找」。

HUNT LAB· 拼一个假设，看它够不够「可验证」· 再走一遍结果分支
A HYPOTHESIS YOU CAN KILL

好的假设必须可被数据证伪：「看看有没有异常登录」不是假设，因为它永远无法被判定为「不成立」。而「如果发生了 Kerberoasting，那么 4769 事件中会出现同一用户在短时间内请求多个不同 SPN 的服务票据，且加密类型为 RC4」——这条能被一条查询直接证实或推翻。能杀死它的证据，才是好假设。

1. 提出假设（基于情报、ATT&CK、业务特点） 2. 确定数据源（需要哪些日志） 3. 编写查询（在 SIEM / EDR 中检索） 4. 分析结果（区分正常与异常） 5. 验证结论（找到就升级为事件） 6. 沉淀（把有效的查询变成检测规则）

好的假设：「如果攻击者使用了 Kerberoasting，那么在 4769 事件中，会出现短时间内同一用户请求多个不同 SPN 的服务票据，且加密类型为 RC4。」——有行为、有数据源、有可量化的判据。

坏的假设：「看看有没有异常登录。」——太模糊，无法验证。跑完之后你既不能确认「有」，也不能确认「没有」，等于什么都没做。

两者的差别不在措辞，而在于后者跑完不产生任何可沉淀的东西。狩猎的最后一步是「沉淀」，而坏假设连第一步都过不去。

假设的来源例子
威胁情报某 APT 组织近期使用某技术，检查我们是否中招
ATT&CK 覆盖度某个战术我们完全没有检测，主动去查
行业事件同行业公司被某手法攻击，自查
业务特点我们有大量 RDP 暴露，重点查 RDP 相关
红队报告上次演练中红队用了什么手法，查是否还有残留
成熟度特征
L0 初始依赖厂商情报，只做 IOC 匹配
L1 最小有少量自定义检测规则，能按 ATT&CK 检索
L2 程序化有标准狩猎流程，定期执行，有数据支撑
L3 创新能发现新 TTP，产出可共享的情报
L4 领先自动化狩猎，与红队深度协同

大部分狩猎的结果是「没发现异常」。这看起来像白干，但实际产出有三样：① 验证了检测能力（这个方向我们能看到）；② 建立了基线（正常是什么样）；③ 发现了数据缺口（这个查询跑不出来，因为根本没采这个日志）。

第三个产出最有价值——它直接推动日志建设的完善。很多组织的日志采集清单，就是被一次次狩猎「逼」出来的：想查但查不到，才会去补。

反过来说，如果一次狩猎「没发现异常」，你也必须回答一个问题：是「真没有」，还是「看不到」？ 分不清这两者，就会把数据缺口误当成安全。

检测工程

检测四层次与 70/20/10 配比 · Sigma 工程实践 · 检测即代码 · 覆盖度评估

检测工程是把「攻击行为」翻译成「可执行的检测逻辑」的工程实践。它是威胁狩猎与安全运营之间的桥梁——狩猎发现的 TTP，最终要沉淀成一条能自动跑的规则，否则下次还得靠人再找一遍。

DETECTION PIPELINE· 拼一条 Sigma 规则 · 点 ATT&CK 格子看覆盖状态
TTP OVER IOC

合理的检测配比是 TTP 为主（70%）、IOC 为辅（20%）、异常检测补充（10%）。原因：IOC 只能抓「已知的、没换基础设施的」攻击者；TTP 能抓「同一手法的新攻击者」；异常检测误报高，但它是唯一有可能发现全新攻击的一层。三层都要有，但不能等量齐观。

没有这套机制时，规则通常有四个结局：存在某人的 SIEM 界面里，没有版本记录；改坏了无法回滚；离职后无人维护；没人知道某条规则是谁、为什么写的。

有了版本管理后，「为什么这么写」「什么时候改过」「谁改的」「当时为什么这么调」都有据可查。这和普通软件工程没有区别——检测规则本质上就是运行在安全系统里的代码，它值得同等的工程纪律。

追求 100% 覆盖的代价极高，且不现实。合理的策略是：① 先覆盖高优先级技术（行业中真实出现过的）；② 优先覆盖攻击链关键节点（初始访问、执行、持久化、凭据访问、横向移动）；③ 接受某些技术「只记录不告警」；④ 定期用紫队演练验证覆盖的有效性。

阶段验收与作品

28 道自测 · 一份可复盘的调查报告 · 把流程跑成肌肉记忆

应急响应这门手艺，考的不是「你知道什么」，而是「你在压力下还能想到什么」。所以这一章的验收方式也不同于前面几个阶段：不是背完术语就算过，而是能在信息不全时做出可辩护的决定，并且事后能把它写成一份让别人能复核的报告。

RUNBOOK DRILL· 换场景 · 每个时间点选一个动作 · 看代价与后果
THE FIRST 15 MINUTES

演练里最容易失分的永远不是技术动作，而是顺序：先拔网线再抓内存，内存里的 C2 地址、注入的进程、解密密钥就一起没了；先改全公司密码再查入口，攻击者用同一个后门又进来一次。应急响应的技术含量，很大一部分藏在「先做什么」这四个字里。

FRAMEWORK · 框架
① 准备（Preparation） → 能力清单、工具包、Playbook、联系人表；② 检测与分析（Detection & Analysis） → 事件确认、时间线、影响范围；③ 遏制、根除与恢复（Containment, Eradication & Recovery） → 止损、清除、业务回归；④ 事后活动（Post-Incident Activity） → 复盘报告、改进项。产出不是文档本身，而是下一个事件的起点被抬高了。 因为事件发生时你能用的东西，只有事前准备好的那些：日志留存多久、EDR 覆盖多少终端、有没有资产清单、有没有联系人表、有没有人知道自己该干什么。事发时你无法凭空造出三个月的日志，也无法在十分钟内教会一个没演练过的人做内存采集。事中做的其实是把事前准备兑现。 ① 影响范围（单机 / 单网段 / 全公司 / 客户数据）；② 业务影响（是否影响收入、是否影响交付、是否有监管上报义务）；③ 数据敏感度（个人信息、财务、源代码、商业秘密）；④ 攻击者所处阶段（仅钓鱼邮件 vs 已横向到域控）；⑤ 是否仍在活跃。分级决定谁被叫醒、多久响应、能不能停机——所以分级标准必须事前写死，事中不许临时商量。 必须包含决策点：每个关键动作前写清「什么条件下做」「谁有权批准」「不做会怎样」。例如「隔离主机」不是无条件动作——如果那是唯一的生产数据库，隔离等于停业。没有授权人的 Playbook，在凌晨三点等于没有 Playbook：值班的人不敢做决定，只能等，而攻击者不等。
DETECTION & ANALYSIS · 检测与分析
① 是真的吗（误报排除：是不是管理员在干活、是不是正常业务）；② 发生在哪台机器、什么时间（资产重要性与时间点是否合理）；③ 之前有没有相关告警（单点还是链条）；④ 主机上还有没有别的异常（进程、连接、账号、计划任务）；⑤ 往外扩散了吗（同类主机、同网段、同账号）。这五问的顺序不能乱：先确认真实性，再谈范围，否则会把大量时间花在误报上。 ① 时区不一致（设备本地时间、UTC、日志服务器时间混用）——全部统一到 UTC 再排；② 时钟偏差（主机 NTP 没同步，差几分钟就足以把因果讲反）——记录每台机器的偏差量并在时间线上标注；③ 证据粒度不同（网络流是分钟级、进程创建是毫秒级）——不要用粗粒度证据去否定细粒度证据，只能说「在这个精度下看不到」。 ① 横向（同网段、同 VLAN、可达的其他主机）；② 纵向（同一攻击链上下游：入口主机 → 跳板 → 目标）；③ 身份（用过的账号还在哪些机器上有登录记录、有没有新建账号、有没有提权）；④ 时间（攻击者最早什么时候进来的——往往比你以为的早几周）。第四点最容易被低估：你发现的那台机器，通常不是第一台被攻陷的。 Timestomping：攻击者修改文件的创建/修改/访问时间，让恶意文件混进系统文件的年代里。检测关键在 NTFS 有两套时间：$STANDARD_INFORMATION（用户态可改）和 $FILE_NAME（较难改）。两者不一致就是强指标。另外：创建时间早于操作系统安装时间、创建时间精确到 0 毫秒、时间精度异常整齐，也都是可疑特征。
CONTAINMENT & RECOVERY · 遏制与恢复
断网会同时切断三样东西：攻击者的通道（好）、你的可见性（坏）、你的取证素材（坏）。正确顺序是：先采内存（易失数据）→ 再保留网络证据（连接表、流量）→ 再做网络层隔离（ACL / VLAN 隔离，而不是拔线）→ 最后才关机。拔线还会惊动攻击者，让他立刻清痕迹或触发破坏逻辑。理想做法是「看得见地隔离」：切断他的出入，保留你的观测。 Windows：计划任务、服务、注册表 Run/RunOnce、WMI 事件订阅、启动文件夹、Image File Execution Options、COM 劫持、BITS 任务、Winlogon Shell。Linux：cron、systemd unit、.bashrc/.profile、/etc/ld.so.preload、SSH authorized_keys、init 脚本。账号层：新建本地账号、域内新增账号、SSH 公钥、应用专用密码。只删样本不清持久化，等于给攻击者留了自动回来的门。 因为「清理干净」这件事无法被证明。你只能证明你检查过的地方没有异常，无法证明没检查的地方也干净——内核态 rootkit、固件植入、你没想到的持久化点，都可能是漏网的。重装把不确定性归零，成本是一次重装的时间，收益是「不用再怀疑」。唯一的例外是取证价值极高的关键主机，那就先镜像再重装。 前提：① 根除已验证（不是「应该清干净了」，而是有检查记录）；② 入口已封堵（最初怎么进来的那条路必须堵上，否则恢复即复发）；③ 监控已就位（恢复期的机器要重点盯，攻击者最喜欢在你恢复时回来）。二次失陷常见的原因就是跳过第二条：只清了结果，没堵入口——比如只删了 webshell，没修那个上传漏洞。
FORENSICS · 取证
按 RFC 3227 的易失性顺序：CPU 寄存器/缓存 → 内存 → 网络连接/ARP/路由表 → 运行中进程 → 磁盘 → 远程日志 → 备份/归档。内存优先是因为它一断电就没了，而且它装着磁盘上永远没有的东西：解密后的载荷、内存中的凭据、C2 地址、注入的代码段。「先重启试试」是取证里最贵的四个字。 ① 无文件攻击的载荷（PowerShell 反射加载、进程注入的 shellcode，磁盘上根本没有文件）；② 明文凭据与密钥（LSASS 里的哈希、Mimikatz 抓的东西、勒索软件的加密密钥）；③ 已删除/已退出的痕迹（进程已终止但结构体还在内存里，psscan 能扫出来而 pslist 看不到）。pslist 与 psscan 的差集，就是有人不想让你看到的进程。 Prefetch（C:\Windows\Prefetch\*.pf）证明某个程序被执行过，还带执行次数、首次/末次执行时间、加载的 DLL 列表——即使文件已被删除，记录仍在。USN Journal（$Extend\$UsnJrnl）证明某个文件在某个时间被创建/改名/删除——它记录的是「变更事件」，正好补上「文件已被删掉、MFT 记录被复用」的缺口。一个证明「跑过」，一个证明「动过」。 证据链（Chain of Custody）是记录证据全生命周期的台账：谁、在什么时间、从哪里、用什么方法采集，之后每一次移交、每一次访问都要签字。哈希是这条链的技术锚点：采集时算一次，每次移交时复算，两个值一致才能证明「这份证据没被动过」。注意：哈希要在采集的第一分钟算，事后补算证明不了任何事——它只能证明「现在这份文件是完整的」，不能证明「采集时就是这份文件」。 目的是保证镜像与原盘逐位一致，任何写入都会破坏证据的可采信性。硬件方式是取证桥/写保护器（物理阻断写信号）；软件方式是在操作系统层面把目标盘挂载为只读（Linux mount -o ro、Windows 用注册表 WriteProtect 或专用工具），并在采集前后各算一次哈希做比对。软件写保护不如硬件可靠（驱动层仍可能写入），所以严肃场景必须用硬件。
NETWORK & INTEL · 网络与情报
NetFlow 只记元数据（五元组、字节数、包数、起止时间），体积极小、可留存数月，适合长期回溯与横向扫描发现；pcap 记完整内容，体积巨大、通常只留几天，适合深度分析与样本提取。正确用法是两级配合：先用 NetFlow 找到「哪台机器在什么时候跟谁说了多少话」，再回到 pcap 去挖那一段的具体内容。 ① SNI（TLS 握手里的明文域名）；② 证书信息（自签名、异常有效期、异常签发者）；③ JA3/JA3S 指纹；④ 包大小与时序（心跳包的固定间隔、上下行字节比例）；⑤ DNS 查询行为（DGA、超长域名、TXT 记录滥用、DoH 绕过）；⑥ 连接节律（固定 60 秒回连）。加密改不了包大小与时序——这是加密流量检测的根本立足点。 JA3 把 TLS ClientHello 里的版本、加密套件列表、扩展列表、椭圆曲线、曲线格式拼成一个字符串再取 MD5。不同 TLS 库（OpenSSL / SChannel / Go crypto）的默认组合不同，同一工具的所有样本往往共用同一个指纹——所以即使域名天天换、IP 天天换，JA3 不变。反过来 JA3S 是服务端指纹，用来识别 C2 服务端框架（如 Cobalt Strike 的默认 profile）。 IOC（IP、域名、哈希）半衰期以天计：攻击者换个 VPS、重新编译一次，哈希就全废了。而且 IOC 只能抓已知的、懒得换基础设施的攻击者。高价值的是 TTP（怎么做）和工具指纹（用什么做的）：它们描述的是行为模式，换域名换 IP 都改不掉。把 IOC 当消耗品，把 TTP 当资产。一条情报如果四条落地路径（检测规则 / 狩猎假设 / 阻断策略 / 演练场景）都走不通，那它就只是读物。
HUNTING & DETECTION ENGINEERING · 狩猎与检测工程
监控是等：规则响了才动，边界由规则作者事先划定。狩猎是找：主动提出「如果攻击者用了某种手法，会在数据里留下什么」，然后去数据里验证。核心差别是谁定义问题——监控回答「已知的问题出现了吗」，狩猎回答「有没有我们还没想到的问题」。所以狩猎的产出往往不是「抓到一个」，而是一条新规则。 必须可被数据证伪：包含「谁、在哪份数据里、会看到什么、什么算异常」。反例：「查一下有没有横向移动」——不可验证。正例：「如果攻击者用 PsExec 横向，那么域内主机会出现服务创建事件 7045，服务名随机且 ImagePath 指向 ADMIN$，且 4624 类型 3 登录紧随其后」。这个假设能写成查询、能跑出结果、能判定真假。 是「为什么能确信没有」。要写清：查了哪些数据源、覆盖的时间范围、查询逻辑是什么、数据的完整性如何（有没有采集缺口）、假设的哪些变体没被覆盖。因为「没发现」有两种：「真没有」和「看不到」。前者是好消息，后者是数据缺口——而数据缺口本身就是最有价值的产出，它直接告诉你下一笔预算该花在哪。 IOC（IP/域名/哈希）→ 工具特征（特定工具的行为）→ TTP（攻击技术的行为模式）→ 异常行为（偏离基线）。优先 TTP 是因为它稳定性最高：IOC 天天换，工具可以换，但「用 certutil 下载文件」「创建服务做横向」这些技术动作是攻击者不得不做的事。合理的配比是 TTP 70% / IOC 20% / 异常 10%——异常检测误报高，但它是唯一有可能发现全新攻击的一层，不能没有。 把检测规则当作代码来管：版本控制、PR 评审、自动化测试（原子测试验证能触发）、CI/CD 部署、健康度监控。它解决的是规则的四类死亡方式：存在某人界面里没有版本记录 / 改坏了无法回滚 / 离职后无人维护 / 没人知道为什么这么写。最关键的环节是自动化测试——没被验证过的覆盖，只是纸面上的覆盖。
COMPREHENSIVE · 综合
① 接警与分级：确认告警来源、资产重要性、是否在业务高峰 → 定级、拉人。② 不惊动的前提下取证：内存镜像（WinPmem/DumpIt）→ 算哈希 → 导出连接表/进程/服务/计划任务/账号 → 记录系统时间与 NTP 偏差。③ 隔离：网络层 ACL 隔离（保留 EDR 通道），不拔线不关机。④ 研判：进程树、父进程异常、签名、命令行、外联地址；比对 ATT&CK；构建时间线（统一 UTC）。⑤ 扩范围：同网段、同账号、同漏洞面；查入口（Web 日志、VPN 日志、邮件网关）。⑥ 根除：清持久化点 + 修入口 + 改相关凭据（含服务账号、API Key）。⑦ 恢复：重装或从可信基线重建 → 验证 → 加强监控。⑧ 复盘：报告含时间线（每条带证据源）、影响范围、根因、改进项（分「立即/一月/一季」三档）。 ① 影子副本删除：vssadmin delete shadows / wbadmin delete catalog → 进程创建日志（4688/Sysmon 1）；② 批量文件改名：单进程短时间大量 SetRenameInformation → 文件系统审计/Sysmon 11；③ 勒索信落地：README.txt/HOW_TO_DECRYPT 类文件名批量出现 → Sysmon 11/EDR 文件事件；④ 加密行为：高熵写入 + 原文件删除 → EDR 行为链；⑤ 横向扩散：SMB 445 短时间多目标 + 服务创建 7045 → 网络流 + 安全日志；⑥ 凭据窃取前置：LSASS 访问（Sysmon 10 TargetImage=lsass.exe）；⑦ 禁用恢复/杀软：bcdedit recoveryenabled no、Set-MpPreference -DisableRealtimeMonitoring → 命令行日志。关键设计：把「删除影子副本」和「批量改名」做成高置信度即时告警，因为这两个动作一旦出现，加密通常已经开始，留给你的窗口只有几分钟。

通过这一章的自测，说明你已经知道正确的做法。但真实事件里，知道和做到之间还有一段距离，这段距离只能靠演练填平：桌面推演（讨论式，零成本）、半实战演练（在测试环境真做一遍内存采集）、红蓝对抗（有人在对面真的在打）。

最容易被跳过的是桌面推演，因为它看起来「只是聊天」。但它恰恰是暴露「谁有权决定停机」这类组织问题的最便宜方式——而这类问题，往往才是真实事件里真正的瓶颈。
